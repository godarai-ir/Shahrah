# واژه‌نامه محتوایی گدارAI

این فایل قرارداد نگارشی مستندات فارسی گدارAI را نگه می‌دارد. پیش از نوشتن یا بازنویسی صفحه‌های مرتبط، واژه‌های همین فایل را مبنا قرار بده. این واژه‌نامه قابل‌گسترش است؛ فعلاً بخش‌های «شروع و نمای کلی»، «درگاه، مدل‌ها و اتصال» و «گاردریل‌ها» تکمیل شده‌اند و بخش‌های بعدی، مثل پرامپت‌ها، بعداً اضافه می‌شوند.

برای مستندات کاربرمحور، متن‌های رابط کاربری محصول منبع اصلی نام‌گذاری هستند. اگر یک گزینه، فیلد، دکمه یا وضعیت در UI با عنوانی مشخص نمایش داده می‌شود، همان عنوان را در راهنمای مربوط به همان UI به کار ببر و مقدار فنی API را جداگانه با قالب کد بیاور.

## قواعد عمومی

- نام برند در نثر فارسی همیشه «گدارAI» است. در پیام خطا، کد، شناسه یا نام رسمی لاتین، مقدار واقعی مثل `GodarAI` را تغییر نده.
- نام فیلد، مقدار API، سرآیند، مسیر، شناسه فنی، فرمان و قطعه‌کد را ترجمه نکن و با قالب کد بنویس؛ مانند `operation`، `validate`، `x-godarai-guardrails` و `guardrails/slug`.
- برای اصطلاح‌های فنی، بار نخست معادل فارسی را بنویس و اگر لازم است برابر انگلیسی را داخل پرانتز بیاور. پس از آن، معادل فارسی را ادامه بده.
- در جدول‌های مرجع، مقدارهای واقعی API را نگه دار. معادل فارسی را در ستون توضیح یا متن اطراف بیاور.
- برای نام کنترل‌ها، گزینه‌های فهرست کشویی، لیبل فرم‌ها، عنوان ستون‌ها و پیام‌های اعتبارسنجی، بهتر است که به متن UI پایبند باشی؛ مگر اینکه مطمئن باشی که واژه پیشنهادی خودت از واژه به کار رفته در UI گویاتر است. در این صورت، UI را با مستندات هماهنگ کن.
- از واژه‌های انگلیسی پراکنده در جمله فارسی استفاده نکن، مگر اینکه نام رسمی، مقدار فنی یا عبارت قابل‌جست‌وجو باشد.
- برای متن فارسی از «درخواست»، «پاسخ»، «سرآیند»، «شناسه فنی»، «گزارش رخداد» و «رد درخواست» استفاده کن.
- در مستندات لازم نیست که به فرم اشاره کنی. مثلاً نیاز نیست بنویسی «نوع در فرم». کافی است بنویسی «نوع».

## شروع و نمای کلی

این بخش برای صفحه‌های معرفی، نمای کلی قابلیت‌ها و شروع سریع است. هدف این صفحه‌ها کمک به کاربر تازه‌وارد است تا بداند گدارAI چه کاری انجام می‌دهد، از کجا شروع کند و برای اولین درخواست به چه چیزهایی نیاز دارد.

### واژه‌های اصلی

| اصطلاح فنی یا رایج | نگارش پیشنهادی | کاربرد و نکته |
| --- | --- | --- |
| GodarAI / Godar AI | گدارAI | در نثر فارسی همیشه «گدارAI» بنویس. اگر نام رسمی لاتین در کد، دامنه، شناسه یا تصویر آمده، مقدار واقعی را تغییر نده. |
| LLM Gateway | درگاه مدل‌های زبانی | بار نخست می‌توان نوشت «درگاه مدل‌های زبانی (LLM Gateway)». پس از آن «درگاه» کافی است. از «گیت‌وی» فقط وقتی استفاده کن که عنوان رسمی UI یا عبارت فنی قابل‌جست‌وجو باشد. |
| gateway | درگاه | برای نقش معماری گدارAI. در کد و مقدار فنی مانند `Gateway Base URL` مقدار را نگه دار و در متن اطراف «نشانی پایه درگاه» بنویس. |
| OpenAI-compatible API | API سازگار با OpenAI | برای توضیح سازگاری قراردادها. از «OpenAI-style» در نثر فارسی استفاده نکن. |
| workspace | فضای کاری | عنوان کاربرپسند برای محدوده کار سازمان یا تیم در پنل. در متن‌های معماری اگر لازم است، بار نخست «محیط اختصاصی سازمان (Tenant)» را توضیح بده. |
| tenant | محیط اختصاصی سازمان | در صفحه‌های شروع و راهنمای کاربر، معمولاً «فضای کاری» طبیعی‌تر است. مقدار فنی `tenant` و مسیرهای API را ترجمه نکن. |
| dashboard | داشبورد | چون UI فعلی «داشبورد» را نشان می‌دهد، در مستندات کاربرمحور همین را نگه دار. |
| quick start | شروع سریع | عنوان دسته و صفحه. در متن فارسی از «quick start» استفاده نکن، مگر در نام پیام یا فایل. |
| first request | اولین درخواست | برای مسیر عملی شروع. از «اولین request» استفاده نکن. |
| request / response | درخواست / پاسخ | در متن فارسی همین دو واژه را به کار ببر. مقدارهای فنی مثل `messages` و `choices` را ترجمه نکن. |
| client application | اپلیکیشن مصرف‌کننده | وقتی منظور سرویس یا برنامه‌ای است که مدل را فراخوانی می‌کند. برای متن کوتاه‌تر می‌توان «اپلیکیشن» نوشت. |
| provider | ارائه‌دهنده مدل | اگر منظور شرکت یا سرویس بالادست است. وقتی UI از «ارائه‌دهنده» استفاده می‌کند، همان را بیاور. |
| provider account | حساب ارائه‌دهنده | اتصال مستقل به یک ارائه‌دهنده مدل. برای راهنمای شروع سریع، «حساب ارائه‌دهنده» را بر «اتصال‌دهنده» مقدم بدان، مگر اینکه دقیقاً به منوی UI اشاره می‌کنی. |
| LLM connectors | اتصال‌دهنده‌های LLM | عنوان منوی tenant-admin است. در توضیح مفهومی بنویس «بخش اتصال‌دهنده‌های LLM، حساب‌های ارائه‌دهنده را مدیریت می‌کند». |
| integration | اتصال | در نثر فارسی از «اتصال» استفاده کن. اگر مقدار یا عنوان UI انگلیسی است، آن را با قالب کد بیاور. |
| credential | اعتبارنامه | برای کلید یا اطلاعات احراز هویت ارائه‌دهنده. از «credential» در نثر استفاده نکن. |
| API Key | کلید دسترسی (API Key) | اگر منظور کلید ارائه‌دهنده است، بگو «کلید دسترسی ارائه‌دهنده». اگر منظور کلید گدارAI است، نوع آن را روشن کن: «توکن دسترسی شخصی» یا «کلید دسترسی مجازی». |
| Personal Access Token / PAT | توکن دسترسی شخصی (PAT) | برای تست، توسعه و استفاده انسانی. پس از نخستین کاربرد می‌توان «PAT» نوشت. |
| Virtual Access Token / VAT | کلید دسترسی مجازی (VAT) | برای سرویس‌ها و هویت‌های غیرانسانی. اگر صفحه درباره Virtual User است، تفاوت «کاربر مجازی» و «VAT» را روشن کن. |
| service identity | هویت سرویس | اگر UI همچنان انگلیسی است، در راهنمای UI بار نخست بنویس «هویت سرویس (`service identity`)». |
| virtual user / virtual account | کاربر مجازی / حساب مجازی | در UI فعلی «کاربران مجازی» آمده است. وقتی مفهوم هویت غیرانسانی برای سرویس مطرح است، «کاربر مجازی» را توضیح بده و مقدارهای فنی را ترجمه نکن. |
| model | مدل | در نثر فارسی از «model» استفاده نکن. برای مقدار فنی فیلد، `model` را نگه دار. |
| model ID | شناسه مدل | مقدار واقعی شناسه را با قالب کد بیاور. |
| virtual model | مدل مجازی | بار نخست می‌توان نوشت «مدل مجازی (Virtual Model)». از «alias» به‌عنوان توضیح دوم استفاده کن، نه جایگزین نام اصلی. |
| alias | شناسه فنی / نام مستعار | در UI مدل مجازی «شناسه فنی» تثبیت شده است. در متن مفهومی اگر منظور نام پایدار مصرفی است، «نام مستعار پایدار» هم قابل قبول است. |
| routing | مسیریابی | برای انتخاب مقصد مدل. از «route کردن» در نثر استفاده نکن. |
| fallback | مسیر جایگزین | اگر بار نخست نیاز به یافت‌پذیری دارد، بنویس «مسیر جایگزین (Fallback)». |
| retry | تلاش دوباره | در فیلد فنی مقدار `retry` را نگه دار. |
| timeout | مهلت پاسخ | واحد را مشخص کن؛ مثلاً ثانیه یا میلی‌ثانیه. |
| telemetry | داده‌های پایش | اگر دقیق‌تر است، به اجزای آن اشاره کن: «گزارش رخداد، رد درخواست و سنجه». در عنوان یا UI انگلیسی، مقدار واقعی را نگه دار. |
| logs | گزارش رخدادها | برای نثر مستندات. عنوان UI ممکن است «لاگ درخواست‌ها» باشد؛ هنگام ارجاع به همان منو، عنوان UI را حفظ کن. |
| traces | رد درخواست‌ها | برای صفحه UI «ردیابی درخواست‌ها» را هم می‌توان به‌کار برد. برای مفهوم توزیع‌شده، «ردیابی توزیع‌شده» بنویس. |
| metrics | سنجه‌ها | اگر عنوان UI است «متریک مدل‌ها» را حفظ کن؛ در نثر عمومی «سنجه‌ها» روان‌تر است. |
| billing | مدیریت مالی / صورتحساب | برای منوی UI «مدیریت مالی» یا عنوان‌های موجود را حفظ کن. در توضیح هزینه، «محاسبه هزینه» و «سقف هزینه» دقیق‌تر است. |

### عنوان‌ها و مسیرهای کاربرمحور

| مسیر یا بخش UI | عنوان فارسی | کاربرد در مستندات |
| --- | --- | --- |
| `/quick-start` | شروع سریع | مسیر عملی برای آماده‌سازی فضای کاری و ارسال اولین درخواست. |
| `/provider-accounts` | اتصال‌دهنده‌های LLM | هنگام اشاره به منو از همین عنوان استفاده کن و در توضیح بنویس «حساب ارائه‌دهنده». |
| `/personal-access-tokens` | توکن‌های دسترسی شخصی | برای ساخت PAT. از «API Key گدارAI» به‌تنهایی استفاده نکن، چون نوع کلید مبهم می‌شود. |
| `/virtual-users` | کاربران مجازی | برای ساخت هویت سرویس و VAT. |
| `/virtual-models` | مدل‌های مجازی | برای ساخت شناسه پایدار مصرف مدل. |
| `/logs` | لاگ درخواست‌ها | هنگام اشاره به منو همین عنوان را حفظ کن؛ در نثر توضیحی «گزارش رخدادها» بنویس. |
| `/traces` | ردیابی درخواست‌ها | برای مشاهده مسیر اجرای یک درخواست. |
| `/metrics` | متریک مدل‌ها | برای پایش مصرف، تاخیر و رفتار مدل‌ها. |

### سه مقدار لازم برای اولین درخواست

| مقدار فنی | نگارش پیشنهادی | نکته |
| --- | --- | --- |
| `Gateway Base URL` / `base_url` | نشانی پایه درگاه | مقدار واقعی را در قالب کد بیاور. برای OpenAI SDK معمولاً مقدار با `/v1` پایان می‌یابد. |
| `model` / `Model ID` | شناسه مدل | کاربر نباید شناسه را حدس بزند؛ باید آن را از مدل‌های مجاز فضای کاری یا مدل مجازی بردارد. |
| `Authorization` / `API Key` | توکن دسترسی | نوع توکن را مشخص کن: PAT برای تست انسانی، VAT برای سرویس یا محیط عملیاتی. |

## درگاه، مدل‌ها و اتصال

این بخش برای صفحه‌هایی است که مشتری را از شناخت معماری درگاه به اتصال عملی محصول خودش می‌رسانند: معرفی درگاه، مدل مجازی، اولین درخواست، احراز هویت، سرآیندهای درخواست و انتخاب SDK. خواننده این بخش توسعه‌دهنده گدارAI نیست؛ مشتری فنی یا تیم محصولی است که می‌خواهد با کمترین ابهام، گدارAI را در اپلیکیشن خود استفاده کند.

### جهت‌گیری لحن

- حس اعتمادپذیری را با دقت، شفافیت و قابل‌بررسی بودن منتقل کن، نه با صفت‌های تبلیغاتی.
- به‌جای وعده کلی، نشان بده کدام بخش قابل کنترل است: توکن، شناسه مدل، حساب ارائه‌دهنده، مدل مجازی، گزارش رخداد و رد درخواست.
- وقتی چیزی وابسته به تنظیمات فضای کاری، پلن یا استقرار است، آن را روشن بگو و از قطعیت بی‌منبع پرهیز کن.
- برای مشتری تازه‌وارد، مسیر پیش‌فرض را مشخص کن: API سازگار با OpenAI، توکن گدارAI، شناسه مدل مجاز و بررسی نتیجه در پایش.

### واژه‌های معماری اتصال

| اصطلاح فنی یا رایج | نگارش پیشنهادی | کاربرد و نکته |
| --- | --- | --- |
| gateway base URL | نشانی پایه درگاه | برای مقدار SDK یا متغیر محیطی. در نمونه OpenAI SDK معمولاً مقدار با `/v1` پایان می‌یابد. |
| endpoint | نقطه پایانی | در عنوان‌های API می‌توان نام رسمی مثل `Chat Completions` را نگه داشت. |
| upstream provider | ارائه‌دهنده بالادست | وقتی درخواست پس از عبور از گدارAI به سرویس مدل فرستاده می‌شود. |
| provider credential | اعتبارنامه ارائه‌دهنده | کلید یا اطلاعات اتصال به ارائه‌دهنده بالادست. در نمونه‌ها مقدار واقعی نیاور. |
| provider account | حساب ارائه‌دهنده | اتصال مستقل به ارائه‌دهنده مدل. در متن UI، بخش «اتصال‌دهنده‌های LLM» محل مدیریت حساب‌های ارائه‌دهنده است. |
| model catalog / discovery | کاتالوگ مدل‌ها / کشف مدل | اگر درباره فهرست مدل‌های ارائه‌دهنده است. مقدار فنی `Discovery` را فقط در متن UI یا عیب‌یابی فنی نگه دار. |
| enabled model | مدل فعال | مدلی که روی حساب ارائه‌دهنده برای مصرف در فضای کاری فعال شده است. |
| allowed model | مدل مجاز | مدلی که هویت یا توکن فعلی اجازه مصرف آن را دارد. «فعال» و «مجاز» را یکی نکن. |
| effective access | دسترسی مؤثر | نتیجه ترکیب تنظیمات حساب ارائه‌دهنده، مدل مجازی، کاربر، تیم و نوع توکن. |
| FQN | FQN | ترجمه نکن. در توضیح بنویس «شناسه کامل مدل یا حساب که برای کپی و فراخوانی استفاده می‌شود». |
| model mode / exposed mode | حالت قابل ارائه | برای حالت‌هایی مثل `chat`، `embedding`، `moderation` و تصویر. مقدار فنی mode را در جدول‌ها نگه دار. |
| capability | قابلیت | برای توانایی مدل مثل چت، تصویر، صوت یا ابزارها. |
| deployment | مقصد فعال / استقرار مدل | اگر درباره مقصد واقعی پشت درگاه است، «مقصد» معمولاً برای مشتری روشن‌تر است. مقدار فنی `deployment` را ترجمه نکن. |

### مدل مجازی

| اصطلاح فنی یا رایج | نگارش پیشنهادی | کاربرد و نکته |
| --- | --- | --- |
| virtual model | مدل مجازی | برای شناسه پایدار مصرف مدل. بار نخست می‌توان برابر انگلیسی را داخل پرانتز آورد. |
| alias در مدل مجازی | شناسه فنی | UI مدل مجازی همین عنوان را نشان می‌دهد. در توضیح مفهومی می‌توان گفت «شناسه پایدار مصرفی». |
| target | مقصد | هر مدل واقعی یا حساب ارائه‌دهنده‌ای که پشت مدل مجازی قرار می‌گیرد. |
| routing strategy | استراتژی مسیریابی | عنوان UI همین است. مقدارهای «اولویتی» و «وزنی» را به کار ببر. |
| priority routing | مسیریابی اولویتی | درخواست از مقصد اول شروع می‌شود و در شرایط خطا به مقصدهای بعدی می‌رود. |
| weighted routing | مسیریابی وزنی | ترافیک بر اساس وزن بین مقصدها تقسیم می‌شود. جمع وزن‌ها باید ۱۰۰ باشد. |
| fallback codes | کدهای مسیر جایگزین | عنوان UI «کدهای فال‌بک» است؛ در نثر توضیحی «کدهای مسیر جایگزین» روشن‌تر است. |
| retry codes | کدهای تلاش دوباره | عنوان UI «کدهای تکرار» است؛ در نثر توضیحی «کدهای تلاش دوباره» را ترجیح بده. |
| fallback exhausted | پایان مسیرهای جایگزین | اگر کد خطا `fallback_exhausted` است، مقدار فنی را نگه دار و در توضیح فارسی بنویس «همه مقصدهای مجاز امتحان شده‌اند». |

### عملیات و شیوه اعمال

| اصطلاح فنی | نگارش پیشنهادی | کاربرد و نکته |
| --- | --- | --- |
| `operation` | عملیات | وقتی درباره فیلد API حرف می‌زنی، مقدار فنی را نگه دار: `operation`. در توضیح فارسی بگو «عملیات گاردریل». |
| `validate` | اعتبارسنجی | عنوان UI در فرم گاردریل‌ها «اعتبارسنجی» است. در نمونه و جدول مقدار واقعی `validate` را نگه دار. |
| `mutate` | اصلاح محتوا | عنوان UI در فرم گاردریل‌ها «اصلاح محتوا» است. در توضیح مفهومی می‌توان گفت این نوع اقدام متن را تغییر می‌دهد. |
| `enforcement` | شیوه اعمال | از «شیوه اجرا» فقط وقتی استفاده کن که متن درباره زمان یا محل اجراست. برای فیلد `enforcement`، معادل اصلی «شیوه اعمال» است. |
| `audit` | عبور همراه با نشانه‌گذاری | عنوان UI در فرم گاردریل‌ها همین است. در توضیح بنویس: «تخطی با وضعیت `flagged` ثبت می‌شود و مسیر ادامه پیدا می‌کند». مقدار فنی را ترجمه نکن. |
| `enforce` | عدم عبور و لاگ | عنوان UI در فرم گاردریل‌ها همین است. در توضیح فنی بنویس: «تخطی مسیر را متوقف می‌کند و خطا برمی‌گرداند». |
| `enforce_ignore_error` | عدم عبور - بدون لاگ | عنوان UI در فرم گاردریل‌ها همین است. در توضیح فنی دقیق بنویس: تخطی را متوقف می‌کند، اما خطای اجرای خود گاردریل را مانند `enforce` متوقف‌کننده حساب نمی‌کند. |
| violation | تخطی | وقتی متن با سیاست گاردریل ناسازگار است. از «نقض» برای متن‌های حقوقی‌تر استفاده کن. |
| block / blocked | توقف / متوقف‌شده | برای وضعیت فنی مقدار `blocked` را نگه دار. در نثر «درخواست متوقف می‌شود» طبیعی‌تر از «بلاک می‌شود» است. |
| flag / flagged | نشانه‌گذاری / `flagged` | در متن بگو «با وضعیت `flagged` ثبت می‌شود». |
| pass / passed | عبور / `passed` | در متن بگو «گاردریل بدون تخطی عبور می‌کند» یا «وضعیت `passed` ثبت می‌شود». |
| error | خطا / `error` | برای وضعیت فنی `error` را نگه دار. در متن «خطای اجرای گاردریل» بنویس. |
| mutate / mutated | تغییر / `mutated` | برای وضعیت فنی `mutated` را نگه دار. در نثر «متن تغییر می‌کند». |

### فیلدهای تنظیمات

| فیلد | نگارش پیشنهادی | نکته |
| --- | --- | --- |
| `terms` | عبارت‌ها | فهرست عبارت‌هایی که `keyword_blocklist` جست‌وجو می‌کند. |
| `patterns` | الگوها | فهرست Regexها. مقدار فنی `patterns` را ترجمه نکن. |
| `pattern` | الگو | برای `regex_replace`. |
| `case_sensitive` | حساس به بزرگی و کوچکی حروف | در نمونه فنی مقدار فیلد را نگه دار. |
| `redaction_text` | متن جایگزین | برای ماسک‌کردن مقدارها. |
| `replacement` | متن جایگزین | برای جایگزینی Regex. |
| `min` | حداقل | مقدار فنی را نگه دار. |
| `max` | حداکثر | مقدار فنی را نگه دار. |
| `schema` | schema | اگر درباره JSON Schema است، مقدار فنی `schema` را نگه دار و در توضیح بگو «تعریف ساختار». |
| `keys` | کلیدها | برای `json_keys`. |
| `mode` | حالت بررسی | مقدارهای `any`، `all`، `none`، `must_contain` و `must_not_contain` را ترجمه نکن. |
| `languages` | زبان‌های کد | مقدار زبان‌ها مثل `sql` و `python` را ترجمه نکن. |
| `token_regex` | Regex استخراج توکن | برای `jwt_validation`. |
| `issuer` | صادرکننده | برای claim یا تنظیم JWT. |
| `audience` | مخاطب | برای claim یا تنظیم JWT. |
| `shared_secret` | کلید مشترک | مقدار واقعی را هرگز در نمونه مستندات نیاور. |
| `inline_jwks` | JWKS درون‌خطی | `JWKS` را ترجمه نکن. |
| `jwks_uri` | آدرس JWKS | عنوان UI همین است. در متن عمومی می‌توان «نشانی JWKS» هم نوشت، اما راهنمای این بخش باید با UI هماهنگ باشد. |
| `introspection_url` | آدرس بررسی توکن | عنوان UI همین است. برای نقطه پایانی بررسی فعال‌بودن توکن استفاده می‌شود. |
| `introspection_auth_header` | هدر احراز هویت بررسی توکن | عنوان UI همین است. مقدار نمونه نباید واقعی باشد. |
| `max_bytes` | حداکثر حجم | واحد را مشخص کن؛ مثلاً «بایت». |
| `allowed_hosts` | دامنه‌های مجاز | اگر مقدار شامل host است، ترجمه نکن. |
| `timeout_ms` | مهلت زمانی | واحد را در توضیح «میلی‌ثانیه» بنویس. |
| `allow_private_networks` | اجازه به شبکه‌های خصوصی | درباره خطر SSRF با احتیاط توضیح بده. |
