# لاگ‌ها و بررسی درخواست‌ها در GodarAI

بخش `Logs` در GodarAI جایی است که می‌توانید درخواست‌های عبور کرده از گیت‌وی را به‌صورت زمانی بررسی کنید و بفهمید هر request دقیقاً چه مسیری را طی کرده، از کدام مدل استفاده کرده، چه هزینه‌ای داشته و در چه وضعیتی تمام شده است.

در عمل، این صفحه برای troubleshooting روزمره یکی از مهم‌ترین نقاط ورود است. وقتی کاربری می‌گوید «پاسخ بد بود»، «درخواست کند شد» یا «هزینه غیرمنتظره بالا رفت»، معمولاً اولین جایی که باید نگاه کنید همین لاگ‌ها هستند.

## چرا Logs مهم است؟

لاگ‌های گیت‌وی فقط یک فهرست رویداد نیستند. این بخش کمک می‌کند:

- requestها را به‌ترتیب زمانی ببینید
- رفتار routing، retry، fallback و cache را بررسی کنید
- model، provider و latency را کنار هم تحلیل کنید
- token usage و cost را در سطح request ببینید
- داده لازم برای عیب‌یابی یا تحلیل incident را سریع‌تر پیدا کنید

اگر [OpenTelemetry برای مشاهده‌پذیری](/observability-opentelemetry) دید end-to-end روی کل سیستم می‌دهد، Logs بیشتر برای مشاهده مستقیم رفتار خود GodarAI و ترافیک LLM شما کاربرد دارد.

## در لاگ هر درخواست چه چیزهایی مهم است؟

بسته به نوع endpoint و وضعیت اجرای request، معمولاً این دسته از اطلاعات برای شما مهم‌تر هستند:

- زمان درخواست
- نوع endpoint یا workload
- model و provider
- latency
- token usage
- هزینه
- وضعیت cache، retry، fallback یا load balancing
- اطلاعات هویتی مثل tenant، team یا virtual account

این اطلاعات وقتی ارزش بیشتری پیدا می‌کنند که با [رهگیری هزینه](/cost-tracking) و سیاست‌های عملیاتی مثل [Rate Limiting](/guides/rate-limiting) و [Budget Limiting](/guides/budget-limiting) کنار هم دیده شوند.

## Logs چه سؤال‌هایی را سریع جواب می‌دهد؟

در استفاده واقعی، معمولاً این سؤال‌ها از لاگ‌ها شروع می‌شوند:

- آیا cache واقعاً hit شده یا نه؟
- آیا request retry شده است؟
- آیا fallback فعال شده است؟
- کدام مدل یا provider درگیر بوده؟
- این request چقدر latency یا cost داشته؟
- خطا از gateway بوده یا upstream؟

برای همین، Logs فقط ابزار debugging نیست؛ بخشی از ابزار عملیات روزانه و بهینه‌سازی مصرف هم هست.

## تحلیل وضعیت‌های اجرایی

یکی از کاربردی‌ترین بخش‌های Logs، دیدن وضعیت قابلیت‌های gateway روی هر request است. برای مثال:

- `Cache`: آیا غیرفعال بوده، miss شده یا hit داده است؟
- `Retry`: آیا تلاشی برای retry انجام شده یا نه؟
- `Fallback`: آیا request به مقصد جایگزین رفته است؟
- `Load balancing`: آیا توزیع بار بین مقصدها فعال بوده است؟

این وضعیت‌ها کمک می‌کنند خیلی سریع بفهمید policyها فقط «تعریف شده‌اند» یا واقعاً در ترافیک production اثر گذاشته‌اند.

## باز کردن جزئیات یک log

وقتی یک log را باز می‌کنید، معمولاً هدف فقط دیدن summary نیست. جزئیات log برای این کارها ارزش دارد:

- بررسی payload request و response
- دیدن خطاها و metadataهای اجرایی
- بررسی config یا policy مؤثر بر request
- دنبال‌کردن نتیجه fallback، retry یا guardrail

برای تیم‌هایی که چند سرویس یا چند workflow دارند، همین جزئیات تفاوت بین «حدس زدن مشکل» و «فهمیدن علت واقعی» را ایجاد می‌کند.

## نسبت Logs با Guardrails و Moderation

اگر از [Guardrails](/guardrails) یا [Moderation](/supported-apis/moderation) استفاده می‌کنید، Logs یکی از مهم‌ترین جاها برای تحلیل اثر آن‌هاست. این بخش به شما کمک می‌کند بفهمید:

- کدام policy بیشترین fail را ایجاد کرده
- کدام workload بیشتر درگیر moderation شده
- deny، retry یا fallback چند بار فعال شده‌اند
- آیا policy باعث افت کیفیت تجربه یا افزایش latency شده است

بدون این دید، طراحی guardrailها بیشتر به حدس شبیه می‌شود تا تصمیم مبتنی بر داده.

## بازپخش یا تکرار درخواست برای دیباگ

در بسیاری از workflowهای عملیاتی، مفید است بتوانید یک request مسئله‌دار را دوباره اجرا کنید یا نمونه‌ای نزدیک به آن را برای آزمایش نگه دارید. حتی اگر UI نهایی یا جزئیات implementation در GodarAI با منابع مرجع متفاوت باشد، از نظر محصولی این الگو ارزش زیادی دارد:

- requestهای مسئله‌دار را سریع‌تر reproduce می‌کنید
- تغییر prompt یا config را روی همان سناریو می‌سنجید
- ریشه خطا را بدون ساختن مجدد شرایط از صفر پیدا می‌کنید

اگر چنین قابلیتی در محیط شما فعال باشد، لاگ‌ها به یک دروازه عملی برای debugging تبدیل می‌شوند، نه فقط یک آرشیو تاریخی.

## اشتراک‌گذاری log با اعضای تیم

برای همکاری تیمی، مهم است بتوانید درباره یک request مشخص حرف بزنید، نه درباره «یک خطای مبهم». به همین دلیل، هر سازوکاری که log مشخص را برای هم‌تیمی‌ها قابل ارجاع کند، ارزش عملیاتی بالایی دارد.

در GodarAI هم بهتر است Logs را به‌عنوان نقطه مرجع مشترک بین تیم محصول، backend، زیرساخت و AI engineering ببینید.

## داده حساس و حالت Do Not Track

همیشه منطقی نیست که متن کامل request و response را ذخیره کنید. بعضی workloadها داده حساس، شخصی یا سازمانی دارند و نیازمند احتیاط بیشتری هستند.

در چنین سناریوهایی، الگوی `Do Not Track` یا ثبت حداقلی داده می‌تواند مفید باشد. ایده اصلی این است:

- متادیتاهای عملیاتی مثل latency، token usage و cost ثبت شوند
- اما payload کامل request و response ذخیره نشود یا محدود شود

این رویکرد به شما کمک می‌کند بین مشاهده‌پذیری و حریم داده تعادل بهتری برقرار کنید.

برای درک بهتر headerها و metadataهای مؤثر، [Request Headers](/request-headers) را هم ببینید.

## چه زمانی Logs به‌تنهایی کافی نیست؟

هرچند Logs ابزار بسیار مهمی است، اما همیشه کافی نیست. اگر مسئله شما این جنس باشد:

- زنجیره‌ای از چند سرویس و job غیرهمزمان
- correlation بین frontend و backend
- تحلیل span-level در چند لایه
- مشاهده رفتار دیتابیس، queue و gateway کنار هم

در این حالت، باید Logs را با [OpenTelemetry برای مشاهده‌پذیری](/observability-opentelemetry) ترکیب کنید.

## رویکرد پیشنهادی برای استفاده روزمره

برای بیشتر تیم‌ها، این الگو عملی است:

1. هر incident را اول از Logs شروع کنید.
2. model، cost، latency و وضعیت cache/retry/fallback را سریع بررسی کنید.
3. اگر مسئله عمیق‌تر بود، آن را با OTel و تریس‌های لایه‌های دیگر correlate کنید.
4. اگر الگوی تکرارشونده دیدید، policy یا config مرتبط را بازبینی کنید.

## چند توصیه عملی

### فقط خطاها را نگاه نکنید

خیلی از بهینه‌سازی‌ها از درخواست‌های «موفق اما ناکارآمد» شروع می‌شوند، نه فقط از failureهای آشکار.

### لاگ‌ها را با هویت و هزینه بخوانید

وقتی بدانید request متعلق به کدام tenant، team یا workload بوده، تحلیل شما بسیار کاربردی‌تر می‌شود.

### وضعیت cache و fallback را جدی بگیرید

این وضعیت‌ها معمولاً سریع‌ترین سرنخ برای فهم رفتار واقعی gateway هستند.

### برای داده حساس از logging کامل استفاده نکنید

اگر محتوای حساس دارید، طراحی logging باید با policy حریم داده و نیازهای سازمانی شما هم‌راستا باشد.

## FAQ

### Logs چه تفاوتی با OpenTelemetry دارد؟

Logs بیشتر روی رفتار خود GodarAI و درخواست‌های عبوری از gateway تمرکز دارد، اما OTel برای همبستگی end-to-end بین کل سرویس‌ها و لایه‌ها مناسب‌تر است.

### آیا از روی Logs می‌توان فهمید cache یا fallback فعال شده یا نه؟

بله، یکی از مهم‌ترین کاربردهای Logs دقیقاً همین است که وضعیت قابلیت‌های gateway را روی هر request قابل مشاهده می‌کند.

### اگر داده حساس داشته باشیم، آیا باید logging را کامل خاموش کنیم؟

نه لزوماً. در بسیاری از سناریوها بهتر است payload را ثبت نکنید اما متادیتاهای عملیاتی مثل latency، tokens و cost را نگه دارید.
