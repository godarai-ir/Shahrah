# حذف یا ماسک‌کردن داده شخصی (PII Redaction)

`PII Redaction` یعنی شناسایی و جایگزین‌کردن اطلاعات حساس و هویتی پیش از آن‌که به مدل زبانی برسند یا از مدل برگردند. این اطلاعات می‌تواند شامل ایمیل، شماره تلفن، شناسه‌های سازمانی، اطلاعات کارت، نام اشخاص یا سایر داده‌های حساس باشد.

در GodarAI، این قابلیت را بهتر است به‌عنوان یک الگوی Guardrail ببینیم: هدف این نیست که فقط تشخیص دهیم داده حساس وجود دارد، بلکه باید آن را پیش از ادامه جریان، حذف، ماسک یا با شناسه‌ای استاندارد جایگزین کنیم.

## چرا PII Redaction مهم است؟

در بسیاری از workflowهای واقعی، کاربران یا سیستم‌ها ناخواسته داده حساس را داخل prompt می‌فرستند. برای مثال:

- اطلاعات تماس مشتری
- کد ملی، شماره پرونده یا شناسه کارمند
- داده‌های مالی یا بانکی
- متن قرارداد، تیکت یا یادداشت داخلی
- داده‌های شخصی داخل خروجی ابزارها یا agentها

اگر این داده‌ها بدون کنترل به مدل برسند، ریسک‌های مهمی ایجاد می‌شود:

- نقض حریم داده
- افزایش ریسک انطباق (Compliance)
- نشت اطلاعات در لاگ‌ها یا سامانه‌های جانبی
- دشوار شدن اشتراک‌گذاری امن داده برای debugging

PII Redaction کمک می‌کند این ریسک پیش از رسیدن به لایه inference کاهش پیدا کند.

## PII Redaction چه تفاوتی با Moderation دارد؟

این دو موضوع نزدیک‌اند، اما یکسان نیستند:

- [Moderation](/supported-apis/moderation) بیشتر می‌پرسد «آیا این محتوا حساس، ممنوع یا پرریسک است؟»
- `PII Redaction` می‌پرسد «اگر داده حساس وجود دارد، چگونه قبل از ادامه پردازش آن را خنثی یا مخفی کنیم؟»

به زبان ساده، moderation بیشتر برای تشخیص است، اما redaction برای تغییر امن payload پیش از ادامه مسیر.

## این قابلیت معمولاً کجا اعمال می‌شود؟

بیشتر مواقع، PII Redaction در این نقاط معنا پیدا می‌کند:

- روی `ورودی` پیش از ارسال prompt به model
- روی `خروجی` پیش از نمایش پاسخ به کاربر یا ارسال آن به سرویس دیگر
- روی داده‌ای که از ابزارها یا سیستم‌های بیرونی وارد جریان agentic می‌شود

در اکثر سناریوها، شروع از ورودی منطقی‌تر است؛ چون بهترین حالت این است که داده حساس اساساً به مدل نرسد.

## چه چیزهایی می‌توانند redact شوند؟

بسته به ruleها و detectorهای شما، این دسته‌ها معمولاً کاندیدای رایج هستند:

- ایمیل
- شماره تلفن
- آدرس یا موقعیت جغرافیایی
- اطلاعات کارت یا پرداخت
- نام افراد
- شناسه‌های سازمانی و کارمندی
- الگوهای سفارشی داخلی

برای GodarAI، این بخش آخر خیلی مهم است. چون بسیاری از داده‌های حساس سازمانی الزاماً PII عمومی نیستند و ممکن است شناسه‌های داخلی، شماره تیکت، شماره پرونده یا کدهای domain-specific باشند.

## Redaction چگونه انجام می‌شود؟

دو رویکرد رایج وجود دارد:

- استفاده از detectorها یا Guardrailهای آماده برای دسته‌های شناخته‌شده PII
- استفاده از ruleهای سفارشی، به‌ویژه بر پایه Regex

در حالت دوم، شما الگو را مشخص می‌کنید و تعیین می‌کنید matchها با چه چیزی جایگزین شوند. برای مثال:

- `[EMAIL_REDACTED]`
- `[PHONE_HIDDEN]`
- `{{CUSTOMER_ID_1}}`
- `[SENSITIVE_VALUE]`

این رویکرد برای سناریوهای سازمانی بسیار مفید است، چون حساسیت‌های واقعی شما همیشه به چند الگوی عمومی خلاصه نمی‌شوند.

## چرا Regex همچنان مهم است؟

هرچند detectorهای آماده کمک بزرگی هستند، اما در بسیاری از سازمان‌ها داده حساس شکل بسیار مشخص و ساختارمند دارد. برای مثال:

- شناسه پرسنلی با الگوی داخلی
- شماره درخواست یا پرونده
- کد پروژه یا مشتری
- قالب‌های قراردادی مشخص

در این شرایط، Guardrail مبتنی بر Regex هنوز یکی از دقیق‌ترین و کنترل‌پذیرترین ابزارهاست. البته باید با دقت طراحی شود تا:

- false positive زیاد نداشته باشد
- داده بی‌ربط را بی‌دلیل ماسک نکند
- هزینه و latency غیرضروری ایجاد نکند

## بعد از شناسایی، چه چیزی جایگزین می‌شود؟

جایگزینی معمولاً به یکی از این شکل‌هاست:

- یک placeholder ثابت مثل `[REDACTED]`
- یک placeholder نوع‌مند مثل `[EMAIL_REDACTED]`
- یک شناسه استانداردشده و شماره‌دار مثل `{{EMAIL_ADDRESS_1}}`

هرکدام مزایا و trade-off خود را دارند:

- placeholder ثابت ساده‌تر است، اما context کمتری می‌دهد
- placeholder نوع‌مند برای فهم مدل یا pipeline مفیدتر است
- placeholder شماره‌دار برای حفظ تمایز بین چند مقدار هم‌نوع بهتر است

## نسبت PII Redaction با Logs

یکی از مهم‌ترین دلایل استفاده از redaction این است که فقط مدل را محافظت نمی‌کند؛ زنجیره مشاهده‌پذیری را هم امن‌تر می‌کند. اگر payload قبل از ادامه مسیر redact شود:

- احتمال نشت داده در [Logs](/observability-logs) کمتر می‌شود
- اشتراک‌گذاری log با هم‌تیمی‌ها امن‌تر می‌شود
- debugging بدون مشاهده مستقیم داده خام ساده‌تر می‌شود

با این حال، باید همیشه روشن باشد که redaction در کدام نقطه از مسیر اتفاق می‌افتد؛ چون اگر داده قبل از redaction در جای دیگری ثبت شده باشد، هنوز ریسک باقی می‌ماند.

## نسبت PII Redaction با Guardrails

PII Redaction را بهتر است یکی از الگوهای تخصصی [Guardrails](/guardrails) ببینید. Guardrail عمومی می‌تواند فقط هشدار دهد یا request را متوقف کند، اما Redaction یک گام عملی‌تر برمی‌دارد:

- داده حساس را پیدا می‌کند
- payload را transform می‌کند
- نسخه transform‌شده را به مسیر بعدی می‌فرستد

این تفاوت مهم است، چون در بعضی سناریوها نمی‌خواهید request را deny کنید؛ فقط می‌خواهید آن را برای ارسال امن‌تر کنید.

## چه زمانی redaction بهتر از deny است؟

همیشه بستن کامل request بهترین تصمیم نیست. گاهی:

- کاربر فقط ناخواسته یک ایمیل یا شماره وارد کرده
- داده حساس برای task اصلی ضروری نیست
- می‌خواهید تجربه کاربر حفظ شود ولی ریسک پایین بیاید

در این موارد، redaction از deny مناسب‌تر است. اما اگر حضور آن داده ذاتاً غیرمجاز باشد، ممکن است deny هنوز انتخاب درست‌تری باشد.

## Best Practices

### از subset کوچک شروع کنید

اول redaction را روی چند جریان پرریسک فعال کنید و رفتار واقعی آن را در production بسنجید.

### روی داده‌های domain-specific سرمایه‌گذاری کنید

الگوهای حساس واقعی شما ممکن است بیشتر از ایمیل و تلفن، به شناسه‌های داخلی و داده‌های سازمانی مربوط باشند.

### لاگ‌ها را بعد از فعال‌سازی بررسی کنید

لازم است در [Logs](/observability-logs) و telemetry ببینید چه چیزهایی transform شده‌اند و آیا false positive یا false negative قابل‌توجهی وجود دارد.

### جایگزین‌ها را معنی‌دار انتخاب کنید

Placeholder باید هم امن باشد و هم تا حد لازم context را برای ادامه pipeline حفظ کند.

### redaction را با policyهای دیگر ترکیب کنید

خیلی وقت‌ها بهترین نتیجه از ترکیب redaction با [Guardrails](/guardrails)، [Moderation](/supported-apis/moderation) و policyهای هویتی به‌دست می‌آید.

## محدودیت‌ها

PII Redaction هم مثل هر کنترل دیگری محدودیت دارد:

- patternهای آماده همیشه همه داده‌های حساس domain-specific را نمی‌گیرند
- Regex ضعیف می‌تواند false positive یا false negative بسازد
- بعضی transformها ممکن است context مفید برای مدل را از بین ببرند
- اگر نقطه اجرای redaction دیر باشد، ممکن است داده قبلاً در جایی دیگر دیده یا ثبت شده باشد

## FAQ

### آیا می‌توانم الگوهای redaction را سفارشی کنم؟

بله، در سناریوهای سازمانی این کار معمولاً ضروری است. به‌ویژه اگر داده حساس شما از نوع شناسه‌ها و الگوهای داخلی باشد، Guardrailهای مبتنی بر Regex یا ruleهای سفارشی ارزش زیادی دارند.

### آیا PII Redaction فقط برای ورودی است؟

خیر. از نظر مفهومی روی خروجی هم معنا دارد، مخصوصاً وقتی پاسخ مدل قرار است به کاربر نمایش داده شود یا وارد سیستم دیگری شود.

### آیا redaction همیشه بهتر از deny است؟

نه. اگر حضور داده حساس ذاتاً غیرمجاز باشد، deny می‌تواند تصمیم درست‌تری باشد. redaction بیشتر برای سناریوهایی خوب است که می‌خواهید جریان کار حفظ شود اما داده خام عبور نکند.
