# چرخش API Key در GodarAI

`API Key Rotation` یعنی تعویض دوره‌ای secret یک کلید بدون این‌که سرویس شما دچار downtime یا اختلال ناگهانی شود. در محیط‌های production، چرخش کلید باید یک فرآیند عادی و قابل‌پیش‌بینی باشد، نه یک عملیات اضطراری فقط بعد از incident.

این صفحه روی مفهوم، الگوها و بهترین‌عملکردهای چرخش کلید در GodarAI تمرکز دارد تا بتوانید lifecycle کلیدهای انسانی و سرویس‌محور را امن‌تر مدیریت کنید.

## چرا rotation مهم است؟

اگر یک API key برای مدت طولانی بدون تغییر باقی بماند، ریسک‌های مهمی ایجاد می‌شود:

- نشت کلید دیرتر کشف می‌شود اما همچنان معتبر می‌ماند
- کلید در چند سرویس، محیط یا pipeline پخش می‌شود
- تغییر مالکیت یا تغییر تیم بدون بازنگری در secret اتفاق می‌افتد
- audit و hygiene امنیتی ضعیف‌تر می‌شود

چرخش کلید کمک می‌کند secretها عمر نامحدود نداشته باشند و اگر کلیدی جایی درز کرد، پنجره سوءاستفاده محدودتر شود.

## rotation چه تفاوتی با revoke دارد؟

این دو یکی نیستند:

- `revoke` یعنی کلید فعلی دیگر قابل استفاده نباشد
- `rotate` یعنی secret جدید صادر شود و کلید قبلی فوراً یا بعد از یک بازه گذار از مدار خارج شود

اگر می‌خواهید یک سرویس همچنان بدون قطعی کار کند، rotation معمولاً انتخاب بهتری از revoke مستقیم است.

## ایده اصلی rotation بدون downtime

الگوی سالم این است که:

1. secret جدید تولید شود
2. secret قبلی برای یک بازه محدود هنوز معتبر بماند
3. سرویس‌ها و integrationها به secret جدید مهاجرت کنند
4. بعد از پایان بازه گذار، secret قبلی منقضی یا غیرفعال شود

این بازه گذار همان چیزی است که جلوی شکست ناگهانی deploymentها، workerها یا cron jobهایی را می‌گیرد که هنوز secret قدیمی را استفاده می‌کنند.

## بازه گذار (Transition Window) چیست؟

بازه گذار یک پنجره زمانی محدود است که در آن:

- کلید جدید معتبر است
- کلید قبلی هم هنوز موقتاً پذیرفته می‌شود

این الگو مخصوصاً برای workloadهایی مهم است که به‌روزرسانی secret در آن‌ها فوری نیست، مثل:

- چند سرویس مستقل
- workerهای پراکنده
- jobهای زمان‌بندی‌شده
- چند محیط deployment

هرچه سیستم شما پراکنده‌تر باشد، طراحی درست این پنجره مهم‌تر می‌شود.

## در GodarAI کدام کلیدها بیشتر نیاز به rotation دارند؟

از نظر عملیاتی، همه کلیدها مهم‌اند، اما حساسیت آن‌ها یکسان نیست:

- `PAT`ها بیشتر برای توسعه و استفاده انسانی هستند و باید کوتاه‌عمرتر و محدودتر باشند
- `VAT`ها معمولاً در production و سرویس‌های غیرانسانی استفاده می‌شوند و rotation منظم برای آن‌ها بسیار مهم‌تر است

برای آشنایی با تفاوت این دو، [ساخت API Key در گدارAI](/guides/api-keys) و [احراز هویت](/authentication) را هم ببینید.

## rotation دستی یا خودکار؟

دو الگوی اصلی وجود دارد:

### rotation دستی

برای زمانی مناسب است که:

- می‌خواهید یک کلید خاص را فوری عوض کنید
- suspect به نشت یا misuse دارید
- در حال انجام migration کنترل‌شده هستید

مزیتش کنترل بیشتر است، اما اگر زیاد به آن تکیه کنید، به‌مرور عملیات امنیتی شما وابسته به یادآوری انسان‌ها می‌شود.

### rotation خودکار

برای production معمولاً الگوی بالغ‌تری است. در این حالت:

- زمان چرخش از قبل تعریف می‌شود
- secretها به‌صورت دوره‌ای عوض می‌شوند
- اخطارها و مهلت‌های لازم از قبل معلوم هستند

این روش برای workloadهای پایدار و سازمانی، hygiene امنیتی بهتری ایجاد می‌کند.

## چه چیزهایی باید در rotation policy مشخص باشند؟

یک policy خوب برای rotation معمولاً این پرسش‌ها را روشن می‌کند:

- هر کلید هر چند وقت یک بار باید rotate شود؟
- بازه گذار چقدر باشد؟
- چه کسی اجازه rotate دارد؟
- بعد از rotate چه کسی باید مطلع شود؟
- اگر workloadی هنوز secret قدیمی را استفاده می‌کند، چه‌طور آن را پیدا می‌کنیم؟

حتی اگر پیاده‌سازی نهایی GodarAI در محیط شما با مستند مرجع متفاوت باشد، این سؤال‌ها از نظر عملیاتی ثابت‌اند.

## API key ID و secret چه نسبتی دارند؟

در بسیاری از طراحی‌های سالم، هویت منطقی کلید ثابت می‌ماند اما secret آن عوض می‌شود. این مدل مزیت دارد، چون:

- attribution و audit به همان کلید منطقی وصل می‌ماند
- usage history از بین نمی‌رود
- budget، cost tracking و analytics دچار گسست نمی‌شوند

پس rotation بهتر است «تعویض secret» باشد، نه ساختن دستی یک هویت کاملاً جدید مگر در سناریوهای خاص.

## چه محدودیت‌هایی باید در نظر بگیریم؟

برای rotation امن، معمولاً این محدودیت‌ها مفیدند:

- همزمان تعداد نسخه‌های معتبر secret محدود باشد
- وقتی transition فعال است، rotate دوباره بدون دلیل مجاز نباشد
- مدت transition از period اصلی rotation کوتاه‌تر باشد
- عملیات rotate در audit log ثبت شود

این محدودیت‌ها جلوی آشفتگی در مدیریت secretها را می‌گیرند.

## ارتباط rotation با audit و observability

rotation فقط یک اقدام امنیتی نیست؛ یک رویداد عملیاتی هم هست. بهتر است بعد از هر rotate بتوانید بدانید:

- کدام کلید rotate شده
- چه زمانی rotate شده
- حالت دستی بوده یا خودکار
- secret قبلی تا چه زمانی معتبر می‌ماند
- آیا هنوز requestهایی با secret قبلی می‌آیند یا نه

برای همین، rotation باید با [لاگ درخواست‌ها](/observability-logs) و سیاست‌های دسترسی شما هماهنگ باشد.

## بهترین‌عملکردها برای کاربران GodarAI

### برای production از VAT استفاده کنید

چرخش منظم secret برای workloadهای غیرانسانی زمانی تمیزتر است که کلید به یک هویت سرویس‌محور متصل باشد، نه به یک فرد.

### برای هر workload کلید جدا داشته باشید

اگر چند سرویس از یک کلید مشترک استفاده کنند، rotation، attribution و incident response سخت‌تر می‌شود.

### transition window را خیلی کوتاه یا خیلی بلند نگیرید

اگر خیلی کوتاه باشد، سرویس‌ها قبل از به‌روزرسانی می‌شکنند. اگر خیلی بلند باشد، secret قدیمی بیش از حد در سیستم می‌ماند.

### rotation را فقط واکنشی نبینید

بهترین rotationها آن‌هایی هستند که قبل از incident و به‌صورت برنامه‌ریزی‌شده انجام می‌شوند.

### بعد از rotate، مصرف secret قدیمی را پایش کنید

اگر هنوز درخواست با secret قبلی می‌آید، یعنی بخشی از سیستم به‌روزرسانی نشده و باید پیدا شود.

## چه زمانی به revoke فوری نیاز داریم؟

rotation همیشه کافی نیست. اگر:

- نشت کلید قطعی شده
- استفاده مخرب در حال وقوع است
- کلید به فرد یا سیستم اشتباه تعلق داشته

ممکن است revoke فوری و قطع کامل دسترسی از rotation مهم‌تر باشد. در این حالت، trade-off شما بین availability و containment است.

## FAQ

### آیا rotation فقط برای کلیدهای production مهم است؟

خیر، اما برای production بسیار حیاتی‌تر است. PATهای توسعه هم بهتر است بی‌عمر نامحدود نباشند.

### آیا rotation یعنی کلید قبلی همان لحظه از کار بیفتد؟

نه لزوماً. در طراحی‌های بدون downtime، معمولاً یک بازه گذار در نظر گرفته می‌شود تا migration به secret جدید تدریجی انجام شود.

### برای backend و worker از PAT استفاده کنیم یا VAT؟

برای workloadهای غیرانسانی بهتر است از `VAT` استفاده کنید تا rotation، revoke، audit و ownership مستقل از افراد باشد.
