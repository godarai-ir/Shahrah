# ساخت API Key در گدارAI

برای استفاده برنامه‌نویسی از گدارAI، به یک API Key نیاز دارید. این کلید به اپلیکیشن، اسکریپت، CLI یا سرویس شما اجازه می‌دهد درخواست‌های OpenAI-compatible را از طریق gateway گدارAI ارسال کند، بدون اینکه لازم باشد API key ارائه‌دهنده را مستقیم داخل اپلیکیشن پخش کنید.

در GodarAI ایده اصلی ساده است:

- توسعه‌دهنده یا کاربر انسانی از یک کلید شخصی استفاده می‌کند
- سرویس، job، agent یا CI/CD از یک کلید سرویس‌محور استفاده می‌کند
- دسترسی به provider و modelها در سطح خود پلتفرم کنترل می‌شود، نه با پخش secretهای جداگانه در همه سرویس‌ها

## چه نوع API Keyهایی در GodarAI داریم؟

در معماری فعلی GodarAI دو نوع کلید اصلی وجود دارد:

| نوع | وابسته به | مناسب برای |
| --- | --- | --- |
| `PAT` | کاربر انسانی | توسعه فردی، تست، استفاده شخصی |
| `VAT` | کاربر مجازی (Virtual User) | سرویس‌ها، production، jobها، CI/CD |

## `PAT` چیست؟

توکن دسترسی شخصی (Personal Access Token) یا `PAT` برای زمانی مناسب است که یک کاربر واقعی می‌خواهد از طرف خودش به gateway وصل شود.

سناریوهای مناسب:

- توسعه محلی
- تست با SDK
- استفاده در اسکریپت‌های شخصی
- آزمایش سریع مدل‌ها قبل از ساخت integration رسمی

نکته مهم در پیاده‌سازی فعلی GodarAI این است که هنگام ساخت PAT دیگر `allowed_models` یا `models` مستقیماً از کاربر پذیرفته نمی‌شود. دسترسی PAT به مدل‌ها از طریق تنظیمات دسترسی Provider Account و Virtual Model کنترل می‌شود.

## `VAT` چیست؟

توکن حساب مجازی (Virtual Account Token) یا `VAT` برای هویت‌های غیرانسانی طراحی شده است؛ یعنی جاهایی که کلید باید به یک سرویس یا workload تعلق داشته باشد، نه به یک شخص.

سناریوهای مناسب:

- backend service
- worker
- cron job
- agent
- CI/CD pipeline
- سرویس production

در GodarAI، VAT به یک کاربر مجازی (Virtual User) متصل می‌شود و می‌تواند به team یا org unit هم scope بگیرد. این مدل باعث می‌شود lifecycle کلیدهای سرویس از lifecycle افراد جدا بماند.

## کدام نوع کلید را انتخاب کنیم؟

قاعده ساده:

- اگر یک انسان از کلید استفاده می‌کند، `PAT`
- اگر یک اپلیکیشن یا سرویس از کلید استفاده می‌کند، `VAT`

اگر بین این دو مردد هستید، این سؤال را بپرسید:

«اگر صاحب این کلید از تیم خارج شود، آیا باید کلید هم از بین برود؟»

- اگر بله، PAT مناسب‌تر است
- اگر نه، VAT انتخاب حرفه‌ای‌تری است

## API Key در GodarAI چه کاری می‌کند؟

API Key در GodarAI فقط برای احراز هویت نیست. این کلید بخشی از مدل کنترل دسترسی، مشاهده‌پذیری و مصرف هم هست. با استفاده از آن، سیستم می‌تواند:

- tenant درخواست را تشخیص دهد
- کاربر یا virtual user را شناسایی کند
- دسترسی به modelها را بررسی کند
- هزینه و مصرف را به همان هویت نسبت دهد
- policyهایی مثل rate limit و budget limit را اعمال کند

## کلیدها کجا ساخته و مدیریت می‌شوند؟

بر اساس APIهای فعلی backend، مسیرهای اصلی مدیریت کلید در GodarAI این‌ها هستند:

- `POST /api/v1/personal-access-tokens`
- `GET /api/v1/personal-access-tokens`
- `DELETE /api/v1/personal-access-tokens/:id`
- `POST /api/v1/keys/vat`
- `GET /api/v1/virtual-users/:virtualUserID/tokens`
- `POST /api/v1/virtual-users/:virtualUserID/tokens`
- `POST /api/v1/virtual-users/:virtualUserID/tokens/:tokenID/revoke`
- `POST /api/v1/virtual-users/:virtualUserID/tokens/:tokenID/rotate`

برای کاربر docs، معنای عملی این routeها این است:

- PATها در flow شخصی کاربر ساخته و revoke می‌شوند
- VATها در flow مربوط به virtual user و token management ساخته و مدیریت می‌شوند

## ساخت PAT در GodarAI

برای ساخت PAT معمولاً این اطلاعات کافی است:

- نام کلید
- در صورت نیاز، زمان انقضا

در backend فعلی، اگر نام تکراری باشد درخواست رد می‌شود. همچنین مدل‌ها در زمان ساخت PAT به‌صورت مستقیم روی خود request تنظیم نمی‌شوند و از مسیر policyهای دسترسی کنترل می‌شوند.

### چه زمانی PAT انتخاب خوبی نیست؟

PAT برای production انتخاب خوبی نیست وقتی:

- کلید بین چند سرویس share می‌شود
- مالک کلید یک فرد است ولی مصرف مربوط به یک سیستم است
- نیاز به revoke/rotate سازمان‌یافته برای workloadها دارید

در این حالت بهتر است از VAT استفاده کنید.

## ساخت VAT در GodarAI

برای ساخت VAT معمولاً باید یک کاربر مجازی (Virtual User) داشته باشید. در backend فعلی GodarAI هم route قدیمی `POST /api/v1/keys/vat` وجود دارد و هم flow استانداردتر virtual-user token.

برای VAT این نکات مهم‌اند:

- VAT برای سرویس‌ها و workloadهای غیرانسانی است
- باید به team یا virtual user معتبر متصل باشد
- اگر virtual user غیرفعال باشد، ساخت token رد می‌شود
- اگر مدل‌های مجاز تعریف شوند، باید در scope دسترسی همان هویت باشند

## Virtual User چیست و چرا مهم است؟

کاربر مجازی (Virtual User) یک هویت غیرانسانی در GodarAI است که برای سرویس‌ها ساخته می‌شود. مزیتش این است که:

- کلید سرویس به یک شخص واقعی وابسته نیست
- audit و attribution شفاف‌تر می‌شود
- revoke و rotate بدون دست‌زدن به PAT افراد انجام می‌شود
- محدودیت‌ها و بودجه‌ها را می‌توان روی همین identity اعمال کرد

## بعد از ساخت کلید چه چیزی دریافت می‌کنیم؟

در پیاده‌سازی فعلی، هنگام ساخت کلید:

- یک کلید خام برای استفاده واقعی برگردانده می‌شود
- یک نسخه mask‌شده برای نمایش و مدیریت نگه داشته می‌شود
- در دیتابیس فقط `token_hash` ذخیره می‌شود، نه خود کلید خام

این یعنی از نظر امنیتی باید این فرض را داشته باشید که:

- کلید خام را فقط همان بار اول می‌بینید
- اگر آن را از دست بدهید، باید کلید جدید بسازید یا rotate کنید

## rotate و revoke چه فرقی دارند؟

- `revoke`: کلید فعلی را غیرفعال می‌کند
- `rotate`: یک کلید جدید می‌سازد و کلید قبلی را بلافاصله یا بعد از یک grace period از مدار خارج می‌کند

در backend فعلی GodarAI، برای VAT قابلیت rotate وجود دارد و raw token جدید فقط هنگام rotate برگردانده می‌شود.

## API Key را چگونه در کد استفاده کنیم؟

رایج‌ترین الگو در گدارAI، استفاده از همان کلید در SDKهای OpenAI-compatible است:

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)
```

یا با متغیر محیطی:

```bash
export OPENAI_BASE_URL="YOUR_GODARAI_BASE_URL"
export OPENAI_API_KEY="YOUR_GODARAI_API_KEY"
```

## چند توصیه عملی برای کاربران GodarAI

### برای توسعه از PAT و برای production از VAT استفاده کنید

این ساده‌ترین و سالم‌ترین تفکیک عملیاتی است.

### کلید سرویس را به فرد وابسته نکنید

اگر سرویس شما با PAT یک فرد کار می‌کند، دیر یا زود در revoke، audit یا ownership به مشکل می‌خورید.

### کلید خام را مثل secret واقعی نگه دارید

چون raw token فقط یک بار نمایش داده می‌شود، آن را از همان ابتدا در secret manager یا محیط امن قرار دهید.

### برای هر workload مهم، کلید جدا بسازید

بهتر است backend، worker، CI و agentها هرکدام کلید مستقل داشته باشند تا:

- revoke هدفمند شود
- گزارش مصرف شفاف بماند
- policyهای جداگانه قابل اعمال باشند

### از model access مرکزی استفاده کنید

به‌جای اینکه کلیدها را با دسترسی‌های پراکنده مدیریت کنید، دسترسی modelها را از طریق Provider Account و Virtual Model policyها کنترل کنید.

## جمع‌بندی

API Key در GodarAI فقط یک secret برای ورود نیست؛ بخشی از هویت، دسترسی، مصرف و کنترل عملیاتی gateway است. اگر برای افراد از PAT و برای سرویس‌ها از VAT استفاده کنید، مدیریت دسترسی، گزارش‌گیری، rotate/revoke و اعمال policyهایی مثل budget limit و rate limit بسیار تمیزتر و قابل اتکاتر خواهد شد.
