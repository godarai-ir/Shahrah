# کنترل نرخ درخواست در گدارAI

کنترل نرخ درخواست در گدارAI برای این ساخته شده است که مصرف مدل‌ها از کنترل خارج نشود. وقتی چند تیم، چند سرویس یا محصول از یک گیت‌وی مشترک استفاده می‌کنند، کافی است یک حلقه بی‌نهایت، یک integration اشتباه یا یک جهش ناگهانی در ترافیک اتفاق بیفتد تا هزینه، ظرفیت یا کیفیت سرویس به‌سرعت تحت فشار قرار بگیرد.

در گدارAI، قواعد کنترل نرخ (Rate Limiting Rules) به شما کمک می‌کنند:

- تعداد درخواست‌ها را در یک بازه زمانی محدود کنید
- مصرف توکن را برای مدل‌ها یا مصرف‌کننده‌ها (افراد، تیم‌ها، واحدهای سازمانی) کنترل کنید
- برای کاربران، تیم‌ها یا کلیدهای مختلف سیاست متفاوت داشته باشید
- قبل از آن‌که هزینه یا فشار ترافیکی به ارائه‌دهنده LLM منتقل شود، ترافیک را در خود gateway مهار کنید

## این قابلیت چه مسئله‌ای را حل می‌کند؟

چند سناریوی رایج:

- یک سرویس داخلی به دلیل باگ، به‌طور ناخواسته هزاران درخواست به مدل می‌فرستد
- یک کاربر/تیم با تسک‌های ساده‌تر نباید به اندازه کاربر/تیم با تسک‌های پیچیده‌تر، از ظرفیت مدل استفاده کند
- یک مدل ارائه دهنده LLM خاص ظرفیت محدودی دارد و باید ترافیک آن کنترل شود
- می‌خواهید برای هر فرد / تیم / واحد سازمانی، هر کلید دسترسی یا هر مدل، سقف جداگانه داشته باشید

در همه این حالت‌ها، rate limiting یکی از لایه‌های اصلی کنترل عملیاتی در GodarAI است.

## مدل ذهنی GodarAI برای rate limit

در GodarAI، قوانین کنترل نرخ به‌صورت ایزوله در سطح فضای کاربری شما نگهداری می‌شوند و هر قانون معمولاً این اجزا را دارد:

- `rule_id`: شناسه یکتا برای قانون
- `name`: نام نمایشی برای پنل یا گزارش
- `conditions`: شرایطی که تعیین می‌کنند قانون روی چه درخواست‌هایی اعمال شود
- `limit`: تعریف خود محدودیت
- `priority`: اولویت قانون
- `conflict_behavior`: رفتار در برخورد چند قانون
- `response_behavior`: نحوه پاسخ در صورت عبور از حد مجاز
- `retry_after_header`: آیا هدر `Retry-After` برگردانده شود یا نه
- `effective_from` و `expires_at`: بازه زمانی اعتبار قانون

## چه چیزهایی را می‌توان محدود کرد؟

در سطح محصول، rate limiting معمولاً روی این ابعاد معنا پیدا می‌کند:

- تعداد درخواست در دقیقه (`RPM`)
- تعداد توکن در دقیقه (`TPM`)
- محدودیت ساعتی یا روزانه برای سناریوهای خاص
- محدودیت بر اساس actor، تیم، مدل یا metadata

در پیاده‌سازی فعلی GodarAI، هدرهای استاندارد rate limit هم روی پاسخ‌ها پشتیبانی می‌شوند:

- `X-Ratelimit-Limit`
- `X-Ratelimit-Remaining`
- `X-Ratelimit-Reset`

اگر درخواست رد شود، گدارAI پاسخ `429` با خطای سازگار با الگوی OpenAI برمی‌گرداند.

## ترتیب ارزیابی قوانین

نکته مهم در طراحی قوانین این است که قانون‌های عمومی و قانون‌های خاص را با دقت بچینید. در بسیاری از سناریوها، اولویت و رفتار برخورد قوانین تعیین می‌کند که در زمان تطبیق، کدام محدودیت مؤثر باشد.

در مدل فعلی GodarAI، سه رفتار اصلی برای برخورد ruleها وجود دارد:

- `first_match`
- `most_restrictive`
- `apply_all`

معمولاً `first_match` یا `most_restrictive` نقطه شروع بهتری است:

- `first_match`: وقتی ترتیب قانون‌ها برایتان مهم است
- `most_restrictive`: وقتی می‌خواهید محدودکننده‌ترین قانون برنده شود

## شرایط (Conditions) را چگونه تعریف کنیم؟

در GodarAI قوانین بر پایه `subjects`، `models` و `metadata` وضع می‌شوند:

- هویت فراخواننده: کاربر، سرویس، virtual user یا virtual key
- فرد، تیم یا واحد سازمانی
- مدل یا مدل مجازی
- metadataهای ارسالی از سمت کلاینت
- بازه زمانی فعال بودن قانون

برای کاربر GodarAI، سؤال اصلی این است: «این محدودیت دقیقاً روی کدام ترافیک باید اعمال شود؟»

## ساختار limit

در GodarAI، بخش `limit` معمولاً به‌صورت یک شیء JSON تعریف می‌شود. بسته به سطح کاربری شما، این object می‌تواند شامل مواردی مثل این باشد:

```json
{
  "metric": "requests_per_minute",
  "value": 1000
}
```

یا:

```json
{
  "metric": "tokens_per_minute",
  "value": 50000
}
```

## چند الگوی رایج برای طراحی قانون

### 1. محدودیت برای هر واحد سازمانی

اگر می‌خواهید هر واحد سازمانی سقف خودش را داشته باشد، قانون باید روی ترافیک همان واحد سازمانی اعمال شود و از بقیه واحدهای سازمانی جدا باشد.

مناسب برای:

- واحدهای سازمانی با مسولیت‌های مختلف
- کنترل ظرفیت واحدهای پرمصرف
- جلوگیری از توزیع ناعادلانه منابع بین واحدهای سازمانی

### 2. محدودیت برای هر تیم

اگر چند تیم از GodarAI استفاده می‌کنند، می‌توانید برای هر تیم محدودیت جداگانه بگذارید.

مناسب برای:

- تقسیم ظرفیت بین تیم‌های product، backend و support
- کنترل هزینه بین تیم‌های داخلی
- اعمال سیاست‌های متفاوت بر اساس سطح دسترسی

### 3. محدودیت برای هر مدل

بعضی مدل‌ها گران‌تر یا محدودترند. در این حالت، بهتر است قانون روی خود مدل یا مدل مجازی اعمال شود.

مناسب برای:

- مدل‌های premium
- مدل‌های self-hosted با GPU محدود
- rollout مرحله‌ای روی مدل‌های جدید

### 4. محدودیت برای هر کلید یا هویت سرویس

اگر از virtual key یا virtual user استفاده می‌کنید، می‌توانید برای هر integration سقف مستقل بگذارید.

مناسب برای:

- سرویس‌های production
- jobهای پس‌زمینه
- agentها یا workflowهای خودکار

### 5. محدودیت بر اساس metadata

اگر اپلیکیشن شما metadataهایی مثل `project_id`، `environment` یا `customer_tier` ارسال می‌کند، می‌توانید قانون را به همان metadata متکی کنید.

این الگو زمانی مفید است که یک کلید مشترک دارید، اما می‌خواهید محدودیت در سطح contextهای داخلی‌تر اعمال شود.

## نمونه rule مفهومی در GodarAI

نمونه زیر یک representation مفهومی است تا شکل قانون روشن شود:

```json
{
  "rule_id": "team-backend-gpt4-rpm",
  "name": "محدودیت RPM برای تیم backend روی GPT-4",
  "enabled": true,
  "priority": 10,
  "conditions": {
    "team_id": "backend",
    "model": "gpt-4o"
  },
  "limit": {
    "metric": "requests_per_minute",
    "value": 1000
  },
  "conflict_behavior": "most_restrictive",
  "response_behavior": "return_429",
  "retry_after_header": true
}
```

نمونه دوم برای محدودیت توکن بر اساس metadata:

```json
{
  "rule_id": "project-hourly-token-limit",
  "name": "محدودیت ساعتی توکن برای هر پروژه",
  "enabled": true,
  "priority": 20,
  "conditions": {
    "metadata.project_id": "proj-123"
  },
  "limit": {
    "metric": "tokens_per_hour",
    "value": 50000
  },
  "conflict_behavior": "first_match",
  "response_behavior": "return_429",
  "retry_after_header": true
}
```

## وقتی درخواست از حد مجاز عبور می‌کند چه می‌شود؟

وقتی درخواست از سقف تعیین‌شده عبور کند:

- گدارAI قبل از ارسال ترافیک به provider آن را متوقف می‌کند
- پاسخ `429 Too Many Requests` برمی‌گردد
- بدنه خطا به‌شکل سازگار با APIهای OpenAI-style نرمالایز می‌شود
- هدرهای rate limit برای تشخیص وضعیت فعلی برگردانده می‌شوند

این یعنی rate limiting در GodarAI فقط یک گزارش‌گیری منفعل نیست؛ بخشی از بررسی‌های الزامی در مسیر درخواست است.

## رابطه rate limiting با بودجه

نرخ محدودیت (Rate Limit) و محدودیت بودجه (Budget Limit) دو چیز متفاوت‌اند:

- rate limit برای کنترل سرعت مصرف در یک بازه زمانی است
- budget limit برای کنترل مجموع مصرف مالی یا حجمی در یک دوره طولانی‌تر است

در عمل، معمولاً این دو را با هم استفاده می‌کنید:

- rate limit جلوی spike و burst را می‌گیرد
- budget limit جلوی مصرف بیش از سقف ماهانه یا اعتباری را می‌گیرد

برای GodarAI این تفکیک خیلی مهم است، چون هزینه روی مانده اعتبار مصرف هم اثر مستقیم دارد.

## چند توصیه عملی برای طراحی قانون

### قانون‌های خاص را بالاتر بگذارید

اگر رفتار شما به ترتیب قانون‌ها حساس است، اول قانون‌های خاص‌تر و بعد قانون‌های عمومی‌تر را تعریف کنید.

### بین مدل و مدل مجازی تفاوت قائل شوید

اگر اپلیکیشن‌ها ازمدل مجازی و نام مستعار (alias) استفاده می‌کنند، بهتر است در طراحی قوانین روشن باشد که محدودیت روی alias اعمال می‌شود یا روی model واقعی پشت آن.

### برای production و staging قانون جدا داشته باشید

اگر metadata محیط را ارسال می‌کنید، قانونهای production و staging را از هم جدا کنید تا تست‌ها روی ترافیک واقعی اثر نگذارند.

### soft limit را فقط با مشاهده‌پذیری خوب فعال کنید

اگر از soft limit استفاده می‌کنید، حتماً مطمئن شوید logs، metrics و alerting شما به‌اندازه کافی واضح هستند. soft limit بدون visibility خوب، خیلی زود به یک فیچر بی‌اثر تبدیل می‌شود.

### از `Retry-After` غافل نشوید

اگر کلاینت‌های شما قابلیت تکرار مجدد (retry) کنترل‌شده دارند، برگرداندن `Retry-After` کمک می‌کند رفتار کلاینت منطقی‌تر شود.

## GodarAI این محدودیت‌ها را چگونه اعمال می‌کند؟

در لایه فنی، GodarAI از cache و state سریع برای enforcement استفاده می‌کند و نتیجه را در مسیر درخواست ثبت می‌کند. در پیاده‌سازی فعلی، هدرهای rate limit و رفتار `429` بخشی از قرارداد endpointهای اصلی مثل `chat/completions` و `embeddings` هستند.

## جمع‌بندی

کنترل نرخ درخواست در GodarAI یکی از مهم‌ترین ابزارهای مهار هزینه، محافظت از ظرفیت مدل‌ها و حفظ کیفیت سرویس در سطح gateway است. اگر ruleها را با scope درست، اولویت شفاف و ترکیب مناسب با budget limit طراحی کنید، rate limiting می‌تواند از ساده‌ترین و موثرترین لایه‌های دفاع عملیاتی در محصول شما باشد.
