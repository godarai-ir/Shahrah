# مدل Tenant، Team و Account در گدارAI

برای کار با گدارAI، فقط دانستن اینکه «چطور API call بزنیم» کافی نیست. خیلی زود به این سؤال‌ها می‌رسید:

- کاربر دقیقاً در کدام مرز تعریف می‌شود؟
- تیم چه فرقی با tenant دارد؟
- هویت سرویس باید به user وصل شود یا به virtual user؟
- «account» در محصول دقیقاً به چه معناست؟

این صفحه یک نمای سطح‌بالا از مدل هویتی و عملیاتی GodarAI می‌دهد تا جای هر مفهوم در ساختار محصول روشن باشد.

## تصویر کلی

گدارAI یک پلتفرم چندمستاجری (Multi-tenant) است. در ساده‌ترین حالت، ساختار مفهومی آن این‌طور دیده می‌شود:

- Tenant
- Org Unit
- Team
- User
- Virtual User
- API Key

هر کدام از این لایه‌ها نقش متفاوتی در دسترسی، بودجه، مدل‌ها و audit دارند.

## Tenant چیست؟

tenant بالاترین مرز ایزوله‌سازی در GodarAI است. هر tenant معمولاً:

- کاربران خودش را دارد
- teamها و org unitهای خودش را دارد
- wallet، policy و model access خودش را دارد
- از tenantهای دیگر جداست

در معرفی docs هم این اصل صراحتاً آمده که GodarAI بر پایه `tenant isolation by subdomain` ساخته شده است.

به زبان ساده:

- اگر دو مجموعه باید از نظر داده، دسترسی و billing از هم جدا باشند، معمولاً باید در دو tenant جدا قرار بگیرند

## Org Unit چیست؟

واحد سازمانی (Org Unit) یک لایه میانی برای سازمان‌های بزرگ‌تر است. Org Unit زمانی مفید می‌شود که بخواهید داخل یک tenant، چند بخش سازمانی جدا داشته باشید؛ مثلاً:

- Engineering
- Marketing
- Operations

هر org unit می‌تواند:

- teamهای خودش را داشته باشد
- membershipهای خودش را داشته باشد
- مرز مدیریتی روشن‌تری برای `org_admin` ایجاد کند

## Team چیست؟

team در GodarAI فقط یک گروه کاربری نیست؛ یک workspace عملیاتی است. team می‌تواند:

- مستقیم زیر tenant باشد
- یا زیر یک org unit قرار بگیرد
- `workspace_type` داشته باشد
- model access و permissionهای خودش را داشته باشد
- مبنای ownership برای keyها، workloadها و بودجه باشد

اگر org unit را لایه سازمانی بدانیم، team معمولاً لایه اجرایی و روزمره کار است.

## User چیست؟

user همان هویت انسانی است. کاربر انسانی:

- وارد پنل می‌شود
- membership می‌گیرد
- PAT می‌سازد
- مصرف و عملیاتش audit می‌شود

یک user می‌تواند:

- فقط در سطح tenant باشد
- عضو چند team باشد
- عضو یک یا چند org unit باشد

## Virtual User چیست؟

Virtual User هویت غیرانسانی برای سرویس‌ها و workloadهاست. این مفهوم در GodarAI خیلی مهم است، چون سرویس production نباید به PAT یک انسان وابسته باشد.

Virtual User معمولاً برای این سناریوهاست:

- backend service
- worker
- agent
- CI/CD
- automation

Virtual User می‌تواند به team یا org unit وصل باشد و بعد برایش VAT صادر شود.

## API Keyها در این ساختار کجا قرار می‌گیرند؟

در معماری فعلی GodarAI دو نوع کلید اصلی داریم:

- `PAT` برای user انسانی
- `VAT` برای virtual user

به‌صورت مفهومی:

- PAT نماینده یک فرد است
- VAT نماینده یک سرویس یا workload است

همین تفاوت، پایه اصلی lifecycle و audit درست در محصول است.

## «Account» در GodarAI دقیقاً یعنی چه؟

اینجا مهم‌ترین جایی است که باید شفاف باشیم: در متن TrueFoundry، «account» یک مرز داخلی زیر tenant بود. اما در GodarAI این واژه می‌تواند چند معنا ایجاد کند و اگر دقیق تفکیک نشود، باعث سوءبرداشت می‌شود.

در GodarAI بهتر است «account» را در سه معنای متفاوت از هم جدا کنیم:

### 1. حساب مستاجر یا فضای اصلی tenant

این همان tenant شماست؛ مرز اصلی ایزوله‌سازی، کاربران، wallet، policy و access.

### 2. حساب ارائه‌دهنده (Provider Account)

Provider Account به اتصال شما به vendor مدل اشاره دارد؛ مثلاً:

- یک حساب OpenAI
- یک حساب Anthropic
- یک اتصال اختصاصی به provider دیگر

این مفهوم ربطی به user/team hierarchy ندارد، ولی روی model access اثر مستقیم دارد.

### 3. حساب مجازی یا هویت سرویس‌محور

در بعضی متون قدیمی یا وارداتی، ممکن است «virtual account» گفته شود؛ اما در مدل canonical فعلی GodarAI بهتر است از `Virtual User` و `VAT` استفاده کنیم، چون دقیق‌تر و منطبق‌تر با backend هستند.

## پس معادل عملی account boundary در GodarAI چیست؟

اگر از دید کاربر عملیاتی نگاه کنیم، مرزهایی که واقعاً جای «account boundary» را پر می‌کنند بیشتر این‌ها هستند:

- tenant برای ایزوله‌سازی کلان
- org unit برای مرز سازمانی
- team برای مرز اجرایی و ownership
- virtual user برای هویت سرویس‌محور

در بیشتر سناریوهای واقعی GodarAI، team و virtual user چیزی را حل می‌کنند که در بعضی پلتفرم‌های دیگر با یک لایه account داخلی حل می‌شود.

## چه منابعی tenant-level هستند و چه چیزهایی team-level؟

در عمل، بعضی منابع بیشتر tenant-level هستند و بعضی team-level:

- wallet معمولاً در سطح tenant معنا پیدا می‌کند
- policyها می‌توانند tenant-level باشند ولی روی team/user/model اعمال شوند
- provider accountها در سطح tenant مدیریت می‌شوند
- teamها مرز اجرایی برای membership، key ownership و workloadها هستند

این باعث می‌شود tenant نقش «لایه مرکزی» و team نقش «لایه بهره‌برداری روزمره» را داشته باشد.

## چرا همه چیز را فقط در سطح tenant مدیریت نکنیم؟

از نظر فنی ممکن است، اما خیلی زود به مشکل می‌خورید:

- ownership مبهم می‌شود
- budget attribution سخت می‌شود
- permissionها بیش‌ازحد باز می‌شوند
- سرویس‌های production و development در هم می‌روند

به همین دلیل، حتی اگر فقط یک tenant دارید، باز هم طراحی درست team و virtual user اهمیت زیادی دارد.

## یک مدل ذهنی ساده برای شروع

اگر تازه می‌خواهید ساختار GodarAI را طراحی کنید، این الگو معمولاً خوب جواب می‌دهد:

- یک tenant برای هر محیط یا مشتری اصلی
- در صورت نیاز، org unit برای بخش‌های بزرگ سازمان
- team برای هر مرز ownership واقعی
- user برای انسان‌ها
- virtual user برای سرویس‌ها
- PAT برای توسعه‌دهندگان
- VAT برای production و automation

## چند سناریوی رایج

### 1. شرکت کوچک با چند تیم

اگر شرکت کوچک است، احتمالاً به org unit نیاز ندارید. کافی است:

- یک tenant داشته باشید
- چند team مثل backend، frontend و ML بسازید
- سرویس‌ها را با virtual user مدیریت کنید

### 2. سازمان بزرگ با چند بخش

اگر سازمان چند بخش مستقل دارد:

- یک tenant
- چند org unit
- چند team زیر هر org unit

این ساختار هم access را شفاف‌تر می‌کند و هم delegation مدیریتی را ساده‌تر.

### 3. سرویس production مشترک

اگر یک workload مشترک بین اعضای تیم وجود دارد:

- به‌جای PAT افراد، یک virtual user بسازید
- VAT بدهید
- آن را به team مناسب وصل کنید

این کار lifecycle سرویس را از lifecycle انسان‌ها جدا می‌کند.

## چند سوءبرداشت رایج

### team همان tenant نیست

team یک مرز داخلی عملیاتی است؛ tenant مرز اصلی ایزوله‌سازی است.

### provider account همان user account نیست

Provider Account برای اتصال به vendor است، نه برای عضویت کاربر یا hierarchy داخلی.

### virtual user همان user انسانی نیست

virtual user برای workload و سرویس است، نه برای login انسانی.

### هر جا در متن دیدید «account»، باید context آن را مشخص کنید

در GodarAI، بدون مشخص‌کردن context، واژه account می‌تواند مبهم باشد.

## توصیه‌های عملی برای GodarAI

### از ابتدا بین tenant، team و provider account تفکیک بگذارید

این کار بعداً جلوی آشفتگی مفهومی و permissionهای اشتباه را می‌گیرد.

### برای سرویس‌ها از virtual user استفاده کنید

اگر سرویسی هنوز با PAT یک فرد کار می‌کند، ساختار identity شما هنوز کامل نشده است.

### team را بر اساس ownership واقعی بسازید

نه صرفاً بر اساس عنوان‌های ظاهری یا ساختار اداری مبهم.

### فقط وقتی org unit بسازید که واقعاً نیاز دارید

برای همه سازمان‌ها این لایه لازم نیست؛ گاهی team به‌تنهایی کافی است.

## جمع‌بندی

مدل GodarAI را می‌توان این‌طور خلاصه کرد: `tenant` مرز اصلی ایزوله‌سازی است، `org unit` مرز سازمانی اختیاری است، `team` مرز اجرایی و ownership است، `user` هویت انسانی است و `virtual user` هویت سرویس‌محور. چیزی که در بعضی پلتفرم‌ها با واژه کلی `account` توضیح داده می‌شود، در GodarAI بهتر است با این لایه‌های دقیق‌تر فهمیده شود تا هم access درست طراحی شود و هم keyها، budgetها و workloadها در جای درستی قرار بگیرند.
