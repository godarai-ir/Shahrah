# مدیریت کاربران در گدارAI

مدیریت کاربران در گدارAI فقط به معنی اضافه یا حذف کردن یک نفر از پلتفرم نیست. در عمل، شما باید مشخص کنید هر فرد یا هر هویت سیستمی در کدام tenant قرار دارد، عضو کدام team یا واحد سازمانی (Org Unit) است، چه نقشی دارد، و به چه منابعی باید دسترسی داشته باشد.

در GodarAI، این بخش پایه اصلی کنترل دسترسی، مدیریت کلیدها، بودجه، rate limit و audit است.

## مدیریت کاربر در GodarAI چه مسئله‌ای را حل می‌کند؟

چند نیاز رایج:

- اضافه کردن اعضای جدید به tenant
- تعیین اینکه چه کسی `tenant_admin` باشد و چه کسی فقط `member`
- عضویت دادن کاربر در چند team مختلف
- تفکیک دسترسی بین نقش‌های سازمانی و نقش‌های تیمی
- غیرفعال کردن کاربر بدون حذف فوری اطلاعات او
- جدا کردن هویت انسانی از هویت سرویس‌محور

## مدل ذهنی GodarAI برای هویت‌ها

در GodarAI بهتر است این سه دسته را از هم جدا ببینید:

- کاربر انسانی: فردی که وارد پنل می‌شود، PAT می‌سازد و با رابط کاربری کار می‌کند
- کاربر مجازی (Virtual User): هویت غیرانسانی برای سرویس‌ها، jobها و CI/CD
- عضویت‌ها: رابطه کاربر با teamها و org unitها

این تفکیک باعث می‌شود:

- دسترسی هر فرد روشن باشد
- سرویس‌ها به PAT افراد وابسته نشوند
- مصرف و audit قابل نسبت‌دادن بماند

## کاربران چگونه به پلتفرم اضافه می‌شوند؟

در الگوی محصولی، دو مسیر اصلی وجود دارد:

- اضافه‌شدن خودکار از طریق ورود سازمانی مثل SSO
- اضافه‌شدن دستی از سمت مدیر tenant

اگرچه مستند منبع روی SSO تاکید داشت، در ساختار فعلی GodarAI چیزی که برای کاربر docs مهم‌تر است این است که onboarding و مدیریت tenant-admin از مسیر APIها و flowهای مدیریت tenant انجام می‌شود و کاربر بعد از حضور در tenant می‌تواند در teamها و org unitها عضو شود.

## نقش‌های اصلی کاربران در GodarAI

بر اساس طراحی و کد فعلی، نقش‌های مهم این‌ها هستند:

| نقش | scope | توضیح |
| --- | --- | --- |
| `tenant_admin` | کل tenant | دسترسی کامل مدیریتی در سطح tenant |
| `org_admin` | واحد سازمانی | مدیریت teamهای همان واحد سازمانی |
| `team_admin` | تیم | مدیریت اعضا، permissionها و keyهای تیم |
| `member` | کاربر عادی | دسترسی محدود بر اساس membership و permission |
| `readonly_member` | کاربر فقط‌خواندنی | مناسب برای مشاهده بدون اعمال تغییر |

در بعضی اسناد طراحی، نام‌هایی مثل `tenant_user` یا `team_member` هم دیده می‌شود؛ اما در لایه RBAC فعلی backend، شکل canonical بیشتر حول `tenant_admin`، `org_admin`، `team_admin`، `member` و `readonly_member` می‌چرخد.

## تفاوت نقش سراسری با عضویت تیمی

این یکی از مهم‌ترین نکات برای کاربران GodarAI است:

- نقش سراسری تعیین می‌کند کاربر در کل tenant چه سطحی از اختیار دارد
- عضویت تیمی یا سازمانی تعیین می‌کند کاربر در کدام context عملیاتی کار می‌کند

مثلاً یک نفر می‌تواند:

- در سطح tenant فقط `member` باشد
- اما در یک team خاص `team_admin` باشد

یا:

- در یک org unit مدیر باشد
- ولی در سایر teamها فقط عضو عادی باشد

## team و org unit چه نقشی در مدیریت کاربر دارند؟

در GodarAI، teamها و org unitها فقط برای دسته‌بندی نیستند؛ آن‌ها روی access، budget، policy و attribution اثر می‌گذارند.

یک کاربر می‌تواند:

- مستقل از teamها داخل tenant وجود داشته باشد
- عضو چند team مختلف باشد
- عضو یک یا چند org unit باشد

این مدل برای سازمان‌هایی که چند تیم product، backend، data یا support دارند بسیار مهم است.

## مجوزهای اعضای تیم

همه اعضای یک team لزوماً اختیار یکسان ندارند. در طراحی فعلی، برای اعضای غیرادمین می‌شود مجوزهای مشخص‌تری تعریف کرد.

مثلاً:

```json
{
  "team_member_permissions": [
    "/key/generate",
    "/key/update",
    "/key/delete",
    "/model/new"
  ]
}
```

این یعنی حتی اگر یک نفر `team_admin` نباشد، می‌تواند بعضی عملیات‌های مشخص را در همان team انجام دهد.

## مدیریت کاربران از طریق APIهای GodarAI

در کنار رابط کاربری، backend فعلی routeهای مشخصی برای مدیریت teamها، org unitها و virtual userها دارد. نمونه‌های مهم:

- `GET /api/v1/org-units`
- `POST /api/v1/org-units`
- `POST /api/v1/org-units/:orgUnitID/members`
- `PATCH /api/v1/org-units/:orgUnitID/members/:userID`
- `DELETE /api/v1/org-units/:orgUnitID/members/:userID`
- `GET /api/v1/teams`
- `POST /api/v1/teams`
- `POST /api/v1/teams/:teamID/members`
- `PATCH /api/v1/teams/:teamID/members/:userID`
- `DELETE /api/v1/teams/:teamID/members/:userID`
- `PATCH /api/v1/users/roles`

برای کاربر docs، معنای عملی این routeها این است که مدیریت user در GodarAI بیشتر از جنس membership و role binding است، نه فقط یک لیست ساده از userها.

## تغییر نقش کاربر

تغییر نقش یکی از حساس‌ترین عملیات‌های مدیریتی است، چون مستقیماً روی سطح دسترسی اثر می‌گذارد.

در عمل:

- `tenant_admin` باید محدود و کم‌تعداد باشد
- نقش‌های org و team را تا جای ممکن به context همان بخش محدود کنید
- برای کارهای روزمره، به‌جای دادن admin کامل، از membership و permissionهای محدودتر استفاده کنید

## غیرفعال‌سازی کاربر

گاهی لازم نیست کاربر را فوراً حذف کنید. غیرفعال‌سازی (Deactivate) زمانی مفید است که:

- کاربر موقتاً نباید وارد شود
- وضعیت همکاری او نامشخص است
- می‌خواهید دسترسی را قطع کنید اما هنوز audit و سابقه او حفظ شود

در لایه auth فعلی، اگر کاربر active نباشد یا نقش او در وضعیت deactivated تلقی شود، احراز هویت مؤثر نخواهد بود.

## حذف کاربر

حذف کاربر باید با احتیاط انجام شود. از منظر عملیاتی، قبل از حذف کاربر بهتر است این موارد بررسی شوند:

- آیا هنوز عضو team یا org unit است؟
- آیا PAT فعال دارد؟
- آیا روی flowهای عملیاتی یا مالکیت تنظیمات اثر می‌گذارد؟

قاعده خوب این است که:

- اول membershipها و وابستگی‌های مستقیم را پاک کنید
- بعد در صورت نیاز user را حذف کنید

## تفاوت کاربر انسانی با Virtual User

این دو را نباید با هم قاطی کرد:

- کاربر انسانی برای ورود به پنل، کار با UI و ساخت PAT مناسب است
- Virtual User برای workloadهای غیرانسانی و ساخت VAT مناسب است

اگر یک backend service یا CI pipeline دارید، به‌جای ساخت user صوری برای آن، از Virtual User استفاده کنید. این کار هم audit را بهتر می‌کند و هم lifecycle سرویس را از lifecycle افراد جدا نگه می‌دارد.

## ارتباط مدیریت کاربر با API Key

مدیریت user در GodarAI مستقیماً روی کلیدها اثر می‌گذارد:

- PATها به کاربر انسانی وابسته‌اند
- VATها به virtual user وابسته‌اند
- team membership و role می‌توانند scope مصرف و دسترسی را محدود کنند

پس طراحی user management فقط یک موضوع IAM نیست؛ به‌طور مستقیم روی امنیت، هزینه و بهره‌برداری هم اثر دارد.

## چند سناریوی رایج

### 1. توسعه‌دهنده‌ای که در چند team عضو است

یک کاربر می‌تواند هم‌زمان:

- در team پلتفرم `team_admin` باشد
- در team داده `member` باشد
- در team دیگری فقط دسترسی مشاهده داشته باشد

این مدل برای سازمان‌های چندتیمی طبیعی و پشتیبانی‌شده است.

### 2. مدیر tenant با تیم‌های مستقل

در یک شرکت کوچک، ممکن است فقط یک یا دو `tenant_admin` داشته باشید و بقیه کاربران در teamها مدیریت شوند. این بهترین حالت برای کاهش ریسک دسترسی بیش از حد است.

### 3. سرویس production بدون وابستگی به فرد

برای سرویس production بهتر است:

- یک Virtual User بسازید
- برای آن VAT صادر کنید
- سرویس را به team یا org unit مناسب متصل کنید

به این ترتیب خروج یک فرد از شرکت باعث از کار افتادن سرویس نمی‌شود.

## توصیه‌های عملی برای GodarAI

### نقش `tenant_admin` را محدود نگه دارید

تعداد زیاد admin در سطح tenant معمولاً هم ریسک امنیتی می‌سازد و هم مرز مسئولیت‌ها را مبهم می‌کند.

### به‌جای admin کامل، از team scope استفاده کنید

اگر نیاز مدیریتی فقط مربوط به یک تیم است، `team_admin` یا permissionهای تیمی انتخاب بهتری از `tenant_admin` هستند.

### انسان و سرویس را با دو identity جدا مدیریت کنید

برای افراد از user + PAT و برای سرویس‌ها از Virtual User + VAT استفاده کنید.

### قبل از حذف، اول membershipها را تمیز کنید

این کار هم سازگاری داده‌ای را بهتر نگه می‌دارد و هم جلوی خطاهای مدیریتی را می‌گیرد.

### role و permission را حداقلی طراحی کنید

اصل کمترین سطح دسترسی (Least Privilege) در GodarAI کاملاً ارزشمند است: هر کاربر فقط همان سطحی را داشته باشد که واقعاً لازم دارد.

## جمع‌بندی

مدیریت کاربران در GodarAI ترکیبی از role، membership، team، org unit و virtual identity است. اگر این بخش را درست طراحی کنید، هم امنیت و audit بهتر می‌شود، هم مدیریت API keyها و policyها تمیزتر پیش می‌رود، و هم تیم‌های مختلف می‌توانند بدون تداخل روی یک gateway مشترک کار کنند.
