# محدودیت بودجه در گدارAI

محدودیت بودجه در گدارAI برای این است که مصرف مدل‌ها فقط از نظر سرعت کنترل نشود، بلکه از نظر هزینه هم سقف مشخص داشته باشد. این موضوع مخصوصاً وقتی مهم می‌شود که چند تیم، چند سرویس یا چند مشتری از یک gateway مشترک استفاده می‌کنند و می‌خواهید قبل از خالی شدن اعتبار یا جهش هزینه، مصرف را مهار کنید.

در GodarAI، قواعد محدودیت بودجه (Budget Limiting Rules) به شما کمک می‌کنند:

- برای کاربر، تیم، مدل یا حساب مجازی سقف هزینه تعریف کنید
- مصرف را به‌صورت روزانه، هفتگی یا ماهانه کنترل کنید
- بعضی ruleها را فقط برای مشاهده و هشدار نگه دارید و بعضی را به‌صورت مسدودکننده فعال کنید
- بین بودجه عملیاتی gateway و کیف پول ریالی (Rial Wallet) تفکیک روشنی داشته باشید

## این قابلیت چه مسئله‌ای را حل می‌کند؟

چند سناریوی رایج:

- یک تیم تحقیقاتی روی مدل‌های گران‌قیمت کار می‌کند و باید سقف ماهانه جدا داشته باشد
- می‌خواهید هر کاربر فقط تا مقدار مشخصی در روز هزینه ایجاد کند
- لازم است هزینه یک مدل خاص مثل `gpt-4o` یا یک مدل self-hosted را جداگانه کنترل کنید
- می‌خواهید برای هر پروژه یا هر محیط مثل `production` و `staging` بودجه مستقل داشته باشید

در همه این حالت‌ها، محدودیت بودجه یکی از مهم‌ترین ابزارهای کنترل مالی در GodarAI است.

## تفاوت محدودیت بودجه با کیف پول ریالی

در GodarAI این دو لایه را باید از هم جدا ببینید:

- کیف پول ریالی، backstop نهایی پرداخت است؛ اگر موجودی کافی نباشد، درخواست در نهایت متوقف می‌شود
- محدودیت بودجه، یک policy عملیاتی است که قبل از رسیدن مصرف به وضعیت نامطلوب، برای scopeهای مختلف سقف می‌گذارد

به بیان ساده:

- wallet می‌گوید «آیا اصلاً اعتبار قابل پرداخت داریم؟»
- budget rule می‌گوید «آیا این کاربر / تیم / مدل مجاز است تا این مقدار هزینه کند؟»

در معماری فعلی Shahrah، هزینه‌ها با فیلدهایی مثل `cost_usd` و `cost_irr` ثبت می‌شوند و کیف پول tenant همچنان آخرین لایه محافظت مالی باقی می‌ماند.

## تفاوت محدودیت بودجه با کنترل نرخ

کنترل نرخ درخواست (Rate Limiting) و محدودیت بودجه (Budget Limiting) مکمل هم هستند، نه جایگزین هم:

- rate limit برای مهار سرعت مصرف در بازه‌های کوتاه مثل دقیقه است
- budget limit برای مهار مجموع هزینه در بازه‌های بلندتر مثل روز، هفته یا ماه است

در عمل معمولاً هر دو را با هم استفاده می‌کنید:

- rate limit جلوی burst و spike را می‌گیرد
- budget limit جلوی فرسایش تدریجی اعتبار و رشد هزینه را می‌گیرد

## مدل ذهنی GodarAI برای budget rule

در GodarAI، هر قانون بودجه یک شناسه یکتا دارد و روی مجموعه‌ای از درخواست‌ها اعمال می‌شود. در پیاده‌سازی فعلی، فیلدهای کلیدی این ruleها شامل این موارد هستند:

- `rule_id`: شناسه یکتای قانون
- `limit_to`: سقف بودجه
- `unit`: دوره بودجه
- `priority`: اولویت rule
- `budget_applies_per`: نحوه تفکیک بودجه
- `enabled`: فعال یا غیرفعال بودن قانون

در اعتبارسنجی فعلی backend، مقدار `unit` فقط یکی از این سه حالت را می‌پذیرد:

- `cost_per_day`
- `cost_per_week`
- `cost_per_month`

همچنین `budget_applies_per` می‌تواند یکی از این حالت‌ها باشد:

- `user`
- `model`
- `virtualaccount`
- `metadata.<key>`

## ترتیب ruleها چرا مهم است؟

در طراحی budget ruleها، ترتیب و اولویت ruleها مهم است. اگر چند قانون روی یک درخواست match شوند، باید مشخص باشد کدام قانون تصمیم نهایی را برای اجازه یا رد درخواست می‌گیرد و کدام‌ها فقط برای ردیابی مصرف استفاده می‌شوند.

قاعده عملی خوب این است:

- ruleهای خاص‌تر را بالاتر بگذارید
- ruleهای عمومی یا پیش‌فرض را پایین‌تر بگذارید

مثلاً اگر همه کاربران باید روزانه 10 دلار سقف داشته باشند اما تیم ML باید 100 دلار سقف داشته باشد، rule تیم ML باید بالاتر از rule عمومی قرار بگیرد.

## scope قانون را چگونه تعریف کنیم؟

در GodarAI قانون بودجه را معمولاً بر اساس یکی یا چند بعد طراحی می‌کنید:

- کاربر
- تیم
- واحد سازمانی
- حساب مجازی (Virtual Account)
- مدل یا مدل مجازی
- metadata ارسالی از سمت کلاینت

اگر ترجمه فارسی یک مفهوم ممکن است کمتر مانوس باشد، بهتر است آن را با فرم فارسی و اصل انگلیسی در کنار هم ببینیم:

- حساب مجازی (Virtual Account)
- فراداده (Metadata)
- محدوده اعمال (Scope)

## `budget_applies_per` دقیقاً چه می‌کند؟

به‌طور پیش‌فرض، اگر یک rule روی چند درخواست match شود، همه آن درخواست‌ها از یک بودجه مشترک استفاده می‌کنند. اما با `budget_applies_per` می‌توانید بودجه را به چند سبد مستقل بشکنید.

مثال‌ها:

- `user`: هر کاربر بودجه مستقل خودش را دارد
- `model`: هر مدل بودجه مستقل خودش را دارد
- `virtualaccount`: هر حساب مجازی بودجه مستقل خودش را دارد
- `metadata.project_id`: هر پروژه بودجه مستقل خودش را دارد

این قابلیت برای سناریوهای چندتیمی و چندمحصولی خیلی مهم است، چون اجازه می‌دهد بدون ساختن ruleهای بسیار زیاد، یک سیاست کلی اما تفکیک‌شده داشته باشید.

## واحدهای بودجه در GodarAI

در پیاده‌سازی فعلی، سه دوره اصلی برای بودجه پشتیبانی می‌شود:

- هزینه روزانه (`cost_per_day`)
- هزینه هفتگی (`cost_per_week`)
- هزینه ماهانه (`cost_per_month`)

اگر هدفتان کنترل burst است، به سراغ rate limit بروید. اگر هدفتان کنترل هزینه تجمعی است، یکی از این سه واحد برای budget rule مناسب‌تر است.

## اگر بودجه رد شود چه اتفاقی می‌افتد؟

در طراحی عملیاتی Shahrah، اگر یک بودجه مؤثر برای key، team یا org وجود داشته باشد و هزینه تخمینی درخواست از بودجه باقی‌مانده بیشتر شود، درخواست باید قبل از فراخوانی provider متوقف شود.

در این سناریو معمولاً:

- درخواست به provider ارسال نمی‌شود
- پاسخ خطای سازگار با GodarAI برگردانده می‌شود
- tenant wallet همچنان آخرین لایه بررسی مالی باقی می‌ماند

این رفتار باعث می‌شود budget limiting فقط یک گزارش تحلیلی نباشد، بلکه یک کنترل اجرایی واقعی روی مسیر درخواست باشد.

## چند الگوی رایج برای طراحی بودجه

### 1. بودجه روزانه برای هر کاربر

اگر می‌خواهید هر کاربر سقف مستقل داشته باشد:

- یک rule عمومی تعریف کنید
- `budget_applies_per` را روی `user` بگذارید
- از `cost_per_day` استفاده کنید

این الگو برای تیم‌های محصول، پشتیبانی و کاربران داخلی بسیار رایج است.

### 2. بودجه ماهانه برای یک مدل گران

اگر یک مدل خاص هزینه بالایی دارد:

- rule را روی همان model یا virtual model اعمال کنید
- از `cost_per_month` استفاده کنید
- در صورت نیاز rule را به حالت مسدودکننده بگذارید

این الگو برای مدل‌های premium یا GPU-intensive مناسب است.

### 3. بودجه پروژه‌ای بر اساس metadata

اگر اپلیکیشن شما `project_id` یا `environment` را در metadata می‌فرستد، می‌توانید بودجه هر پروژه را جداگانه حساب کنید.

این مدل مخصوص وقتی خوب جواب می‌دهد که:

- چند سرویس از یک کلید مشترک استفاده می‌کنند
- اما شما به تفکیک داخلی‌تری برای گزارش و کنترل نیاز دارید

### 4. بودجه تیمی با استثنا برای تیم‌های ویژه

مثلاً:

- همه تیم‌ها ماهانه 200 دلار
- تیم پژوهش ماهانه 1500 دلار

در این حالت:

- rule تیم پژوهش را بالاتر بگذارید
- rule عمومی را پایین‌تر بگذارید

## نمونه rule مفهومی

نمونه زیر صرفاً یک representation مفهومی از ساختار rule در GodarAI است:

```json
{
  "rule_id": "team-ml-monthly-budget",
  "limit_to": 1500,
  "unit": "cost_per_month",
  "priority": 10,
  "budget_applies_per": "user",
  "enabled": true
}
```

نمونه دوم برای بودجه پروژه‌ای:

```json
{
  "rule_id": "project-daily-budget",
  "limit_to": 100,
  "unit": "cost_per_day",
  "priority": 20,
  "budget_applies_per": "metadata.project_id",
  "enabled": true
}
```

## توصیه‌های عملی برای کاربران GodarAI

### rule عمومی را آخر بگذارید

اگر یک rule بدون شرط یا با شرط بسیار باز دارید، آن را پایین‌تر از ruleهای خاص قرار دهید تا رفتارهای استثنایی درست اعمال شوند.

### برای production و staging بودجه جدا تعریف کنید

اگر metadata محیط را می‌فرستید، بودجه این دو محیط را جدا کنید تا تست‌ها یا jobهای staging روی هزینه واقعی production اثر نگذارند.

### بودجه روزانه را با کیف پول اشتباه نگیرید

ممکن است یک کاربر هنوز از بودجه روزانه خودش عبور نکرده باشد، اما tenant wallet دیگر اعتبار کافی نداشته باشد. این دو لایه مستقل هستند و هر دو باید درست طراحی شوند.

### روی مدل‌های گران حتماً rule اختصاصی بگذارید

اگر فقط rule عمومی داشته باشید، یک مدل گران می‌تواند همان بودجه عمومی را خیلی سریع مصرف کند. برای مدل‌های حساس بهتر است سقف مستقل بگذارید.

### برای metadata از کلیدهای پایدار استفاده کنید

اگر از `metadata.<key>` استفاده می‌کنید، بهتر است کلیدهایی مثل `project_id`، `environment` یا `cost_center` پایدار و استاندارد باشند تا گزارش‌گیری و enforcement قابل اتکا بماند.

## جمع‌بندی

محدودیت بودجه در GodarAI لایه‌ای برای کنترل مالی عملیاتی است که کنار rate limit و کیف پول ریالی، به شما کمک می‌کند مصرف مدل‌ها را در سطح کاربر، تیم، مدل یا پروژه مهار کنید. اگر ruleها را با scope درست، اولویت شفاف و تفکیک مناسب بین wallet و budget طراحی کنید، می‌توانید هم هزینه را بهتر کنترل کنید و هم از بروز مصرف ناخواسته قبل از رسیدن به بحران جلوگیری کنید.
