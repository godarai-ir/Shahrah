# کش پاسخ در گدارAI

کش پاسخ در گدارAI برای کم کردن هزینه، کاهش زمان پاسخگویی و حذف فراخوانی تکراری به ارائه‌دهنده LLM طراحی شده است. وقتی یک درخواست از کش پاسخ داده شود، گیت‌وی دیگر لازم نیست همان درخواست را دوباره به مدل بالادست بفرستد؛ در نتیجه هم پاسخ سریع‌تر برمی‌گردد و هم هزینه‌ای به درخواست کننده تحمیل نمی‌شود.

در وضعیت فعلی، کش پاسخ برای درخواست‌های `non-streaming` و با پشتیبانی از اندپوینت `chat/completions` در نظر گرفته شده و به‌صورت پیش‌فرض غیرفعال است. فعال‌سازی سراسری از سمت درخواست کننده انجام می‌شود و هر کلاینت بعد از آن می‌تواند به‌صورت per-request از کش استفاده کند.

:::note
در گدارAI، کش پاسخ با prompt caching داخل خود ارائه‌دهنده LLM یکی نیست. prompt caching فقط بخشی از پردازش پرامپت را در ارائه‌دهنده سبک‌تر می‌کند، اما کش پاسخ در سطح گیت‌وی گدارAI می‌تواند کل فراخوانی به ارائه‌دهنده LLM را حذف کند.
:::

## دو نوع کش در گدارAI

گدارAI دو حالت اصلی برای کش پاسخ دارد:

### 1. `simple`

در این حالت، فقط درخواست‌هایی از کش پاسخ داده می‌شوند که از نظر محتوا (payload) و پارامترها دقیقاً یکسان باشند. این حالت برای سناریوهایی مناسب است که:

- پرسش‌ها تکراری و ثابت هستند
- پاسخ باید قطعی و قابل پیش‌بینی (deterministic) بماند
- روی دقت (precision) بالا حساس هستید
- می‌خواهید رفتار کش کاملاً قابل پیش‌بینی باشد

### 2. `smart`

در این حالت، گدارAI اول exact match را بررسی می‌کند و اگر hit نشد، فقط متن آخرین پیام کاربر را به‌صورت معنایی (semantic) مقایسه می‌کند. باقی درخواست همچنان باید از نظر مدل، پیام‌های قبلی، temperature و سایر پارامترها یکسان بماند.

این mode برای سناریوهایی بهتر است که کاربر قصد (intent) ثابت خود را با عبارت‌های متفاوت می‌پرسد، مثل:

- پرسش‌ و پاسخ‌های پر تکرار و مرکز راهنمایی مشتریان 
- چت‌بات‌های پشتیبانی
- سناریوهای سلف سرویس برای کاربران نهایی

در پیاده‌سازی فعلی، smart cache از embedding برای متن آخرین پیام کاربر استفاده می‌کند و آستانه شباهت (`similarity_threshold`) باید بین `0.8` تا `1.0` باشد. مقدار پیش‌فرض `0.9` است.

## چه چیزهایی از smart cache عبور می‌کنند؟

در گدارAI، smart cache همیشه برای همه درخواست‌ها اعمال نمی‌شود. این درخواست‌ها رد (bypass) می‌شوند:

- درخواست‌های `stream: true`
- درخواست‌هایی که `tools` دارند
- درخواست‌هایی که `tool_choice` دارند
- پیام‌هایی که آخرین message آن‌ها از نوع `user` نیست
- پیام‌هایی که آخرین محتوای کاربر شامل image یا محتوای غیرمتنی باشد

این محدودیت‌ها باعث می‌شوند hit اشتباه کمتر شود و کش فقط روی درخواست‌هایی اعمال شود که semantics آن‌ها قابل اتکا باشد.

## هدر تنظیم کش

برای فعال کردن کش روی هر درخواست، از هدر `x-godarai-cache-config` استفاده کنید.

### نمونه `simple`

```bash
curl https://YOUR-TENANT-NAME.godarai.ir/v1/chat/completions \
  -H "Authorization: Bearer $GODARAI_KEY" \
  -H "Content-Type: application/json" \
  -H 'x-godarai-cache-config: {"type":"simple","ttl":600,"namespace":"production"}' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [
      {
        "role": "user",
        "content": "سلام، وضعیت سفارش من چیست؟"
      }
    ]
  }'
```

### نمونه `smart`

```bash
curl https://YOUR-TENANT-NAME.godarai.ir/v1/chat/completions \
  -H "Authorization: Bearer $GODARAI_KEY" \
  -H "Content-Type: application/json" \
  -H 'x-godarai-cache-config: {"type":"smart","ttl":600,"similarity_threshold":0.9,"namespace":"support"}' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [
      {
        "role": "user",
        "content": "چطور رمز عبورم را بازیابی کنم؟"
      }
    ]
  }'
```

:::tip
اگر از tooling قدیمی استفاده می‌کنید، ممکن است هنوز هدر legacy یعنی `x-shahrah-cache-config` را ببینید. برای مستندات و کلاینت‌های جدید، مبنا `x-godarai-cache-config` است.
:::

## پارامترهای پشتیبانی‌شده

| فیلد | الزامی | توضیح |
| --- | --- | --- |
| `type` | بله | یکی از `simple` یا `smart` |
| `ttl` | خیر | مدت نگهداری پاسخ در کش بر حسب ثانیه |
| `namespace` | خیر | جدا کردن کش برای tenant / environment / context خاص |
| `similarity_threshold` | فقط برای `smart` | آستانه شباهت semantic بین `0.8` تا `1.0` |

### راهنمای انتخاب `similarity_threshold`

| بازه | رفتار | مناسب برای |
| --- | --- | --- |
| `0.95 - 1.0` | بسیار سخت‌گیرانه | سناریوهای حساس به hit اشتباه |
| `0.85 - 0.95` | متعادل | بیشتر چت‌بات‌ها و FAQها |
| `0.80 - 0.85` | بازتر | سناریوهای کم‌ریسک یا exploratory |

برای شروع، `0.9` انتخاب خوبی است.

## جداسازی کش در گدارAI

گدارAI کش را فقط با یک hash ساده مشترک نگه نمی‌دارد. isolation به‌شکل چندلایه انجام می‌شود تا پاسخ یک فضای کاری (tenant) یا virtual key ناخواسته به فضای کاری دیگر نرسد.

در پیاده‌سازی فعلی، کش بر اساس این محدوده‌ها (scope) ایزوله می‌شود:

- `tenant`
- `virtual key` یا account صادرکننده
- `namespace`
- مدل مجازی
- نسخه مدل مجازی
- هویت embedding در smart cache

### `namespace` را چه زمانی استفاده کنیم؟

اگر یک virtual key برای چند context متفاوت استفاده می‌شود، `namespace` کمک می‌کند کش هر context جدا بماند.

نمونه‌های رایج:

- `production`
- `staging`
- `tenant-123`
- `helpdesk`
- `mobile-app`

اگر `namespace` مشخص نکنید، مقدار پیش‌فرض `default` استفاده می‌شود.

## هدرهای پاسخ

گدارAI روی response هدرهایی برمی‌گرداند که نشان می‌دهند کش چه اتفاقی برای درخواست افتاده است:

| هدر | توضیح |
| --- | --- |
| `x-godarai-cache-status` | وضعیت کش: `hit`, `miss`, `bypass`, `error` |
| `x-godarai-cached-trace-id` | شناسه trace مربوط به پاسخ اصلی در صورت hit |
| `x-godarai-cache-similarity-score` | امتیاز شباهت در smart cache |

این هدرها برای debugging و تحلیل hit rate در محیط عملیاتی بسیار مهم هستند.

## cache hit چه اثری روی هزینه‌ها دارد؟

اگر درخواست از کش پاسخ داده شود:

- درخواست به سوی ارائه‌دهنده خدمات LLM ارسال نمی‌شود
- از اعتبار (ریالی/ارزی) کاربر چیزی کسر نمی‌شود
- تاخیر پاسخگویی کمتر می‌شود
- trace و log همچنان می‌توانند وضعیت cache hit را نشان دهند

این رفتار برای GodarAI مهم است، چون کاهش هزینه فقط به دلار ختم نمی‌شود و مستقیماً روی مصرف کیف پول ریالی شما هم اثر می‌گذارد.

## cache miss یا failure چه می‌شود؟

اگر کش hit نشود یا embedding / cache backend خطا بدهد، گدارAI بر اساس استراتژی fail-open عمل می‌کند و درخواست را به inference عادی می‌فرستد. یعنی کش نباید دسترس‌پذیری اصلی gateway را مختل کند.

این تصمیم با نیازهای عملیاتی گدارAI هم‌راستا است:

- پاسخ‌گویی گیت‌وی باید حفظ شود
- وقوع خطا در سرویس Redis یا embedding service نباید ترافیک اصلی را متوقف کند
- کش باید بهینه‌ساز باشد، نه یک وابستگی بحرانی در تعامل با ارائه‌دهندگان

## چه زمانی از `simple` و چه زمانی از `smart` استفاده کنیم؟

### `simple` را انتخاب کنید اگر:

- پرامپت‌ها تقریباً تکراری‌اند
- روی صحت و دقت خیلی حساس هستید
- می‌خواهید رفتار کاملاً پیش‌بینی پذیر (deterministic) باشد

### `smart` را انتخاب کنید اگر:

- کاربران یک سؤال را با بیان‌های مختلف می‌پرسند
- FAQ یا گردش کار برای پشتیبانی مشتریان دارید
- hit بیشتر از strict exact-match برایتان ارزش دارد

## پیشنهاد عملی برای تیم‌های GodarAI

اگر تازه می‌خواهید caching پاسخ‌های LLM را وارد اپلیکیشن‌های خود کنید، این ترتیب معمولاً خوب جواب می‌دهد:

1. ابتدا با `simple` شروع کنید و نرخ استفاده از پاسخ‌های کش شده را ببینید.
2. فقط روی endpointها و مورد کاربردهای پرتکرار، `smart` را فعال کنید.
3. برای محیط‌های مختلف از `namespace` جداگانه استفاده کنید.
4. `cache_status` و `cached_trace_id` را در logs و dashboards خود مانیتور کنید.
5. آستانه شباهت را با داده واقعی و نه حدس، تنظیم کنید.

## جمع‌بندی

کش پاسخ در گدارAI یک لایه صرفاً performance-oriented نیست؛ این قابلیت هم‌زمان روی کاهش تاخیر، هزینه دریافت سرویس از  ارائه‌دهنده LLM و پایداری تجربه محصول اثر می‌گذارد. اگر از آن با `namespace` درست، حالت مناسب و مانیتورینگ کافی استفاده شود، می‌تواند یکی از موثرترین بهینه‌سازی‌های عملیاتی در سطح gateway باشد.
