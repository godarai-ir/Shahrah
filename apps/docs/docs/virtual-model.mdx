# راهنمای مدل مجازی

مدل مجازی در GodarAI یک نام مستعار پایدار برای مسیریابی درخواست‌ها به یک یا چند مدل واقعی است. اپلیکیشن شما به‌جای وابسته شدن به نام مدل یک ارائه‌دهنده مشخص، فقط همان alias را صدا می‌زند و تنظیمات مسیریابی، تلاش مجدد و fallback از داخل گیت‌وی مدیریت می‌شود.

## مدل مجازی چه مسئله‌ای را حل می‌کند؟

مدل مجازی برای این سناریوها مفید است:

- وقتی می‌خواهید یک نام ثابت برای مصرف در کل سرویس‌ها داشته باشید و بدون تغییر کد کلاینت، مقصدهای پشت آن را عوض کنید.
- وقتی لازم است بین چند مدل یا چند اکانت ارائه‌دهنده، توزیع بار انجام دهید.
- وقتی می‌خواهید در صورت بروز خطا، درخواست به مقصد بعدی منتقل شود.
- وقتی لازم است سیاست retry و timeout را برای هر مقصد به‌صورت جداگانه کنترل کنید.

## آنچه اکنون در GodarAI پشتیبانی می‌شود

در نسخه فعلی، صفحه مدل‌های مجازی این قابلیت‌ها را در اختیار شما می‌گذارد:

- تعریف `alias` پایدار برای مدل مجازی
- انتخاب استراتژی مسیریابی `اولویتی` یا `وزنی`
- تعریف یک یا چند مقصد از بین مدل‌های قابل استفاده در حساب‌های ارائه‌دهنده متصل
- تنظیم `retry attempts`، `retry delay`، `timeout`
- تعیین `retry status codes` و `fallback status codes` برای هر مقصد
- فعال یا غیرفعال کردن مدل مجازی
- کنترل دسترسی برای `مدیران` و `کاربران`
- محاسبه خودکار `حالت‌های قابل ارائه` بر اساس اشتراک قابلیت‌های همه مقصدها
- پیش‌نمایش زنجیره مسیریابی مؤثر قبل از ذخیره

## مفاهیم اصلی

### Alias

`Alias` همان نامی است که سرویس‌های شما باید از آن استفاده کنند. این نام:

- باید یکتا باشد
- فقط می‌تواند شامل حروف، عدد، خط تیره و آندرلاین باشد
- نقطه اتصال ثابت بین اپلیکیشن شما و تنظیمات پشت‌صحنه مسیریابی است

### مقصد

هر مدل مجازی حداقل باید یک مقصد داشته باشد. هر مقصد در عمل به یک مدل واقعی از یک ارائه‌دهنده متصل اشاره می‌کند. مقصدها از مدل‌های فعال در حساب‌های ارائه‌دهنده انتخاب می‌شوند.

### استراتژی مسیریابی

#### مسیریابی اولویتی

در حالت `اولویتی`، درخواست ابتدا به مقصد اول فرستاده می‌شود. اگر به دلیل کدهای مشخص‌شده یا خطاهای مرتبط نیاز به fallback باشد، گیت‌وی به ترتیب به مقصدهای بعدی می‌رود.

این حالت برای سناریوهای `primary / backup` مناسب‌تر است.

#### مسیریابی وزنی

در حالت `وزنی`، به هر مقصد یک وزن اختصاص داده می‌شود و مجموع وزن‌ها باید دقیقاً `100` باشد. گیت‌وی ترافیک را مطابق این وزن‌ها توزیع می‌کند.

این حالت برای این موارد مناسب است:

- تقسیم ظرفیت بین چند ارائه‌دهنده
- rollout تدریجی
- کنترل سهم مصرف هر مقصد

## Retry و Fallback چگونه کار می‌کنند؟

برای هر مقصد می‌توانید سیاست رفتار در خطا را جداگانه تعریف کنید:

- `Retry attempts`: تعداد دفعات تلاش مجدد روی همان مقصد
- `Retry delay`: فاصله بین تلاش‌های مجدد بر حسب میلی‌ثانیه
- `Timeout`: حداکثر زمان انتظار برای همان مقصد
- `Retry status codes`: کدهایی که باعث می‌شوند درخواست روی همان مقصد دوباره امتحان شود
- `Fallback status codes`: کدهایی که باعث می‌شوند گیت‌وی به مقصد بعدی برود

### مقادیر پیش‌فرض فعلی

- تعداد تلاش مجدد: `2`
- وقفه بین تلاش‌ها: `100ms`
- timeout: `60s`
- کدهای پیش‌فرض retry: `408, 425, 429, 500, 502, 503, 504`
- کدهای پیش‌فرض fallback: `429, 500, 502, 503, 504`

## کنترل دسترسی

در بخش `کنترل دسترسی` می‌توانید تعیین کنید چه کسانی این مدل مجازی را:

- مدیریت کنند
- مصرف کنند

برای کاربران، امکان تعریف دسترسی عمومی نیز وجود دارد تا همه کاربران مجاز بتوانند از آن مدل استفاده کنند.

## حالت‌های قابل ارائه

GodarAI به‌صورت خودکار بررسی می‌کند که همه مقصدهای انتخاب‌شده چه قابلیت‌های مشترکی دارند. فقط همان حالت‌های مشترک می‌توانند روی مدل مجازی نهایی ارائه شوند.

به زبان ساده:

- اگر همه مقصدها از یک mode خاص پشتیبانی کنند، آن mode قابل ارائه است.
- اگر یک mode فقط در بخشی از مقصدها وجود داشته باشد، در مدل مجازی نهایی قابل اتکا نیست.
- اگر بین مقصدها هیچ اشتراک معناداری وجود نداشته باشد، آن ترکیب برای استفاده عملی مناسب نیست.

## پیش‌نمایش مسیریابی مؤثر

پیش از ذخیره، صفحه یک پیش‌نمایش از ترتیب مؤثر ارسال درخواست نشان می‌دهد:

- در حالت اولویتی، توالی fallback را می‌بینید
- در حالت وزنی، علاوه بر توالی، وزن هر مقصد هم نمایش داده می‌شود

این بخش کمک می‌کند قبل از ذخیره مطمئن شوید منطق واقعی مسیریابی با انتظار شما هماهنگ است.

## چه چیزهایی فعلاً در این صفحه وجود ندارند؟

برای جلوگیری از ابهام، این موارد در راهنمای فعلی توضیح داده نشده‌اند چون در UI فعلی GodarAI برای مدل مجازی در دسترس نیستند:

- مسیریابی latency-based
- sticky routing
- metadata-based target filtering
- header override
- prompt override
- SLA cutoff

اگر این قابلیت‌ها بعداً به GodarAI اضافه شوند، باید مستندات این صفحه نیز هم‌زمان به‌روزرسانی شود.

## پیشنهادهای عملی برای استفاده

برای شروع امن‌تر، این الگوها معمولاً خوب جواب می‌دهند:

1. اگر می‌خواهید پایداری بالا داشته باشید، از استراتژی `اولویتی` با یک مقصد اصلی و یک مقصد پشتیبان استفاده کنید.
2. اگر می‌خواهید مصرف را بین دو ارائه‌دهنده تقسیم کنید، از استراتژی `وزنی` استفاده کنید و مجموع وزن‌ها را دقیقاً روی `100` نگه دارید.
3. اگر مقصدها از modeهای متفاوتی پشتیبانی می‌کنند، قبل از ذخیره حتماً بخش `حالت‌های قابل ارائه` را بررسی کنید.
4. اگر یک مدل فقط برای گروه خاصی از کاربران است، از `کنترل دسترسی` برای محدودسازی مصرف استفاده کنید.
