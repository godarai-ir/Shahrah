# خروجی ساختاریافته - Structured Outputs

اگر می‌خواهید پاسخ model فقط «متن خوب» نباشد، بلکه خروجی قابل‌اعتماد و machine-readable هم تولید کند، باید از structured outputs استفاده کنید. در `Chat Completions` این کار معمولاً با `response_format` انجام می‌شود.

این قابلیت برای سناریوهایی مثل این خیلی مهم است:

- استخراج داده
- ساخت JSON برای workflow
- تولید state برای UI
- اتوماسیون backend
- validation downstream

## structured output چه مسئله‌ای را حل می‌کند؟

بدون structured output، حتی اگر به model بگویید «JSON برگردان»، هنوز ممکن است:

- متن اضافه تولید کند
- structure را نادرست بسازد
- fieldهای دلخواه خودش را اضافه کند
- typeها را اشتباه برگرداند

structured output کمک می‌کند خروجی به contract نزدیک‌تر، پایدارتر و قابل parseتر شود.

## دو حالت اصلی در GodarAI

در قرارداد فعلی، دو فرم مهم برای `response_format` وجود دارد:

- `json_object`
- `json_schema`

این naming با مسیرهای واقعی محصول هم‌راستاست؛ در منطق validation فعلی نیز همین دو فرمت canonical هستند.

## `json_object`

این حالت ساده‌تر است. هدف آن این است که model یک JSON معتبر برگرداند، بدون این‌که شما schema دقیق فیلدها را enforce کرده باشید.

نمونه:

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

response = client.chat.completions.create(
    model="openai:default:gpt-4o",
    messages=[
        {
            "role": "system",
            "content": "You are a helpful assistant designed to return JSON."
        },
        {
            "role": "user",
            "content": "اطلاعات برنده جام جهانی 2022 را استخراج کن."
        }
    ],
    response_format={"type": "json_object"}
)

print(response.choices[0].message.content)
```

این حالت خوب است وقتی:

- فقط JSON معتبر می‌خواهید
- schema خیلی سخت‌گیرانه لازم ندارید
- parsing ساده برایتان کافی است

## `json_schema`

اگر structure دقیق می‌خواهید، باید از `json_schema` استفاده کنید. در این حالت، شما schema را تعریف می‌کنید و model باید پاسخ را مطابق آن بسازد.

نمونه:

```python
from openai import OpenAI
import json

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

user_info_schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string"},
        "age": {"type": "integer", "minimum": 0},
        "occupation": {"type": "string"},
        "location": {"type": "string"},
        "skills": {
            "type": "array",
            "items": {"type": "string"}
        }
    },
    "required": ["name", "age", "occupation", "location", "skills"],
    "additionalProperties": False
}

response = client.chat.completions.create(
    model="openai:default:gpt-4o",
    messages=[
        {
            "role": "system",
            "content": "اطلاعات کاربر را طبق schema برگردان."
        },
        {
            "role": "user",
            "content": "من سارا هستم، 28 سالمه، در تهران زندگی می‌کنم و در حوزه تحلیل داده کار می‌کنم. مهارت‌هام Python و SQL و machine learning هستند."
        }
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "user_info",
            "schema": user_info_schema,
            "strict": True
        }
    }
)

result = json.loads(response.choices[0].message.content)
print(result)
```

## چه زمانی `json_object` و چه زمانی `json_schema`؟

قاعده عملی:

- اگر فقط JSON معتبر می‌خواهید: `json_object`
- اگر structure دقیق و enforce‌شده می‌خواهید: `json_schema`

مثلاً:

- summary ساده برای dashboard: `json_object`
- extraction قابل‌اتکا برای workflow production: `json_schema`

## `strict: true` یعنی چه؟

وقتی در `json_schema` از `strict: true` استفاده می‌کنید، model باید خیلی نزدیک‌تر به schema بماند. این برای use caseهای production بسیار ارزشمند است، اما schema شما هم باید تمیز طراحی شده باشد.

در متن منبع یک نکته مهم آمده بود که برای GodarAI هم باید جدی بگیرید:

- اگر strict روشن است، schema ناقص یا نیمه‌اختیاری می‌تواند باعث خطا یا رفتار نامطلوب شود

به زبان عملی:

- propertyهایی که واقعاً لازم‌اند را در `required` بگذارید
- اگر چیزی optional است، با دقت طراحی‌اش کنید
- `additionalProperties: false` را وقتی می‌خواهید schema بسته باشد، فعال کنید

## مزیت اصلی `json_schema`

این حالت برای سناریوهای production-grade بهتر است چون:

- downstream parsing ساده‌تر می‌شود
- احتمال hallucinated field کمتر می‌شود
- validation سمت اپلیکیشن معنی‌دارتر می‌شود
- contract بین model و backend روشن‌تر می‌ماند

## Pydantic و typed schema

اگر در Python کار می‌کنید، یک الگوی بسیار خوب این است که schema را از روی مدل Pydantic بسازید.

نمونه:

```python
from openai import OpenAI
from pydantic import BaseModel, Field
from typing import List

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

class UserInfo(BaseModel):
    name: str = Field(description="Full name")
    age: int = Field(ge=0, description="Age in years")
    occupation: str = Field(description="Occupation")
    location: str = Field(description="City or location")
    skills: List[str] = Field(description="Professional skills")

response = client.chat.completions.create(
    model="openai:default:gpt-4o",
    messages=[
        {"role": "system", "content": "اطلاعات کاربر را ساختاریافته برگردان."},
        {"role": "user", "content": "من علی هستم، 31 ساله، در شیراز زندگی می‌کنم و برنامه‌نویس backend هستم. Go و PostgreSQL و Docker بلد هستم."}
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "user_info",
            "schema": UserInfo.model_json_schema(),
            "strict": True
        }
    }
)
```

این روش چند مزیت دارد:

- schema از source of truth کد شما می‌آید
- validation سمت اپلیکیشن آسان‌تر می‌شود
- drift بین docs، schema و parser کمتر می‌شود

## نکته مهم درباره fieldهای optional

برای schemaهای strict، fieldهای optional می‌توانند دردسرساز شوند اگر طراحی‌شان با contract نهایی شما هم‌راستا نباشد. در practice:

- اگر field واقعاً باید همیشه وجود داشته باشد، optional نکنید
- اگر field ممکن است وجود نداشته باشد، parsing و contract downstream را از قبل طراحی کنید

## آیا parsing نهایی هنوز لازم است؟

بله. حتی با structured output، باز هم parsing و validation سمت اپلیکیشن شما لازم است. structured output ریسک را کم می‌کند، اما جای validation نهایی business logic را نمی‌گیرد.

قاعده خوب:

- model را کمک‌خلبان schema بدانید، نه منبع نهایی اعتماد

## structured outputs و prompts

در GodarAI، structured output فقط به `response_format` محدود نیست؛ در لایه prompt/manifest هم ردپای همین قرارداد وجود دارد. در validation فعلی promptها، فرمت‌های معتبر برای `structured_output.format` همین‌ها هستند:

- `json_schema`
- `json_object`

این یعنی اگر بعداً prompt versioning یا manifest-based flows را هم استفاده کنید، همان mental model این صفحه برایتان معتبر می‌ماند.

## structured outputs و tools

گاهی structured output را با tool calling ترکیب می‌کنید. اینجا باید حواستان باشد:

- اگر قرار است model اول tool call بزند، خروجی نهایی ممکن است در turn بعدی ساخته شود
- schema نهایی را برای پاسخ final طراحی کنید، نه فقط intermediate message
- وقتی tool result را برمی‌گردانید، context را کامل نگه دارید

این ترکیب برای agentهای production خیلی قدرتمند است، ولی نیاز به طراحی دقیق‌تر دارد.

## structured outputs و caching

خود structured output لزوماً به معنای bypass cache نیست، اما باید توجه کنید که هر پارامتر اضافه در request می‌تواند روی cache key و behavior اثر بگذارد. اگر در کنار structured output از tools یا multimodal هم استفاده کنید، caching story می‌تواند متفاوت شود.

پس بهتر است:

- سناریوی text-only structured را جدا تست کنید
- سناریوی tool-enabled structured را جدا ارزیابی کنید

## چند الگوی خوب

### extraction

مثلاً استخراج اطلاعات کاربر، قرارداد، محصول یا فرم:

- بهترین گزینه: `json_schema`

### lightweight automation

مثلاً ساخت config ساده یا payload تقریبی:

- می‌تواند با `json_object` هم کافی باشد

### typed backend workflows

وقتی backend شما strongly-typed است:

- schema را از مدل‌های typed مثل Pydantic تولید کنید

## چند اشتباه رایج

### گفتن «JSON بده» بدون `response_format`

این کار ممکن است ظاهراً جواب بدهد، اما برای production قابل اتکا نیست.

### schema بیش‌ازحد باز

اگر schema خیلی آزاد باشد، structured output عملاً ارزش زیادی اضافه نمی‌کند.

### schema بیش‌ازحد سخت بدون طراحی خوب

strict بودن خوب است، ولی فقط وقتی schema واقعاً با use case شما جور باشد.

### اعتماد کامل بدون validation

structured output کمک می‌کند، اما validation اپلیکیشن را حذف نمی‌کند.

## توصیه‌های عملی برای GodarAI

### برای workflowهای واقعی، `json_schema` را پیش‌فرض بگیرید

اگر خروجی قرار است وارد سیستم دیگری شود، schema بهتر از JSON آزاد است.

### schema را کوچک و واضح نگه دارید

هرچه schema جمع‌وجورتر و دقیق‌تر باشد، کیفیت خروجی بهتر می‌شود.

### از Pydantic یا مدل typed معادل استفاده کنید

این کار فاصله بین model output و application contract را کم می‌کند.

### parsing نهایی را در backend نگه دارید

هیچ‌وقت raw output model را بدون validate وارد سیستم حساس نکنید.

## جمع‌بندی

structured outputs در `Chat Completions` یکی از بهترین راه‌ها برای تبدیل خروجی model به داده قابل‌استفاده در محصول است. در GodarAI، قرارداد اصلی حول `response_format` با دو حالت `json_object` و `json_schema` می‌چرخد. اگر بین انعطاف و کنترل، انتخاب درستی داشته باشید و validation سمت اپلیکیشن را هم نگه دارید، این قابلیت می‌تواند backbone بسیاری از automationها و integrationهای production-grade شما باشد.
