# تفکر عمیق‌تر - Extended Thinking

در بعضی modelهای reasoning-capable، فقط پاسخ نهایی مهم نیست؛ بلکه بخش‌هایی از فرایند استدلال هم می‌تواند در response وجود داشته باشد. در GodarAI این موضوع را با عنوان `Extended Thinking` می‌شناسیم.

این بخش مخصوص سناریوهایی است که:

- reasoning چندمرحله‌ای مهم است
- conversation چند-turnی دارید
- tool calling و reasoning با هم ترکیب می‌شوند
- می‌خواهید context استدلالی model بین turnها حفظ شود

## Extended Thinking چه تفاوتی با reasoning معمولی دارد؟

در صفحه `Caching & Reasoning` بیشتر درباره `reasoning_effort` و `reasoning_content` حرف زدیم. اما `Extended Thinking` یک گام جلوتر می‌رود:

- `reasoning_content` معمولاً خلاصه متنی reasoning است
- `thinking_blocks` ساختارمندترند
- `thinking_blocks` می‌توانند `signature` داشته باشند

همین signatureها هستند که برای ادامه سالم reasoning chain در چند turn اهمیت حیاتی دارند.

## `thinking_blocks` چیست؟

`thinking_blocks` آرایه‌ای از بلوک‌های structured است که reasoning model برمی‌گرداند. هر بلوک معمولاً چیزی شبیه این دارد:

- `type`
- `thinking`
- `signature`

نمونه:

```json
{
  "message": {
    "content": "پاسخ نهایی",
    "reasoning_content": "خلاصه‌ای از روند استدلال",
    "thinking_blocks": [
      {
        "type": "thinking",
        "thinking": "روند استدلال model...",
        "signature": "ErUBCkQIARgCIkC..."
      }
    ]
  }
}
```

## چرا signature مهم است؟

این امضاها صرفاً metadata تزئینی نیستند. در بعضی providerها، اگر بخواهید reasoning chain را در turn بعدی ادامه دهید، باید `thinking_blocks` را دقیقاً با همان signatureهای اصلی برگردانید.

اگر:

- signature حذف شود
- مقدارش عوض شود
- blockها ناقص یا دست‌کاری شوند

provider می‌تواند request را رد کند یا continuity reasoning از بین برود.

## چه modelهایی معمولاً به این فضا نزدیک‌اند؟

در متن منبع، این خانواده‌ها برجسته بودند:

- بعضی مدل‌های Anthropic
- مدل‌های Claude روی Bedrock
- بعضی مدل‌های Gemini / Vertex

اما از دید GodarAI، مهم‌ترین اصل این است:

- Extended Thinking را یک capability model/provider-specific بدانید، نه یک ویژگی تضمین‌شده برای همه modelها

## استفاده پایه

نمونه ساده:

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

response = client.chat.completions.create(
    model="anthropic:default:claude-3-7-sonnet",
    messages=[
        {"role": "user", "content": "چرا 3^3^3 از راست به چپ ارزیابی می‌شود؟"}
    ],
    reasoning_effort="high",
    max_tokens=8000,
)

msg = response.choices[0].message
print(msg.content)
print(msg.reasoning_content)
print(msg.thinking_blocks)
```

## `reasoning_content` در برابر `thinking_blocks`

این دو را با هم قاطی نکنید:

- `reasoning_content` بیشتر برای مشاهده و debug انسانی مفید است
- `thinking_blocks` برای replay دقیق context و provider continuity مهم‌ترند

اگر فقط بخواهید reasoning را ببینید، شاید `reasoning_content` کافی باشد. اما اگر می‌خواهید multi-turn reasoning درست کار کند، `thinking_blocks` مهم‌ترند.

## streaming با Extended Thinking

در حالت stream، معمولاً reasoning یکجا و ساده برنمی‌گردد. بسته به provider ممکن است:

- `reasoning_content` تکه‌تکه در deltaها بیاید
- `reasoning_signature` جداگانه برسد
- یا `thinking_blocks` مستقیم در model extraها ظاهر شوند

به همین دلیل، در سناریوهای production باید stream را accumulate کنید و بعد یک assistant message کامل بسازید.

الگوی مفهومی:

```python
def accumulate_stream(stream):
    content = ""
    reasoning_content = ""
    reasoning_signature = None
    thinking_blocks_direct = []
    tool_calls_buf = {}

    for chunk in stream:
        delta = chunk.choices[0].delta
        extra = delta.model_extra or {}

        if delta.content:
            content += delta.content

        if extra.get("reasoning_content"):
            reasoning_content += extra["reasoning_content"]

        if extra.get("reasoning_signature"):
            reasoning_signature = extra["reasoning_signature"]

        for tb in (extra.get("thinking_blocks") or []):
            thinking_blocks_direct.append(tb)

        for tc in (delta.tool_calls or []):
            slot = tool_calls_buf.setdefault(tc.index, {
                "id": "",
                "type": "function",
                "function": {"name": "", "arguments": ""},
            })
            if tc.id:
                slot["id"] += tc.id
            if tc.function:
                slot["function"]["name"] += tc.function.name or ""
                slot["function"]["arguments"] += tc.function.arguments or ""

    if thinking_blocks_direct:
        thinking_blocks = thinking_blocks_direct
    elif reasoning_content or reasoning_signature:
        thinking_blocks = [{
            "type": "thinking",
            "thinking": reasoning_content,
            **({"signature": reasoning_signature} if reasoning_signature else {}),
        }]
    else:
        thinking_blocks = []

    return content, thinking_blocks, list(tool_calls_buf.values())
```

## چرا serialization assistant message مهم است؟

اگر بعد از پاسخ اول، assistant message را ناقص ذخیره کنید، turn بعدی ممکن است reasoning chain را از دست بدهد. به همین دلیل، در docs قبلی tools هم توصیه کردیم که از:

```python
message.model_dump(exclude_none=True)
```

استفاده کنید.

این کار کمک می‌کند:

- `content` حفظ شود
- `tool_calls` حفظ شوند
- `thinking_blocks` و signatureها هم از بین نروند

## multi-turn conversation

در Extended Thinking، ساده‌ترین قاعده این است:

- assistant message را همان‌طور که برگشته replay کنید

نمونه:

```python
response = client.chat.completions.create(
    model="anthropic:default:claude-3-7-sonnet",
    messages=[{"role": "user", "content": "3^3^3 چیست؟"}],
    reasoning_effort="high",
    max_tokens=8000,
)

assistant_message = response.choices[0].message.model_dump(exclude_none=True)

response2 = client.chat.completions.create(
    model="anthropic:default:claude-3-7-sonnet",
    messages=[
        {"role": "user", "content": "3^3^3 چیست؟"},
        assistant_message,
        {"role": "user", "content": "حالا توضیح بده چرا از راست به چپ حساب می‌شود."}
    ],
    reasoning_effort="high",
    max_tokens=8000,
)
```

## ترکیب با tool calling

یکی از مهم‌ترین سناریوها وقتی است که reasoning و tool calling هم‌زمان فعال باشند. در این حالت:

- model هم `tool_calls` برمی‌گرداند
- هم ممکن است `thinking_blocks` داشته باشد

و شما باید هر دو را در history برگردانید.

نمونه:

```python
import json
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get weather for a city",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
        }
    }
}]

messages = [{"role": "user", "content": "هوای توکیو چطور است؟"}]

response = client.chat.completions.create(
    model="anthropic:default:claude-3-7-sonnet",
    messages=messages,
    tools=tools,
    reasoning_effort="high",
    max_tokens=8000,
)

msg = response.choices[0].message
messages.append(msg.model_dump(exclude_none=True))

for tool_call in msg.tool_calls:
    args = json.loads(tool_call.function.arguments)
    result = f"Sunny, 24°C in {args['city']}"
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": result,
    })

response2 = client.chat.completions.create(
    model="anthropic:default:claude-3-7-sonnet",
    messages=messages,
    tools=tools,
    reasoning_effort="high",
    max_tokens=8000,
)
```

در این سناریو اگر `thinking_blocks` را از assistant message حذف کنید، بعضی providerها continuity لازم را از دست می‌دهند.

## Google Search grounding

در متن منبع، نمونه‌ای از grounding با Google Search هم آمده بود. از دید مفهومی، این همان ترکیب reasoning/tooling با یک سرچ بیرونی است. اما برای docs این صفحه، نکته اصلی این است:

- هر جا model برای ادامه reasoning به tool بیرونی تکیه کند، حفظ assistant message کامل اهمیت بیشتری پیدا می‌کند

## چه اشتباه‌هایی رایج‌اند؟

### دست‌کاری `thinking_blocks`

هیچ normalizing دستی، trim کردن یا بازنویسی روی blockها انجام ندهید مگر این‌که دقیقاً بدانید provider چه می‌خواهد.

### برنگرداندن signature

signature حذف‌شده یا ناقص می‌تواند chain را بشکند.

### ساختن دستی assistant message ناقص

اگر فقط `content` را نگه دارید و `thinking_blocks` را حذف کنید، turn بعدی ممکن است fail یا degrade شود.

### تست نکردن stream و non-stream به‌صورت جدا

رفتار reasoning در stream معمولاً پیچیده‌تر است.

## چه زمانی واقعاً به Extended Thinking نیاز دارید؟

وقتی که:

- session چندمرحله‌ای reasoning-heavy دارید
- tool calling بخشی از منطق کار است
- می‌خواهید continuity استدلال بین turnها حفظ شود

اگر فقط یک جواب نهایی ساده می‌خواهید، معمولاً `reasoning_effort` و `reasoning_content` کافی‌اند و نیازی نیست با لایه کامل Extended Thinking درگیر شوید.

## توصیه‌های عملی برای GodarAI

### assistant message را با `model_dump(exclude_none=True)` ذخیره کنید

این امن‌ترین الگوی عمومی برای حفظ context reasoning است.

### `thinking_blocks` را immutable فرض کنید

آن‌ها را مثل payload امضاشده ببینید، نه یک field قابل ویرایش.

### reasoning + tools را جداگانه تست کنید

وقتی tool calling وارد ماجرا می‌شود، حساسیت chain preservation بیشتر می‌شود.

### ابتدا non-stream، بعد stream

اگر در حال ساخت agent production هستید، اول non-stream multi-turn reasoning را پایدار کنید و بعد به streaming بروید.

## جمع‌بندی

`Extended Thinking` در GodarAI برای سناریوهایی مهم است که reasoning باید بین چند turn حفظ شود، مخصوصاً وقتی tool calling هم وجود دارد. تفاوت اصلی آن با reasoning ساده در وجود `thinking_blocks` و `signature`هاست. اگر assistant message را کامل و بدون دست‌کاری replay کنید، این قابلیت می‌تواند context استدلالی model را در workflowهای چندمرحله‌ای بسیار پایدارتر نگه دارد.
