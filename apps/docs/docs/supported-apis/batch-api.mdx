# Batch API

`Batch API` برای زمانی است که نمی‌خواهید تعداد زیادی درخواست را به‌صورت هم‌زمان و برخط (Online) ارسال کنید، بلکه می‌خواهید آن‌ها را به‌شکل job آسنکرون (Asynchronous Job) ثبت کنید و بعداً نتیجه را دریافت کنید.

این الگو معمولاً برای پردازش‌های حجیم و غیرتعاملی مناسب است؛ مثل:

- برچسب‌گذاری تعداد زیادی رکورد
- خلاصه‌سازی انبوه اسناد
- ارزیابی مجموعه‌ای از promptها
- تولید embedding برای ingestion اولیه داده‌ها
- پردازش شبانه یا زمان‌بندی‌شده

## وضعیت فعلی در گدارAI

در طراحی محصول و اسناد برنامه‌ریزی گدارAI، `Batch API` به‌عنوان یک قابلیت برنامه‌ریزی‌شده در نظر گرفته شده است، اما در پیاده‌سازی فعلی `services/control-plane` هنوز endpoint عمومی آن در دسترس نیست.

به‌صورت مشخص، در roadmap محصول مسیرهای زیر پیش‌بینی شده‌اند:

```text
POST /v1/batches
GET  /v1/batches/{batch_id}
POST /v1/files
GET  /v1/files/{file_id}
DELETE /v1/files/{file_id}
GET  /v1/files/{file_id}/content
```

اما در کد فعلی gateway، route عملیاتی برای این endpointها هنوز پیدا نمی‌شود. بنابراین این صفحه فعلاً مستند «قابلیت در حال برنامه‌ریزی» است، نه راهنمای استفاده از feature آماده در production.

## Batch API چه مسئله‌ای را حل می‌کند؟

اگر امروز برای هر ورودی یک request جدا به `Chat Completions` یا `Embeddings` بزنید، معمولاً با این چالش‌ها روبه‌رو می‌شوید:

- مدیریت concurrency سخت‌تر می‌شود
- retry و tracking jobها پیچیده‌تر می‌شود
- کنترل هزینه برای پردازش‌های بزرگ دشوارتر می‌شود
- برای عملیات طولانی، مدل synchronous مناسب نیست

`Batch API` این مسئله را با تبدیل مجموعه‌ای از requestها به یک job آسنکرون حل می‌کند. در این مدل معمولاً:

1. فایل ورودی آپلود می‌شود.
2. یک batch job ساخته می‌شود.
3. job در backend پردازش می‌شود.
4. وضعیت job از طریق API قابل پیگیری است.
5. خروجی نهایی به‌صورت فایل یا artifact قابل دریافت می‌شود.

## این قابلیت برای چه سناریوهایی مفید است؟

- backfill کردن داده‌های قدیمی
- آماده‌سازی embedding برای مخزن دانش
- ارزیابی quality روی datasetهای بزرگ
- تولید خروجی انبوه برای migration یا enrichment
- پردازش‌هایی که نیاز به پاسخ realtime ندارند

اگر کاربر شما منتظر پاسخ لحظه‌ای است، `Batch API` انتخاب خوبی نیست. در آن حالت endpointهای synchronous مثل `Chat Completions` یا `Embeddings` مناسب‌تر هستند.

## تفاوت Batch API با requestهای عادی

در endpointهای عادی:

- request را می‌فرستید
- همان‌جا پاسخ می‌گیرید
- timeout و latency برای کاربر نهایی مهم است

در `Batch API`:

- یک job ثبت می‌کنید
- پردازش در پس‌زمینه انجام می‌شود
- نتیجه بعداً آماده می‌شود
- برای throughput و مقیاس‌پذیری، مناسب‌تر است

## مسیر پیشنهادی محصول در گدارAI

با توجه به معماری فعلی گدارAI، این قابلیت احتمالاً در نسخه نهایی چنین نقشی خواهد داشت:

- استفاده از contract سازگار با OpenAI برای کاهش friction مهاجرت
- اتصال به `Files API` برای دریافت dataset ورودی
- اعمال auth، budget و rate-limit در سطح tenant و key
- ثبت trace و usage برای هر job و هر آیتم درون batch
- امکان اجرای batch روی مدل‌های مختلف بر اساس routing policy

برای گدارAI این موضوع به‌خصوص مهم است، چون بسیاری از مشتریان سازمانی به پردازش‌های زمان‌بندی‌شده، ingestion انبوه، و کنترل دقیق هزینه در سطح tenant نیاز دارند.

## تا قبل از ارائه رسمی Batch API چه کار کنیم؟

تا وقتی این endpoint رسماً پیاده‌سازی نشده، پیشنهاد عملی این است:

### برای پردازش متنی

از `Chat Completions` استفاده کنید و job orchestration را در سرویس خودتان انجام دهید.

### برای تولید بردار

از [Embeddings](D:/source/Shahrah/apps/docs/docs/supported-apis/embeddings.mdx) استفاده کنید و ورودی‌ها را در batchهای کوچک‌تر به‌شکل آرایه‌ای از `string` ارسال کنید.

### برای کنترل فشار روی سیستم

- اندازه batchهای داخلی خودتان را محدود نگه دارید
- retry policy صریح داشته باشید
- jobها را queue کنید
- مصرف بودجه و rate limit را قبل از اجرای گسترده بررسی کنید

## یک الگوی موقت پیشنهادی

اگر همین امروز بخواهید رفتار نزدیک به batch بسازید، می‌توانید چنین الگویی داشته باشید:

1. dataset را در storage خودتان نگه دارید.
2. آن را به chunkهای کوچک‌تر تقسیم کنید.
3. هر chunk را با workerهای داخلی به API گدارAI بفرستید.
4. نتیجه هر request را ذخیره کنید.
5. در انتها یک گزارش نهایی بسازید.

این روش جایگزین رسمی `Batch API` نیست، اما برای MVP یا ingestionهای داخلی کاملاً کاربردی است.

## وقتی Batch API عرضه شود، چه انتظاری باید داشته باشیم؟

بر اساس الگوی رایج این دسته APIها، احتمالاً این قابلیت شامل این بخش‌ها خواهد بود:

- ساخت job با `POST /v1/batches`
- مشاهده وضعیت job
- دریافت فایل نتیجه
- مشاهده خطاهای آیتم‌به‌آیتم
- اتصال به `Files API`
- محاسبه usage و cost برای پردازش انبوه

اما تا وقتی implementation نهایی وارد کد نشده، بهتر است این موارد را «انتظار منطقی» بدانیم، نه contract قطعی محصول.

## چه زمانی از Batch API استفاده نکنیم؟

این قابلیت برای همه use caseها مناسب نیست. مثلاً:

- چت زنده با کاربر
- agentهای تعاملی
- تجربه realtime در UI
- tool calling که نیاز به رفت‌وبرگشت سریع دارد

در این موارد، endpointهای synchronous انتخاب بهتری هستند.

## جمع‌بندی

`Batch API` در گدارAI یک قابلیت مهم و برنامه‌ریزی‌شده برای پردازش‌های انبوه و آسنکرون است، اما در نسخه فعلی gateway هنوز به‌صورت endpoint عمومی عرضه نشده است. اگر امروز به این الگو نیاز دارید، بهترین راه این است که orchestration را موقتاً در سرویس خودتان پیاده کنید و برای پردازش واقعی از endpointهای آماده مثل `Chat Completions` و `Embeddings` استفاده کنید.
