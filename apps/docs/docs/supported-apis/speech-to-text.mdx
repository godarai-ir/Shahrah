# Speech to Text

`Speech to Text` یا تبدیل گفتار به متن، فایل صوتی را می‌گیرد و متن قابل‌استفاده برای اپلیکیشن، جست‌وجو، تحلیل یا workflowهای downstream برمی‌گرداند. این قابلیت یکی از پایه‌ای‌ترین APIها برای ساخت تجربه‌های صوتی است.

در طراحی محصول گدارAI، این capability با مسیر زیر در نظر گرفته شده است:

```text
POST /v1/audio/transcriptions
```

## وضعیت فعلی در گدارAI

در اسناد محصول و نقشه راه گدارAI، `Speech to Text` بخشی از خانواده `audio` است و در catalog نوع مدل‌ها هم برای آن نوع اختصاصی وجود دارد. اما در پیاده‌سازی فعلی `services/control-plane` هنوز handler عمومی برای `POST /v1/audio/transcriptions` در لایه proxy دیده نمی‌شود.

یعنی در وضعیت فعلی:

- contract هدف این API مشخص است
- جایگاه آن در معماری محصول روشن است
- اما endpoint عمومی آن هنوز مانند `Images` یا `Responses` در gateway فعلی پیاده‌سازی و operational نشده است

پس این صفحه را باید سند قابلیت برنامه‌ریزی‌شده بدانید، نه راهنمای یک endpoint کاملاً عرضه‌شده.

## Speech to Text چه مسئله‌ای را حل می‌کند؟

این API برای زمانی است که ورودی کاربر یا سیستم شما صوت است، اما تمام لایه‌های بعدی شما با متن کار می‌کنند. مثلاً:

- جست‌وجو روی محتوای صوتی
- خلاصه‌سازی تماس یا جلسه
- تحلیل گفتگو
- ساخت agent صوتی
- آرشیو و ایندکس فایل‌های صوتی

به‌جای این‌که برای هر provider صوتی منطق جداگانه بنویسید، هدف گدارAI این است که:

- یک contract یکدست برای STT فراهم کند
- auth، budget و rate limit را متمرکز کند
- usage و observability را در gateway نگه دارد
- routing را بر اساس deploymentهای واقعی tenant انجام دهد

## تفاوت Speech to Text با Audio Translation

این دو API خیلی نزدیک‌اند، ولی خروجی نهایی متفاوتی دارند:

- `Speech to Text`: متن گفتار را استخراج می‌کند
- `Audio Translation`: متن ترجمه‌شده‌ی گفتار را برمی‌گرداند

اگر فایل صوتی فارسی دارید و متن فارسی آن را می‌خواهید، STT انتخاب طبیعی‌تری است. اگر فایل صوتی به زبان دیگر دارید و خروجی مقصد برای پردازش downstream می‌خواهید، translation مطرح می‌شود.

## contract هدف در گدارAI

مسیر هدف این API:

```text
POST /v1/audio/transcriptions
```

از نظر طراحی، این endpoint قرار است با سایر APIهای OpenAI-compatible گدارAI هم‌راستا باشد تا مهاجرت برای تیم‌هایی که از همین قرارداد استفاده می‌کنند ساده‌تر شود.

## انتظار معمول از request

در الگوی رایج این endpoint، معمولاً چنین فیلدهایی دیده می‌شوند:

- `model`
- `file`
- در بعضی مدل‌ها `language`
- در بعضی providerها `prompt` یا `response_format`

نمونه مفهومی:

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

with open("audio.mp3", "rb") as audio_file:
    response = client.audio.transcriptions.create(
        model="openai:default:whisper-1",
        file=audio_file,
    )

print(response)
```

این نمونه contract هدف را نشان می‌دهد، نه این‌که همین حالا در gateway فعلی الزاماً فعال باشد.

## خروجی مورد انتظار

در ساده‌ترین حالت، خروجی شامل متن گفتار است:

```json
{
  "text": "سلام، این یک فایل آزمایشی است."
}
```

بسته به provider و response format، بعداً ممکن است metadataهای بیشتری مثل segment یا timestamp هم مطرح شوند. اما از دید محصول، هدف اصلی این است که تجربه مصرف برای client ساده و قابل‌پیش‌بینی بماند.

## این قابلیت از نظر محصول چطور باید کار کند؟

وقتی `Speech to Text` در گدارAI به‌صورت کامل عرضه شود، انتظار منطقی این است که:

- model بر اساس deployment مجاز tenant resolve شود
- دسترسی بر اساس نوع `audio_transcription` کنترل شود
- فایل صوتی به provider مناسب route شود
- budget و rate limit پیش از اجرا بررسی شوند
- متن خروجی در قالب contract سازگار برگردد
- usage و cost در سطح tenant ثبت شوند

این الگو با سایر endpointهای اصلی گدارAI هم‌راستا است.

## چه formatهایی مهم‌اند؟

در مستند مرجع TrueFoundry، formatهای رایجی مثل این‌ها برای STT ذکر شده‌اند:

- `mp3`
- `mp4`
- `mpeg`
- `mpga`
- `m4a`
- `wav`
- `webm`

اما در گدارAI معیار نهایی برای production، deployment واقعی tenant شماست. یعنی حتی اگر formatی در مستند مرجع رایج باشد، بهتر است آن را با model و provider واقعی configured در محیط خودتان تست کنید.

## سناریوهای رایج استفاده

این API معمولاً در این workflowها ارزشمند است:

- تبدیل تماس ضبط‌شده به متن برای تحلیل
- transcription جلسه برای مستندسازی
- تبدیل voice note کاربر به متن قابل‌جست‌وجو
- تغذیه ورودی صوتی به agentهای متنی
- تولید subtitle یا draft اولیه برای محتوای صوتی

## تا قبل از عرضه رسمی چه کار کنیم؟

اگر همین حالا به STT نیاز دارید، دو مسیر عملی دارید:

### استفاده مستقیم از provider

می‌توانید فعلاً از SDK یا API رسمی provider استفاده کنید و orchestration را در سرویس خودتان نگه دارید.

### ساخت abstraction داخلی

اگر برنامه دارید بعداً این قابلیت را از مسیر گدارAI مصرف کنید، بهتر است از حالا یک abstraction داخلی برای STT داشته باشید تا بعداً فقط adapter را عوض کنید.

## چند توصیه عملی برای کاربران گدارAI

### زبان و کیفیت فایل را جدی بگیرید

کیفیت transcription به زبان، لهجه، noise و کیفیت ضبط بسیار وابسته است.

### formatهای ورودی را محدود و استاندارد نگه دارید

اگر pipeline شما فقط چند format مشخص را بپذیرد، debugging و migration ساده‌تر می‌شود.

### STT و translation را در طراحی محصول قاطی نکنید

کاربران و downstream systemها معمولاً انتظار متفاوتی از این دو خروجی دارند.

### برای rollout بعدی، VAT را در نظر بگیرید

وقتی این endpoint در گدارAI عرضه شود، برای مصرف سازمانی و سیستمی، virtual account token معمولاً از PAT انتخاب مناسب‌تری خواهد بود.

## جمع‌بندی

`Speech to Text` در گدارAI یک قابلیت برنامه‌ریزی‌شده در خانواده `audio` است و contract هدف آن `POST /v1/audio/transcriptions` خواهد بود. اما در پیاده‌سازی فعلی `services/control-plane` هنوز route و handler عمومی آن مانند endpointهای اصلی دیگر دیده نمی‌شود. اگر امروز به STT نیاز دارید، بهتر است موقتاً از provider مستقیم یا abstraction داخلی استفاده کنید و این صفحه را به‌عنوان سند مسیر محصولی گدارAI برای تبدیل گفتار به متن در نظر بگیرید.
