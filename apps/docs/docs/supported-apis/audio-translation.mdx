# Audio Translation

`Audio Translation` برای تبدیل فایل صوتی گفتاری به متن ترجمه‌شده استفاده می‌شود. در الگوی رایج OpenAI-compatible، این endpoint معمولاً صوت ورودی را می‌گیرد و متن نهایی را به زبان مقصد استاندارد برمی‌گرداند؛ در بسیاری از پیاده‌سازی‌ها این مقصد به‌صورت پیش‌فرض انگلیسی است.

در طراحی محصول گدارAI، این قابلیت با مسیر زیر در نظر گرفته شده است:

```text
POST /v1/audio/translations
```

## وضعیت فعلی در گدارAI

در اسناد محصول و نقشه راه گدارAI، `Audio Translation` بخشی از خانواده `audio` است و در catalog نوع مدل‌ها هم برای آن نوع اختصاصی وجود دارد. اما در پیاده‌سازی فعلی `services/control-plane` هنوز handler عمومی برای `POST /v1/audio/translations` در لایه proxy دیده نمی‌شود.

یعنی در وضعیت فعلی:

- contract هدف محصول مشخص است
- جایگاه این قابلیت در معماری معلوم است
- اما endpoint عمومی آن هنوز مانند `Responses` یا `Images` در gateway فعلی پیاده‌سازی‌شده و production-ready نیست

پس این صفحه را باید به‌عنوان مستند «قابلیت برنامه‌ریزی‌شده» در نظر گرفت.

## Audio Translation چه مسئله‌ای را حل می‌کند؟

این قابلیت برای زمانی مفید است که کاربر یا سیستم شما فایل صوتی در یک زبان دارد، اما شما می‌خواهید خروجی متنی ترجمه‌شده دریافت کنید. این موضوع با transcription ساده فرق دارد:

- `Transcription`: صوت را به متن همان زبان یا متن گفتار تبدیل می‌کند
- `Translation`: صوت را می‌گیرد و متن نهایی را به زبان مقصد برمی‌گرداند

این API برای سناریوهایی مثل این مناسب است:

- ترجمه مصاحبه یا پادکست خارجی به متن قابل‌پردازش
- ingest کردن محتوای صوتی غیرفارسی برای pipelineهای متنی
- ساخت workflow تحلیل محتوا روی فایل‌های صوتی چندزبانه
- آماده‌سازی متن ترجمه‌شده برای جست‌وجو، خلاصه‌سازی یا RAG

## contract هدف در گدارAI

مسیر هدف این قابلیت در معماری گدارAI:

```text
POST /v1/audio/translations
```

از دید طراحی محصول، این endpoint قرار است با سایر APIهای OpenAI-compatible هماهنگ باشد تا migration برای تیم‌هایی که قبلاً با این قرارداد کار کرده‌اند ساده‌تر شود.

## انتظار معمول از request

در الگوی رایج این endpoint، معمولاً چنین فیلدهایی مطرح هستند:

- `model`
- `file`
- در بعضی providerها تنظیمات تکمیلی مثل `prompt` یا `response_format`

نمونه مفهومی:

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_BASE_URL",
)

audio_file = open("speech.mp3", "rb")

translation = client.audio.translations.create(
    model="openai:default:whisper-1",
    file=audio_file
)

print(translation.text)
```

این نمونه contract هدف را نشان می‌دهد، نه این‌که الزاماً همین حالا در gateway فعلی فعال باشد.

## خروجی مورد انتظار

در الگوی معمول، پاسخ ساده و متنی است:

```json
{
  "text": "Hello, how are you?"
}
```

در بعضی providerها ممکن است formatها یا metadataهای بیشتری هم وجود داشته باشند، اما هدف گدارAI این است که تجربه مصرف برای client تا حد ممکن ساده و یکدست بماند.

## تفاوت Audio Translation با Speech to Text

این دو خیلی به هم نزدیک‌اند، اما برای use caseهای متفاوتی استفاده می‌شوند:

- `Speech to Text`: متن گفتار را استخراج می‌کند
- `Audio Translation`: متن ترجمه‌شده از گفتار را برمی‌گرداند

اگر مثلاً فایل صوتی انگلیسی دارید و فقط متن انگلیسی آن را می‌خواهید، به STT نزدیک‌تر هستید. اگر فایل صوتی غیرانگلیسی دارید و خروجی متنی مقصد برای پردازش downstream می‌خواهید، translation اهمیت بیشتری پیدا می‌کند.

## این قابلیت از نظر محصول چطور باید کار کند؟

وقتی `Audio Translation` در گدارAI کامل عرضه شود، انتظار منطقی این است که:

- model بر اساس deployment مجاز tenant resolve شود
- دسترسی بر اساس نوع `audio_translation` کنترل شود
- budget و rate limit پیش از اجرا بررسی شوند
- فایل صوتی به provider مناسب route شود
- متن نهایی ترجمه‌شده به client برگردد
- usage و cost در سطح tenant ثبت شوند

این رفتار با الگوی بقیه endpointهای اصلی گدارAI سازگار است.

## چه formatهایی ممکن است مهم باشند؟

در مستند مرجع TrueFoundry، formatهای رایجی مثل این‌ها مطرح شده‌اند:

- `mp3`
- `mp4`
- `mpeg`
- `mpga`
- `m4a`
- `wav`
- `webm`

اما در گدارAI، معیار نهایی برای production باید model و provider واقعی پیکربندی‌شده در tenant شما باشد. یعنی حتی اگر یک format در مستند مرجع آمده باشد، بهتر است آن را روی deployment واقعی خودتان تست کنید.

## تا قبل از عرضه رسمی چه کار کنیم؟

اگر همین حالا به `Audio Translation` نیاز دارید، دو مسیر عملی دارید:

### استفاده مستقیم از provider

می‌توانید موقتاً از API یا SDK رسمی provider استفاده کنید و orchestration را در سرویس خودتان نگه دارید.

### ساخت abstraction داخلی

اگر برنامه دارید بعداً این قابلیت را از مسیر گدارAI مصرف کنید، از همین حالا یک abstraction داخلی برای audio translation بسازید تا بعداً فقط adapter عوض شود.

## چند توصیه عملی برای کاربران گدارAI

### translation و transcription را از ابتدا در طراحی جدا ببینید

این دو معمولاً در محصول قاطی می‌شوند، ولی خروجی و expectation کاربران متفاوت است.

### روی داده واقعی تست بگیرید

برای فایل‌های چندزبانه، لهجه‌دار یا noisy، کیفیت translation را باید با داده واقعی خودتان بسنجید.

### format ورودی را استاندارد نگه دارید

هرچه pipeline ورودی شما روی formatهای محدودتر و پایدارتر کار کند، مهاجرت و debugging ساده‌تر می‌شود.

### برای rollout بعدی، VAT را در نظر بگیرید

وقتی این endpoint در گدارAI عرضه شود، برای مصرف سازمانی و سیستمی، virtual account token معمولاً انتخاب مناسب‌تری از PAT خواهد بود.

## جمع‌بندی

`Audio Translation` در گدارAI یک قابلیت برنامه‌ریزی‌شده در خانواده `audio` است و contract هدف آن `POST /v1/audio/translations` خواهد بود. اما در پیاده‌سازی فعلی `services/control-plane` هنوز route و handler عمومی آن مانند endpointهای اصلی دیگر دیده نمی‌شود. اگر امروز به این قابلیت نیاز دارید، بهتر است موقتاً از provider مستقیم یا یک abstraction داخلی استفاده کنید و این صفحه را به‌عنوان سند مسیر محصولی گدارAI برای audio translation در نظر بگیرید.
