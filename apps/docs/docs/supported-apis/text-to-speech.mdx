# Text to Speech

`Text to Speech` یا تبدیل متن به گفتار، متن نوشته‌شده را به خروجی صوتی تبدیل می‌کند. این قابلیت برای سناریوهایی مثل دستیار صوتی، خواندن محتوای آموزشی، تولید narration، و ساخت تجربه‌های صوتی در محصول بسیار کاربردی است.

در طراحی محصول گدارAI، این قابلیت با مسیر OpenAI-compatible زیر در نظر گرفته شده است:

```text
POST /v1/audio/speech
```

## وضعیت فعلی در گدارAI

در اسناد محصول و roadmap گدارAI، `Text to Speech` به‌عنوان بخشی از خانواده `audio` پیش‌بینی شده است. اما در پیاده‌سازی فعلی `services/control-plane` هنوز handler عمومی برای `POST /v1/audio/speech` در لایه proxy دیده نمی‌شود.

یعنی در این لحظه:

- این صفحه جایگاه محصولی و contract هدف را توضیح می‌دهد
- اما endpoint عمومی TTS هنوز مانند `Chat Completions` یا `Images` در gateway فعلی پیاده‌سازی‌شده و قابل اتکا برای production نیست

پس این مستند را باید «راهنمای قابلیت برنامه‌ریزی‌شده» در نظر بگیرید، نه سند یک feature کاملاً عرضه‌شده.

## Text to Speech چه مسئله‌ای را حل می‌کند؟

اگر بخواهید برای هر provider صوتی منطق جداگانه‌ای برای auth، routing، logging و کنترل مصرف بسازید، integration شما به‌سرعت پیچیده می‌شود. هدف گدارAI از TTS این است که:

- یک contract یکدست برای تبدیل متن به صدا فراهم کند
- model access را در سطح tenant و key کنترل کند
- budget و rate limit را به‌صورت متمرکز اعمال کند
- usage و observability را در همان gateway نگه دارد

## چه زمانی از Text to Speech استفاده کنیم؟

این قابلیت برای سناریوهایی مثل این مناسب است:

- خواندن خودکار متن‌های فارسی برای کاربر
- ساخت narration برای محتوای آموزشی
- تولید voice response در agentهای صوتی
- ساخت preview صوتی برای محتوا
- تبدیل اعلان‌ها یا پاسخ‌های متنی به فایل صوتی

اگر ورودی شما فایل صوتی است و می‌خواهید آن را به متن تبدیل کنید، آن موضوع در دسته `Speech to Text` قرار می‌گیرد، نه `Text to Speech`.

## contract هدف در گدارAI

مسیر هدف محصول برای این API چنین است:

```text
POST /v1/audio/speech
```

از دید طراحی، این endpoint قرار است در کنار سایر APIهای OpenAI-compatible گدارAI قرار بگیرد و برای clientهایی که همین قرارداد را می‌شناسند، friction مهاجرت را کم کند.

## انتظار معمول از request

بر اساس الگوی رایج OpenAI-style TTS، معمولاً چنین فیلدهایی انتظار می‌روند:

- `model`
- `input`
- `voice`
- در بعضی مدل‌ها `format` یا تنظیمات وابسته به provider

نمونه مفهومی:

```json
{
  "model": "openai:default:gpt-4o-mini-tts",
  "voice": "alloy",
  "input": "سلام، به پلتفرم گدارAI خوش آمدید."
}
```

توجه کنید که این نمونه، contract هدف را نشان می‌دهد؛ نه این‌که الزاماً همین حالا در gateway فعلی قابل اجرا باشد.

## این قابلیت از نظر محصول چطور باید کار کند؟

وقتی TTS در گدارAI کامل عرضه شود، انتظار منطقی این است که:

- model بر اساس deploymentهای مجاز tenant resolve شود
- دسترسی بر اساس نوع model مربوط به TTS کنترل شود
- budget و rate limit پیش از اجرا بررسی شوند
- پاسخ صوتی به‌صورت فایل یا stream صوتی برگردد
- usage و cost در سطح tenant ثبت شوند

این رفتار با الگوی بقیه endpointهای اصلی گدارAI هم‌راستا است.

## تفاوت TTS با STT

این دو معمولاً کنار هم می‌آیند، اما مسئله متفاوتی را حل می‌کنند:

- `Text to Speech`: متن را به صوت تبدیل می‌کند
- `Speech to Text`: صوت را به متن تبدیل می‌کند

اگر در حال ساخت agent صوتی هستید، احتمالاً به هر دو نیاز دارید:

1. صوت کاربر را به متن تبدیل کنید
2. پاسخ متنی model را تولید کنید
3. پاسخ را دوباره به صوت تبدیل کنید

## چه providerهایی ممکن است پشت این قابلیت باشند؟

در مستند مرجع TrueFoundry، برای TTS به providerهای متعددی اشاره شده است. اما در گدارAI بهتر است این موضوع را محصول‌محور ببینیم:

- معیار نهایی، deployment واقعی داخل tenant شماست
- model باید با نوع `text_to_speech` ثبت شده باشد
- رفتار جزئی پارامترها ممکن است بین providerها متفاوت باشد

پس حتی پس از پیاده‌سازی نهایی، باید روی modelهای configured خودتان تست عملی بگیرید.

## تا قبل از عرضه رسمی TTS چه کار کنیم؟

اگر همین حالا به قابلیت TTS نیاز دارید، دو مسیر عملی وجود دارد:

### استفاده مستقیم از provider

می‌توانید موقتاً از SDK یا API رسمی provider موردنظر استفاده کنید و orchestration را در سرویس خودتان نگه دارید.

### طراحی abstraction در لایه اپلیکیشن

اگر می‌دانید بعداً می‌خواهید به گدارAI مهاجرت کنید، از همین حالا یک abstraction داخلی برای TTS بسازید تا بعداً فقط adapter را عوض کنید.

## چند توصیه عملی برای کاربران گدارAI

### خروجی صوتی را format-aware طراحی کنید

از همان ابتدا مشخص کنید که در اپ شما `mp3`، `wav` یا stream صوتی کدام مناسب‌تر است.

### برای فارسی، کیفیت صدا را روی داده واقعی خودتان تست کنید

حتی اگر provider از TTS پشتیبانی کند، کیفیت لحن، طبیعی‌بودن و pronunciation فارسی باید با نمونه‌های واقعی ارزیابی شود.

### abstraction داخلی بسازید

اگر roadmap شما شامل TTS است، بهتر است وابستگی مستقیم به یک provider را از الان کم کنید.

### برای production بعدی، VAT را در نظر بگیرید

وقتی این endpoint در گدارAI عرضه شود، برای مصرف سیستمی و سازمانی احتمالاً `VAT` انتخاب مناسب‌تری از `PAT` خواهد بود.

## جمع‌بندی

`Text to Speech` در گدارAI یک قابلیت مهم و برنامه‌ریزی‌شده در خانواده `audio` است و contract هدف آن `POST /v1/audio/speech` خواهد بود. اما در پیاده‌سازی فعلی `services/control-plane` هنوز route و handler عمومی آن مانند endpointهای اصلی دیگر دیده نمی‌شود. اگر امروز به TTS نیاز دارید، بهتر است موقتاً از provider مستقیم یا abstraction داخلی استفاده کنید و این صفحه را به‌عنوان سند مسیر محصولی گدارAI برای TTS در نظر بگیرید.
