# قابلیت‌ها و محدوده پشتیبانی Guardrails

این صفحه مکمل [Guardrails](/guardrails) است و به‌جای توضیح مفهومی، روی محدوده پشتیبانی تمرکز می‌کند: این‌که Guardrails در GodarAI معمولاً روی چه نوع endpointها، چه نوع ورودی‌ها و چه حالت‌های اجرایی معنا دارد و در چه جاهایی نباید انتظار اجرای آن را داشته باشید.

## Guardrails در چه لایه‌ای عمل می‌کند؟

Guardrails در سطح gateway اعمال می‌شود؛ یعنی بین اپلیکیشن شما و مدل یا provider بالادست قرار می‌گیرد. مزیت این رویکرد این است که منطق کنترل، اعتبارسنجی و تصمیم‌گیری از کد تک‌تک کلاینت‌ها جدا می‌شود و می‌تواند به‌صورت متمرکز اعمال شود.

به همین دلیل، پشتیبانی Guardrails بیشتر تابع نوع endpoint و نوع workload است، نه فقط یک provider خاص.

## کدام endpointها برای Guardrails مناسب‌تر هستند؟

به‌صورت مفهومی، Guardrails روی endpointهایی بیشترین معنا را دارد که:

- یک ورودی متنی قابل‌تحلیل داشته باشند
- یا یک خروجی متنی تولیدشده توسط مدل برگردانند

در ساختار مستندات فعلی GodarAI، این دسته از APIها طبیعی‌ترین نامزدها هستند:

- [Chat Completions](/supported-apis/chat-completions/overview)
- [Responses API](/supported-apis/responses-api)
- [Messages](/supported-apis/messages)
- [Embeddings](/supported-apis/embeddings)

برای `Embeddings` معمولاً فقط Guardrail ورودی معنا دارد، چون خروجی آن متن تولیدشده برای ارزیابی policy نیست.

## چه endpointهایی معمولاً candidate خوبی برای Guardrails نیستند؟

همه endpointها برای Guardrails مناسب نیستند. در بسیاری از موارد، اگر endpoint:

- فراخوانی inference متنی نباشد
- خروجی تولیدی قابل‌ارزیابی نداشته باشد
- یا payload آن از جنس فایل، تصویر، صوت یا عملیات غیرمتنی باشد

نباید انتظار همان الگوی Guardrail متنی را داشته باشید.

در عمل، این دسته‌ها معمولاً خارج از سناریوی طبیعی Guardrails متنی قرار می‌گیرند:

- endpointهای فایل
- endpointهای batch
- endpointهای fine-tuning
- بیشتر endpointهای تصویری و صوتی
- endpointهایی که صرفاً retrieval یا readback هستند، نه اجرای inference

این محدودیت مهم است، چون جلوی این سوءبرداشت را می‌گیرد که هر چیزی که از gateway عبور می‌کند الزاماً قابل Guardrail شدن است.

## Guardrails روی ورودی و خروجی چه تفاوتی دارد؟

Guardrails معمولاً در دو مسیر اجرا می‌شود:

- `input guardrails` پیش از ارسال request به model
- `output guardrails` پیش از تحویل response به مصرف‌کننده

تفاوت عملی این دو:

- روی ورودی، بیشتر به‌دنبال جلوگیری از ورود محتوای ناسازگار، prompt injection، داده نامعتبر یا ساختار نامطلوب هستیم
- روی خروجی، بیشتر به‌دنبال ارزیابی کیفیت، انطباق با schema، افشای داده، یا policy enforcement هستیم

اگر use case شما روی کنترل ورودی متمرکز است، از input guardrail شروع کنید. اگر مسئله شما کیفیت و ایمنی پاسخ است، output guardrail اولویت بیشتری دارد.

## حالت همزمان و غیرهمزمان

از نظر اجرایی، Guardrails معمولاً می‌تواند در دو حالت معنا پیدا کند:

- `غیرهمزمان` (Async): برای مشاهده، ثبت نتیجه و تحلیل بدون توقف request
- `همزمان` (Sync): برای کنترل فعال مسیر درخواست یا پاسخ

درک تفاوت این دو خیلی مهم است:

- Async برای شروع امن‌تر است، چون ریسک مسدودسازی ناخواسته ترافیک را کم می‌کند
- Sync زمانی مناسب است که واقعاً می‌خواهید نتیجه Guardrail در تصمیم نهایی اثر مستقیم بگذارد

برای اکثر تیم‌ها، شروع با async و حرکت تدریجی به‌سمت sync، الگوی پایدارتری است.

## نسبت Guardrails با Streaming

در درخواست‌های streaming، رفتار Guardrails پیچیده‌تر می‌شود. از نظر مفهومی:

- Guardrail ورودی می‌تواند پیش از شروع stream ارزیابی شود
- Guardrail خروجی معمولاً فقط وقتی قابل‌تحلیل کامل است که پاسخ نهایی assembled شده باشد

این یعنی اگر مسئله شما روی خروجی stream است، باید در نظر بگیرید که بعضی تصمیم‌ها فقط بعد از تکمیل پاسخ قابل‌اتخاذ هستند. بنابراین همه actionها در streaming به یک اندازه طبیعی یا قابل‌اعمال نیستند.

## در محتوای چندوجهی (Multimodal) چه چیزی ارزیابی می‌شود؟

Guardrails متنی معمولاً فقط بخش متنی پیام را بررسی می‌کند، نه خود فایل تصویری یا داده دودویی را. پس اگر پیام شما ترکیبی از متن و تصویر باشد:

- متن می‌تواند موضوع Guardrail باشد
- خود تصویر معمولاً با Guardrail متنی ارزیابی نمی‌شود

این تفاوت برای workloadهای چندوجهی مهم است، چون ممکن است تصور شود کل payload بررسی شده، درحالی‌که فقط بخش متن واقعاً وارد موتور ارزیابی شده است.

## نسبت Guardrails با Tool Calling

در سناریوهای tool calling، Guardrails فقط روی متن ساده کاربر معنا ندارد. این بخش‌ها هم می‌توانند مهم باشند:

- تصمیم مدل برای فراخوانی ابزار
- آرگومان‌های tool call
- محتوایی که بعد از اجرای ابزار دوباره به مدل برمی‌گردد

در عمل، خیلی از این داده‌ها در نهایت به‌شکل متن یا ساختار JSON دیده می‌شوند و می‌توانند موضوع ruleهای مبتنی بر Regex، schema یا detectorهای معنایی باشند.

برای همین، در workflowهای agentic باید Guardrails را فراتر از «بررسی متن خروجی نهایی» ببینید.

## Quick Reference

خلاصه مفهومی محدوده پشتیبانی:

- endpointهای متنی و inference محور: مناسب
- embeddings: مناسب برای ورودی
- responses و messages: مناسب برای ورودی و خروجی
- streaming: مناسب، اما با محدودیت در زمان و نوع تصمیم روی خروجی
- multimodal: متن قابل ارزیابی است، تصویر معمولاً نه
- audio/image/file/batch style endpointها: معمولاً خارج از محدوده طبیعی guardrail متنی

## این صفحه را چگونه استفاده کنیم؟

اگر می‌خواهید برای یک API خاص Guardrail طراحی کنید، بهتر است این ترتیب را دنبال کنید:

1. اول [Guardrails](/guardrails) را برای درک مدل ذهنی و رفتارهای ممکن بخوانید.
2. بعد endpoint هدف را در مستندات API بررسی کنید.
3. مشخص کنید کنترل شما روی ورودی است یا خروجی.
4. تصمیم بگیرید async لازم دارید یا sync.
5. اگر workload شما streaming، multimodal یا tool-calling است، محدودیت‌های همان سناریو را از قبل در طراحی لحاظ کنید.

## FAQ

### آیا Guardrails روی همه endpointهای GodarAI کار می‌کند؟

خیر. Guardrails بیشتر برای endpointهای inference متنی و مسیرهایی که ورودی یا خروجی قابل‌تحلیل دارند مناسب است، نه برای هر نوع API.

### آیا در embeddings هم Guardrail داریم؟

بله، اما معمولاً فقط در سطح ورودی. چون embeddings خروجی متنی تولیدشده برای policy evaluation ندارد.

### آیا در محتوای چندوجهی، خود تصویر هم بررسی می‌شود؟

نه لزوماً. در Guardrail متنی، معمولاً بخش متنی پیام ارزیابی می‌شود و خود تصویر خارج از این دامنه است.
