# خروجی گرفتن از لاگ‌ها در GodarAI

`Logs Export` به شما امکان می‌دهد داده‌های لاگ GodarAI را در قالبی ساخت‌یافته از سیستم خارج کنید و برای تحلیل، گزارش‌گیری، ممیزی یا اتصال به ابزارهای بیرونی استفاده کنید.

اگر [لاگ‌ها و بررسی درخواست‌ها](/observability-logs) برای troubleshooting روزمره و مشاهده مستقیم requestها مناسب است، `Logs Export` بیشتر برای زمانی ارزش دارد که بخواهید روی داده در مقیاس بزرگ‌تر کار کنید؛ مثلاً برای BI، گزارش مدیریتی، تحلیل هزینه، یا انتقال داده به pipelineهای داخلی.

## چرا Logs Export مهم است؟

دیدن لاگ‌ها داخل UI برای بررسی روزانه عالی است، اما همیشه کافی نیست. در بسیاری از تیم‌ها نیاز دارید:

- گزارش سفارشی برای ذی‌نفعان بسازید
- داده را وارد ابزارهای BI یا warehouse کنید
- روند هزینه و مصرف را در بازه‌های زمانی طولانی تحلیل کنید
- رفتار مدل‌ها و workloadها را در مقیاس بزرگ بررسی کنید
- audit یا بررسی‌های انطباقی را خارج از UI انجام دهید

در این سناریوها، خروجی ساخت‌یافته از لاگ‌ها از «مشاهده» فراتر می‌رود و به «تحلیل داده» تبدیل می‌شود.

## چه نوع داده‌ای معمولاً export می‌شود؟

بسته به طراحی محصول و سطح دسترسی، معمولاً این دسته از فیلدها برای export ارزش بیشتری دارند:

- شناسه لاگ یا request
- `trace_id`
- زمان ایجاد request
- provider و model
- request و response
- token usage
- هزینه
- latency
- status code
- metadata
- config یا شناسه policy مرتبط

این داده‌ها وقتی کنار [رهگیری هزینه](/cost-tracking) و [OpenTelemetry برای مشاهده‌پذیری](/observability-opentelemetry) قرار بگیرند، برای تحلیل‌های عمیق‌تر بسیار مفید می‌شوند.

## چه زمانی export بهتر از مرور مستقیم لاگ‌هاست؟

اگر یکی از این نیازها را دارید، export معمولاً انتخاب بهتری است:

- می‌خواهید داده را روی هزاران یا ده‌ها هزار request تحلیل کنید
- می‌خواهید dashboard سفارشی خارج از UI بسازید
- می‌خواهید داده را به ابزارهایی مثل warehouse، notebook یا BI tool بدهید
- می‌خواهید یک snapshot مشخص برای audit یا گزارش‌گیری نگه دارید
- می‌خواهید تحلیل تیمی یا سازمانی را خارج از محیط product UI انجام دهید

## خروجی گرفتن از لاگ‌ها چه use caseهایی دارد؟

### گزارش‌های مدیریتی

می‌توانید breakdownهایی مثل این بسازید:

- هزینه به‌تفکیک تیم
- مصرف به‌تفکیک model
- رشد latency در بازه‌های زمانی مختلف
- سهم cache hit در کاهش هزینه

### تحلیل محصول و رفتار مصرف

Export کمک می‌کند بفهمید:

- کدام feature بیشترین مصرف مدل را دارد
- کدام workload بیشترین failure را می‌سازد
- کدام provider یا route بیشترین latency را دارد

### انطباق و audit

در بعضی سازمان‌ها لازم است snapshotهایی از داده عملیاتی برای ممیزی، بازرسی یا نگه‌داری خارج از UI ذخیره شود.

### تغذیه ابزارهای بیرونی

خیلی وقت‌ها UI محصول نقطه پایان نیست. داده exportشده می‌تواند وارد:

- data warehouse
- ابزارهای BI
- notebookهای تحلیلی
- pipelineهای ETL
- سیستم‌های audit و governance

شود.

## فرمت خروجی چرا مهم است؟

یکی از ارزش‌های اصلی Logs Export این است که داده در قالبی قابل‌پردازش و ساخت‌یافته خارج شود. در این حالت:

- هر سطر یا رکورد قابل parse است
- تحلیل با ابزارهای برنامه‌نویسی و داده ساده‌تر می‌شود
- join کردن با داده‌های دیگر سازمان راحت‌تر می‌شود

فرمت‌های خط‌محور مثل JSONL معمولاً برای این نوع workflowها مناسب‌اند، چون هم برای ingestion ماشینی خوب‌اند و هم برای پردازش مرحله‌ای.

## انتخاب فیلدها را جدی بگیرید

یکی از مهم‌ترین تصمیم‌ها در export این است که چه فیلدهایی را واقعاً نیاز دارید. انتخاب بیش از حد داده ممکن است:

- فایل خروجی را سنگین کند
- هزینه پردازش بعدی را بالا ببرد
- ریسک نگه‌داری داده حساس را زیاد کند

از طرف دیگر، انتخاب خیلی محدود هم ممکن است تحلیل بعدی را ناقص کند. برای بیشتر تیم‌ها، شروع با هسته‌ای از این فیلدها منطقی است:

- زمان
- request id یا trace id
- model و provider
- token usage
- cost
- latency
- status
- metadataهای هویتی یا محصولی

## نسبت Logs Export با داده حساس

Export لاگ‌ها به‌صورت طبیعی ریسک داده را افزایش می‌دهد، چون اطلاعات از محیط اصلی محصول خارج می‌شود. بنابراین باید خیلی روشن باشد:

- آیا payload کامل request/response لازم است؟
- آیا داده شخصی یا سازمانی داخل export وجود دارد؟
- آیا باید قبل از export از الگوهایی مثل [PII Redaction](/guardrails-pii-redaction) یا logging محدود استفاده شود؟

در بسیاری از موارد، فقط نگه داشتن متادیتاهای عملیاتی کافی است و نیازی به حمل کامل محتوای خام وجود ندارد.

## Logs Export و OTel چه تفاوتی دارند؟

این دو مکمل هم هستند، نه جایگزین:

- `Logs Export` برای خروجی‌گرفتن از داده‌های ثبت‌شده در GodarAI و تحلیل batch یا offline مناسب است
- `OpenTelemetry` بیشتر برای جریان پیوسته telemetry و همبستگی end-to-end بین سرویس‌هاست

اگر مسئله شما گزارش‌گیری، تحلیل تاریخی یا انتقال داده به warehouse است، export معمولاً طبیعی‌تر است. اگر مسئله شما tracing زنده و correlation بین سرویس‌هاست، OTel ارزش بیشتری دارد.

## چند توصیه عملی

### export را بر اساس use case طراحی کنید

برای finance، فیلدهای cost و usage مهم‌ترند. برای SRE، latency و errorها مهم‌ترند. برای product analytics، metadata و feature breakdown مهم‌تر است.

### payload کامل را فقط وقتی لازم است بگیرید

در بسیاری از تحلیل‌ها، request و response کامل لازم نیست و فقط ریسک داده را بالا می‌برد.

### export را با هویت‌ها join کنید

بیشترین ارزش داده زمانی ایجاد می‌شود که بتوانید آن را به tenant، team، workload یا virtual account نسبت دهید.

### export را به workflow تحلیلی واقعی وصل کنید

اگر فایل export فقط دانلود شود و هیچ pipeline تحلیلی نداشته باشد، ارزش عملی آن محدود می‌ماند.

## FAQ

### Logs Export چه تفاوتی با مشاهده مستقیم Logs دارد؟

Logs برای بررسی تعاملی و troubleshooting روزانه مناسب است، اما export برای تحلیل در مقیاس بزرگ، گزارش‌گیری، نگه‌داری snapshot و استفاده در ابزارهای بیرونی مناسب‌تر است.

### آیا باید همیشه request و response کامل را export کنیم؟

خیر. اگر use case شما بدون payload کامل هم قابل‌حل است، بهتر است فقط فیلدهای لازم را بگیرید تا ریسک داده و حجم پردازش کمتر شود.

### Logs Export جایگزین OpenTelemetry است؟

خیر. export بیشتر برای داده‌های تاریخی و batch analysis مناسب است، درحالی‌که OTel برای telemetry پیوسته و همبستگی end-to-end ارزشمندتر است.
