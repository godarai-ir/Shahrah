# احراز هویت

برای دسترسی به مدل‌ها از طریق گدارAI، باید با **API Key خود گدارAI** احراز هویت کنید، نه با کلید خام ارائه‌دهنده‌هایی مثل OpenAI یا Anthropic.

یعنی اپلیکیشن شما فقط یک توکن به گدارAI می‌دهد و خود gateway در پشت‌صحنه اعتبارنامه‌های (credential) ارائه‌دهنده را مدیریت می‌کند.

## شکل استاندارد احراز هویت

رایج‌ترین الگو این است که API key را در هدر `Authorization` بفرستید:

```text
Authorization: Bearer YOUR_GODARAI_API_KEY
```

در بیشتر SDKهای OpenAI-compatible هم همین کار را با `api_key` انجام می‌دهید:

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_GODARAI_API_KEY",
    base_url="YOUR_GODARAI_GATEWAY_BASE_URL",
)
```

یا با متغیر محیطی:

```bash
export OPENAI_BASE_URL="YOUR_GODARAI_GATEWAY_BASE_URL"
export OPENAI_API_KEY="YOUR_GODARAI_API_KEY"
```

## چه نوع توکن‌هایی در گدارAI داریم؟

دو نوع token اصلی داریم:

| نوع | وابسته به | مناسب برای |
| --- | --- | --- |
| `PAT` | کاربر انسانی | توسعه، تست، استفاده شخصی |
| `VAT` | هویت سرویس‌محور | production، backend، worker، CI/CD |

## `PAT`

توکن دسترسی شخصی (Personal Access Token) یا `PAT` برای وقتی مناسب است که یک انسان واقعی می‌خواهد از طرف خودش به gateway وصل شود.

موارد مناسب:

- توسعه محلی
- تست سریع با SDK
- prototyping
- اسکریپت شخصی

## `VAT`

توکن حساب مجازی (Virtual Account Token) یا `VAT` برای عملیات سیستمی طراحی شده است. یعنی وقتی یک سرویس، job، agent یا سرویس بک‌اند باید به گدارAI وصل شود، بهتر است از `VAT` استفاده کند.

موارد مناسب:

- backend service
- worker
- cron job
- CI/CD
- agent
- سرویس production

## کدام را انتخاب کنیم؟

قاعده ساده:

- اگر یک فرد از کلید استفاده می‌کند: `PAT`
- اگر یک سرویس از کلید استفاده می‌کند: `VAT`

اگر بین این دو مردد هستید، این سؤال کمک می‌کند:

«آیا این کلید باید با خروج یک شخص از تیم هم از بین برود؟»

- اگر بله، `PAT`
- اگر نه، `VAT`

## چرا از کلید ارائه‌دهنده استفاده نمی‌کنیم؟

گدارAI اعتبار‌نامه‌های ارائه‌دهندگان را در مخزن امن نگه می‌دارد تا:

- کلیدهای ارائه‌دهنده در همه سرویس‌ها پخش نشوند
- ابطال و چرخش (rotate) ساده‌تر شود
- audit و attribution شفاف‌تر بماند
- سیاست‌های میزان استفاده، هزینه و مدیریت دسترسی در یک نقطه اعمال شوند

## احراز هویت فقط ورود نیست

در گدارAI، API key فقط برای شناسایی شما نیست. این کلید بخشی از مسیر اعمال الزامات اجرایی هم هست. با آن سیستم می‌تواند:

- فضای کاری شما را تشخیص دهد
- کاربر حقیقی یا مجازی را بشناسد
- دسترسی به مدل‌ها را بررسی کند
- مصرف را به همان هویت نسبت دهد
- سیاست‌های میزان استفاده یا کنترل هزینه را اعمال کند

## چند توصیه عملی

### برای کدنویسی از `PAT` و برای محیط عملیاتی (production) از `VAT` استفاده کنید

این سالم‌ترین الگوی عملیاتی است.

### API key را مثل یک متن محرمانه نگه دارید

کلید را داخل repo یا کد hardcode نکنید. از env یا secret manager استفاده کنید.

### برای هر workload مهم، توکن جدا داشته باشید

این کار ملغی کردن، گردش، ممیزی و گزارش مصرف را خیلی ساده‌تر می‌کند.

### دسترسی به مدل را با توکن اشتباه نگیرید

داشتن توکن به‌تنهایی به معنی دسترسی به همه مدل‌ها نیست. دسترسی واقعی به سیاست‌های تنظیم شده و حوزه دسترسی افراد بستگی دارد.

## FAQ

### آیا می‌توانم از کلید خام OpenAI یا Anthropic مستقیماً استفاده کنم؟

خیر. در گدارAI باید از API key خود پلتفرم استفاده کنید و اعتبارنامه‌ی مربوط به ارائه‌دهنده، توسط گدارAI مدیریت می‌شود.

### برای استفاده در محیط عملیاتی، PAT هم کار می‌کند؟

ممکن است از نظر فنی کار کند، اما از نظر عملیاتی انتخاب درستی نیست. برای محیط عملیاتی بهتر است از `VAT` استفاده کنید.

## جمع‌بندی

برای احراز هویت در گدارAI، همیشه از API key خود گدارAI استفاده می‌کنید، نه از کلید ارائه‌دهنده. در عمل، `PAT` برای افراد و `VAT` برای سرویس‌هاست. اگر این تفکیک را از ابتدا درست رعایت کنید، مسیر توسعه، production، revoke، rotate و کنترل دسترسی بسیار تمیزتر و قابل‌اعتمادتر خواهد بود.
