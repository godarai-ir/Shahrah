# احراز هویت در گدارAI

برای ارسال درخواست به مدل‌ها، از کلید دسترسی گدارAI (API Key) استفاده کنید؛ کلید خام ارائه‌دهنده‌هایی مانند OpenAI یا Anthropic را به درخواست ندهید.

گدارAI با این کلید هویت درخواست‌کننده را تشخیص می‌دهد، دسترسی او را بررسی می‌کند و سپس با اعتبارنامه حساب ارائه‌دهنده به مدل مقصد متصل می‌شود.

## پیش‌نیازها

پیش از شروع، این موارد را از محیط گدارAI خود بردارید:

- نشانی پایه درگاه (Base URL)
- یک کلید دسترسی معتبر از نوع `PAT` یا `VAT`
- دسترسی به دست‌کم یک مدل

نشانی پایه را عیناً از تنظیمات محیط بردارید و مسیر نسخه رابط را حدس نزنید.

## ارسال کلید دسترسی

روش پیشنهادی، فرستادن کلید در سرآیند `Authorization` با الگوی `Bearer` است:

```text
Authorization: Bearer YOUR_GODARAI_API_KEY
```

گدارAI برای سازگاری با کارخواه‌های مختلف، سرآیندهای `api-key` و `x-api-key` را نیز می‌پذیرد. مگر اینکه بسته توسعه نرم‌افزار (SDK) شما سرآیند دیگری لازم داشته باشد، از `Authorization` استفاده کنید.

## بررسی احراز هویت با پایتون

ابتدا مقادیر محیط خود را تنظیم کنید:

```bash
export GODARAI_BASE_URL="YOUR_GODARAI_GATEWAY_BASE_URL"
export GODARAI_API_KEY="YOUR_GODARAI_API_KEY"
```

سپس با بسته رسمی OpenAI فهرست مدل‌های در دسترس را بخوانید:

```python
import os

from openai import OpenAI

client = OpenAI(
    api_key=os.environ["GODARAI_API_KEY"],
    base_url=os.environ["GODARAI_BASE_URL"],
)

models = client.models.list()
for model in models.data:
    print(model.id)
```

اگر احراز هویت موفق باشد، درخواست بدون خطای `401` یا `403` اجرا می‌شود و مدل‌های مجاز را برمی‌گرداند. خالی بودن فهرست می‌تواند به این معنا باشد که هنوز مدلی برای هویت شما در دسترس قرار نگرفته است.

## انتخاب نوع کلید

گدارAI دو نوع کلید اصلی دارد:

| نوع | وابسته به | کاربرد مناسب |
| --- | --- | --- |
| `PAT` | کاربر انسانی | توسعه محلی، آزمایش و اسکریپت شخصی |
| `VAT` | کاربر مجازی و تیم | سرویس پشت‌صحنه، پردازشگر، عامل نرم‌افزاری و محیط عملیاتی |

### توکن دسترسی شخصی

توکن دسترسی شخصی (Personal Access Token) یا `PAT` نماینده یک کاربر انسانی است. از آن برای کارهای تعاملی و شخصی استفاده کنید؛ مانند:

- توسعه محلی
- آزمایش سریع با بسته توسعه نرم‌افزار
- ساخت نمونه اولیه
- اجرای اسکریپت شخصی

دسترسی `PAT` به مدل‌ها از تنظیمات دسترسی حساب ارائه‌دهنده و مدل مجازی همان کاربر به دست می‌آید. داشتن کلید به‌تنهایی دسترسی به همه مدل‌ها را ایجاد نمی‌کند.

### توکن حساب مجازی

توکن حساب مجازی (Virtual Account Token) یا `VAT` نماینده یک سرویس است و به شخص وابسته نیست. از آن برای این بارکاری‌ها استفاده کنید:

- Backend Service
- پردازشگر پس‌زمینه
- کار زمان‌بندی‌شده
- عامل نرم‌افزاری
- خط یکپارچه‌سازی و تحویل پیوسته (CI/CD)
- سرویس محیط عملیاتی

ساخت `VAT` این پیش‌نیازها را دارد:

- قابلیت حساب مجازی باید در طرح محیط اختصاصی سازمان فعال باشد.
- یک کاربر مجازی فعال باید وجود داشته باشد.
- کاربر مجازی باید محدوده تیمی معتبر داشته باشد.

برای ساخت کاربر مجازی و توکن آن، [راهنمای مدیریت حساب مجازی](/guides/virtual-account-management) را بخوانید.

### کدام نوع را انتخاب کنیم؟

- اگر کلید نماینده یک فرد است، از `PAT` استفاده کنید.
- اگر کلید نماینده یک سرویس مستقل از افراد است، از `VAT` استفاده کنید.

برای تصمیم‌گیری این پرسش را در نظر بگیرید: «اگر صاحب کلید از تیم خارج شود، آیا کلید نیز باید باطل شود؟» اگر پاسخ مثبت است، `PAT` مناسب‌تر است؛ در غیر این صورت، از `VAT` استفاده کنید.

## چرا کلید ارائه‌دهنده را مستقیم استفاده نمی‌کنیم؟

مدیریت متمرکز اعتبارنامه‌های ارائه‌دهنده این مزایا را دارد:

- کلیدهای ارائه‌دهنده در کد سرویس‌های مصرف‌کننده پخش نمی‌شوند.
- کلید گدارAI را می‌توان برای هر هویت جداگانه باطل یا تعویض کرد.
- ممیزی و انتساب مصرف به کاربر یا سرویس روشن‌تر می‌شود.
- سیاست‌های دسترسی، مصرف و هزینه در یک نقطه اعمال می‌شوند.

روش نگهداری اعتبارنامه ارائه‌دهنده به پیکربندی استقرار بستگی دارد. مدیر سامانه باید پایگاه داده و در صورت استفاده، مرجع رازها را مطابق سیاست امنیتی سازمان محافظت کند.

## احراز هویت با مجوز دسترسی یکسان نیست

کلید دسترسی فقط هویت درخواست‌کننده را مشخص نمی‌کند. گدارAI با اطلاعات همان کلید می‌تواند:

- محیط اختصاصی سازمان را تشخیص دهد.
- کاربر انسانی یا مجازی را شناسایی کند.
- دسترسی به مدل و مسیر درخواستی را بررسی کند.
- مصرف را به همان هویت نسبت دهد.
- محدودیت مصرف و سقف هزینه را اعمال کند.

بنابراین یک کلید معتبر ممکن است برای مدلی خاص مجوز نداشته باشد.

## رفع خطاهای رایج

### پاسخ `401 Unauthorized`

این پاسخ معمولاً یکی از علت‌های زیر را دارد:

- سرآیند احراز هویت ارسال نشده است.
- کلید نادرست یا باطل شده است.
- تاریخ اعتبار کلید گذشته است.

مقدار سرآیند را بررسی کنید و مطمئن شوید پیش یا پس از کلید فاصله اضافی وجود ندارد. اگر کلید باطل یا منقضی شده است، کلید تازه‌ای بسازید.

### پاسخ `403 Forbidden`

این پاسخ یعنی هویت کلید شناخته شده است، اما درخواست اجازه اجرا ندارد. علت‌های رایج عبارت‌اند از:

- کلید مسدود شده است.
- نقش یا سطح دسترسی اجازه استفاده از مسیر را نمی‌دهد.
- مدل در محدوده دسترسی کاربر یا سرویس نیست.

وضعیت کلید، نقش کاربر و تنظیمات دسترسی حساب ارائه‌دهنده یا مدل مجازی را بررسی کنید.

## نگهداری امن کلید

- کلید را مستقیماً داخل کد یا مخزن کد قرار ندهید.
- کلید را از متغیر محیطی یا سامانه مدیریت رازها (Secret Manager) بخوانید.
- برای هر بارکاری مهم یک `VAT` جدا بسازید تا ابطال، چرخش، ممیزی و گزارش مصرف مستقل باشد.
- اگر کلیدی افشا شد، آن را فوراً باطل کنید و کلید تازه‌ای بسازید.

## جمع‌بندی

برای اتصال به مدل‌ها، کلید گدارAI را با سرآیند `Authorization` بفرستید. برای فعالیت یک کاربر انسانی از `PAT` و برای سرویس مستقل از افراد از `VAT` استفاده کنید. معتبر بودن کلید به‌تنهایی دسترسی به همه مدل‌ها و مسیرها را تضمین نمی‌کند.

## پرسش‌های پرتکرار

### آیا می‌توانم کلید خام OpenAI یا Anthropic را مستقیم به گدارAI بدهم؟

خیر. گدارAI درخواست را با کلید خود پلتفرم احراز می‌کند. اعتبارنامه ارائه‌دهنده در حساب ارائه‌دهنده مدیریت می‌شود.

### آیا `PAT` در محیط عملیاتی کار می‌کند؟

ممکن است از نظر فنی کار کند، اما به یک شخص وابسته است. برای سرویس محیط عملیاتی، `VAT` انتخاب مناسب‌تری است.

### چرا امکان ساخت `VAT` را نمی‌بینم؟

قابلیت حساب مجازی باید در طرح محیط اختصاصی سازمان فعال باشد. همچنین برای ساخت آن به یک کاربر مجازی فعال با محدوده تیمی معتبر نیاز دارید.

### تفاوت خطای `401` و `403` چیست؟

خطای `401` معمولاً یعنی کلید وجود ندارد، نامعتبر است یا منقضی شده است. خطای `403` یعنی کلید شناخته شده، اما مسدود است یا برای درخواست موردنظر مجوز ندارد.

### آیا می‌توانم از `x-api-key` استفاده کنم؟

بله. گدارAI سرآیندهای `Authorization`، `api-key` و `x-api-key` را می‌پذیرد. روش پیشنهادی، `Authorization: Bearer ...` است.
