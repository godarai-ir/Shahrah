# مفاهیم پایه مدل‌ها و ارائه‌دهندگان

اگر تازه با کاتالوگ مدل‌ها کار می‌کنید، چند اصطلاح فنی ممکن است شبیه هم به نظر برسند. این صفحه آن‌ها را از زاویه تصمیم‌گیری محصول توضیح می‌دهد: کدام مدل به درد سناریوی شما می‌خورد، چه محدودیتی دارد، هزینه‌اش چگونه خوانده می‌شود و چه چیزی را باید قبل از استفاده عملی بررسی کنید.

## مدل، ارائه‌دهنده و شناسه کامل

| مفهوم | توضیح |
| --- | --- |
| ارائه‌دهنده | سرویس یا شرکتی که مدل را عرضه می‌کند. صفحه ارائه‌دهنده وضعیت، مستندات، وب‌سایت و بعضی قابلیت‌های سطح ارائه‌دهنده را نشان می‌دهد. |
| مدل | گزینه‌ای که برای تولید پاسخ، تحلیل داده، تولید تصویر، پردازش صوت یا کار مشابه استفاده می‌شود. |
| شناسه کامل مدل | مقدار فنی قابل ارجاع مثل `openai/gpt-4o`. این شناسه در لینک مقایسه و API کاتالوگ کاربرد دارد. |
| شناسه مسیر | بخشی از URL صفحه مدل. برای نمونه در `../catalog/models/openai/gpt-4o`، مقدار `openai` ارائه‌دهنده و `gpt-4o` شناسه مسیر مدل است. |

## `mode` و نقطه پایانی

`mode` حالت یا خانواده کاربردی مدل را نشان می‌دهد؛ مثلاً اینکه مدل برای چت، تصویر، صوت، بردارسازی یا کاربرد مشابه ثبت شده است. نقطه پایانی اما مسیر API است؛ مثل `POST /v1/chat/completions` یا `GET /api/v1/models`.

این دو را یکی نگیرید:

| پرسش | پاسخ درست |
| --- | --- |
| `mode` چه می‌گوید؟ | مدل از نظر کاربردی در چه خانواده‌ای قرار می‌گیرد. |
| نقطه پایانی چه می‌گوید؟ | درخواست از چه مسیر API فرستاده می‌شود. |
| آیا هر مدل چندوجهی با هر API کار می‌کند؟ | خیر. باید API، مدل، ارائه‌دهنده و تنظیمات فضای کاری شما با هم سازگار باشند. |

:::info
کاتالوگ به شما برای انتخاب مدل کمک می‌کند، اما قرارداد دقیق درخواست را باید از مستندات API مربوطه بخوانید؛ مثلاً [Chat Completions](/supported-apis/chat-completions/overview)، [Embeddings](/supported-apis/embeddings)، [Image Generation](/supported-apis/image-generation) یا [Speech to Text](/supported-apis/speech-to-text).
:::

## نوع ورودی، نوع خروجی و چندوجهی

نوع ورودی و خروجی مشخص می‌کند مدل با چه داده‌ای کار می‌کند:

| الگو | معنی | نمونه کاربرد |
| --- | --- | --- |
| `text` به `text` | ورودی متن، خروجی متن | پاسخ پشتیبانی، خلاصه‌سازی، دسته‌بندی پیام، تولید متن. |
| `text,image` به `text` | ورودی متن و تصویر، خروجی متن | تحلیل تصویر کالا، خواندن تصویر رسید، توضیح عکس. |
| `text` به `image` | ورودی متن، خروجی تصویر | تولید تصویر محصول، بنر، تصویر کمپین. |
| `audio` به `text` | ورودی صوت، خروجی متن | تبدیل پیام صوتی یا تماس ضبط‌شده به متن. |

مدل چندوجهی مدلی است که بیش از یک نوع ورودی یا خروجی را پشتیبانی کند. برای نمونه، مدلی که هم متن و هم تصویر را می‌پذیرد و پاسخ متنی می‌دهد، برای سناریوهای بررسی تصویر همراه با توضیح کاربر مناسب‌تر از مدل صرفاً متنی است.

## پنجره زمینه و بیشینه خروجی

پنجره زمینه، تعداد تقریبی توکن‌هایی است که مدل می‌تواند در یک درخواست در نظر بگیرد. این مقدار شامل پیام‌های قبلی، متن ورودی، دستور سیستم، ابزارها و بخش‌هایی از پاسخ می‌شود. بیشینه توکن خروجی سقف تولید پاسخ را نشان می‌دهد.

| مقدار | پرسشی که جواب می‌دهد |
| --- | --- |
| پنجره زمینه | آیا مدل می‌تواند یک گفت‌وگوی طولانی، چند سند یا تاریخچه کامل تیکت را یکجا ببیند؟ |
| بیشینه توکن خروجی | آیا مدل می‌تواند پاسخ بلند، گزارش چندبخشی یا خروجی ساخت‌یافته کامل تولید کند؟ |

:::tip
پنجره زمینه بزرگ به معنی این نیست که همیشه باید ورودی را بزرگ بفرستید. برای هزینه و کیفیت بهتر، داده را تا حد ممکن مرتبط، کوتاه و مرتب نگه دارید.
:::

## وضعیت مدل و وضعیت ارائه‌دهنده

وضعیت به شما کمک می‌کند ریسک انتخاب را بفهمید:

| وضعیت | برداشت پیشنهادی |
| --- | --- |
| `active` | گزینه عادی برای بررسی و استفاده، مشروط به دسترسی فضای کاری شما. |
| `preview` | برای آزمایش و ارزیابی مناسب است؛ قبل از محیط عملیاتی محدودیت‌ها را بخوانید. |
| `deprecated` | برای توسعه جدید پیشنهاد نمی‌شود؛ اگر استفاده می‌کنید، برنامه مهاجرت داشته باشید. |
| `unavailable` | برای مصرف فعلی روی آن حساب نکنید. |

وضعیت ارائه‌دهنده با وضعیت مدل یکی نیست. ممکن است یک ارائه‌دهنده فعال باشد اما یک مدل خاص در حال کنارگذاری باشد، یا برعکس یک مدل در کاتالوگ شناخته شود اما در فضای کاری شما فعال نشده باشد.

## قیمت‌گذاری و هزینه استفاده

قیمت مدل معمولاً با چند عدد جداگانه نمایش داده می‌شود:

| نوع قیمت | معنی |
| --- | --- |
| قیمت ورودی | هزینه پردازش توکن‌های ورودی. برای جست‌وجو، خلاصه‌سازی اسناد و مکالمه‌های طولانی مهم است. |
| قیمت خروجی | هزینه تولید پاسخ. برای پاسخ‌های بلند، گزارش‌ها و تولید متن زیاد مهم‌تر می‌شود. |
| قیمت ورودی کش‌شده | اگر ارائه‌دهنده از کش ورودی پشتیبانی کند، هزینه بخش‌های تکراری ممکن است جدا محاسبه شود. |
| قیمت تصویر، صوت یا درخواست | اگر در داده مدل ثبت شده باشد، برای APIهای غیرمتنی یا مدل‌های چندوجهی اهمیت دارد. |

:::warning
قیمت نمایش‌داده‌شده را همراه با واحد، تاریخ اثر و منبع بخوانید. قیمت مدل‌ها ممکن است با زمان، منطقه، پلن ارائه‌دهنده یا تنظیمات حساب تغییر کند.
:::

در تنظیمات نمایش کاتالوگ ممکن است قیمت را با `USD`، `IRR` یا `TOMAN` و با مقیاس «به ازای یک میلیون توکن» یا «به ازای هر توکن» ببینید. برای مقایسه مالی، مطمئن شوید همه اعضای تیم واحد و مقیاس یکسانی را می‌بینند.

## قابلیت‌ها و پارامترهای پشتیبانی‌شده

قابلیت‌ها به شما می‌گویند مدل از چه توانایی‌هایی پشتیبانی می‌کند؛ مثلاً بینایی، ابزارخوانی، خروجی ساخت‌یافته یا قابلیت‌های مشابه. پارامترهای پشتیبانی‌شده نشان می‌دهند هنگام درخواست چه تنظیماتی برای مدل معنا دارد.

برای نمونه، اگر می‌خواهید پاسخ‌ها در قالب JSON معتبر برگردند، فقط دیدن قیمت کافی نیست؛ باید بررسی کنید مدل و API انتخابی با [خروجی ساخت‌یافته](/supported-apis/chat-completions/structured-outputs) سازگار هستند یا نه.

## منابع، مستندات و بنچمارک‌ها

کاتالوگ ممکن است برای هر مدل منابعی مثل مستندات رسمی، مدل‌کارت، منبع قیمت، بنچمارک یا تاریخچه تغییرات نشان دهد. این داده‌ها برای اعتمادپذیری تصمیم مهم‌اند، چون به شما اجازه می‌دهند عددها و ادعاها را پیگیری کنید.

:::tip
برای انتخاب مدل، بنچمارک را کنار سناریوی واقعی خودتان ببینید. مدلی که در یک بنچمارک عمومی بهتر است، ممکن است برای پاسخ‌های کوتاه پشتیبانی، تحلیل پیام‌های فارسی، یا هزینه ماهانه محصول شما بهترین انتخاب نباشد.
:::

## پرسش‌های پرتکرار

### اگر یک مدل چندوجهی است، یعنی برای همه ورودی‌ها بهترین انتخاب است؟

خیر. چندوجهی بودن یعنی مدل چند نوع داده را پشتیبانی می‌کند، نه اینکه برای همه آن‌ها بهترین کیفیت یا کمترین هزینه را دارد. سناریوی واقعی خودتان را تست کنید.

### پنجره زمینه بزرگ‌تر همیشه بهتر است؟

نه همیشه. پنجره بزرگ برای ورودی طولانی مفید است، اما می‌تواند هزینه و پیچیدگی پرامپت را بالا ببرد. اگر فقط چند پیام کوتاه دارید، معیارهای دیگری مثل هزینه، تاخیر، کیفیت و پایداری مهم‌تر می‌شوند.

### وضعیت `preview` را می‌توان در محیط عملیاتی استفاده کرد؟

فقط بعد از بررسی محدودیت‌ها، ریسک تغییرات و توافق داخلی تیم. برای مسیرهای حساس، مدل‌های `active` معمولاً انتخاب مطمئن‌تری هستند.
