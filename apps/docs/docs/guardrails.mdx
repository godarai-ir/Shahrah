# Guardrails در GodarAI

`Guardrails` در GodarAI به شما کمک می‌کند روی ورودی و خروجی مدل‌ها یک لایه کنترل و اعتبارسنجی (Validation) قرار دهید تا رفتار سیستم فقط به «پاسخ گرفتن از مدل» محدود نماند و از نظر ایمنی، سازگاری با policy و کیفیت خروجی هم قابل‌کنترل‌تر شود.

در عمل، بسیاری از خطاهای واقعی سیستم‌های مبتنی بر LLM به این خاطر نیست که provider در دسترس نبوده؛ بلکه به این خاطر است که پاسخ مدل برای pipeline شما مناسب نبوده است. Guardrails دقیقاً برای کاهش همین ریسک طراحی می‌شود.

## Guardrails چه مسئله‌ای را حل می‌کند؟

یک درخواست LLM ممکن است از نظر HTTP کاملاً موفق باشد، اما از نظر محصول یا عملیات شکست‌خورده محسوب شود. برای مثال:

- خروجی با schema مورد انتظار هم‌خوان نیست
- متن شامل محتوای پرریسک، ناسازگار یا غیرمجاز است
- کاربر prompt injection انجام داده است
- خروجی حاوی کد، لینک یا الگوی ممنوع است
- نتیجه برای نمایش مستقیم به کاربر مناسب نیست

Guardrails کمک می‌کند قبل یا بعد از اجرای مدل، این شرایط را بررسی کنید و بسته به نتیجه، تصمیم عملیاتی بگیرید.

## Guardrails را کجا اعمال می‌کنیم؟

به‌صورت مفهومی، Guardrails معمولاً روی یکی از این دو نقطه اعمال می‌شود:

- `ورودی` یا همان request پیش از ارسال به model
- `خروجی` یا همان response پیش از تحویل به مصرف‌کننده

این تفکیک مهم است، چون نوع کنترل در هر کدام متفاوت است:

- روی ورودی معمولاً دنبال prompt injection، محتوای ممنوع، الگوهای خطرناک یا داده‌های نامعتبر هستید
- روی خروجی معمولاً دنبال schema validation، policy enforcement، جلوگیری از افشای داده یا کنترل کیفیت پاسخ هستید

## نمونه Guardrailهای رایج

بسته به use case، Guardrailها می‌توانند از نوع قطعی (Deterministic) یا مبتنی بر مدل باشند. نمونه‌های رایج:

- Regex برای بررسی الگوی متن
- بررسی JSON Schema روی خروجی
- تشخیص وجود کد در پاسخ
- بررسی محتوای حساس یا ناسازگار با policy
- تشخیص prompt injection
- ارزیابی سطح gibberish یا بی‌معنا بودن خروجی

در بسیاری از سناریوها، [Moderation](/supported-apis/moderation) می‌تواند یکی از اجزای سبک‌تر این زنجیره باشد، اما Guardrails معمولاً از moderation گسترده‌تر است و به منطق orchestration هم وصل می‌شود.

## تفاوت Guardrails با Moderation

این دو را بهتر است یکی ندانیم:

- `Moderation` بیشتر برای تشخیص محتوای حساس یا پرریسک کاربرد دارد
- `Guardrails` یک لایه تصمیم‌گیری گسترده‌تر است که می‌تواند validation، blocking، fallback، retry، logging و feedback loop را هم شامل شود

اگر moderation به شما بگوید «این محتوا مشکوک است»، guardrail مشخص می‌کند بعدش چه اتفاقی باید بیفتد.

## رفتارهای ممکن بعد از Guardrail

ارزش واقعی Guardrails فقط در تشخیص نیست؛ در تصمیم بعد از تشخیص است. بسته به طراحی محصول، وقتی یک guardrail پاس یا fail شود، می‌توان این رفتارها را داشت:

- فقط نتیجه را log کنیم
- درخواست را متوقف کنیم
- پاسخ را به کاربر نشان ندهیم
- به مدل یا prompt دیگری fallback کنیم
- درخواست را retry کنیم
- برای ارزیابی بعدی، feedback یا dataset بسازیم

این الگو باعث می‌شود Guardrails بخشی از orchestration در gateway باشد، نه فقط یک هشدار جانبی.

## Guardrails و گیت‌وی چه نسبتی دارند؟

وقتی Guardrails در سطح gateway تعریف شوند، مزیت مهمی به‌دست می‌آورید:

- policyها بین چند سرویس و چند تیم یکدست‌تر می‌شوند
- enforcement از کد تک‌تک کلاینت‌ها جدا می‌شود
- تغییر policy نیازمند انتشار نسخه جدید همه سرویس‌ها نیست
- رفتارهای عملیاتی مثل fallback، retry و deny می‌توانند متمرکز شوند

این همان دلیلی است که Guardrails در GodarAI بیشتر یک قابلیت زیرساختی و محصولی است تا صرفاً یک helper در کد اپلیکیشن.

## چه زمانی Guardrails برای شما ضروری‌تر است؟

اگر یکی از شرایط زیر را دارید، Guardrails احتمالاً باید بخشی از طراحی پایه شما باشد:

- خروجی مدل را مستقیم به کاربر نهایی نشان می‌دهید
- با داده‌های حساس، سازمانی یا policy-bound کار می‌کنید
- agent یا workflow خودکار دارید
- پاسخ باید ساختار مشخصی داشته باشد
- چند تیم یا چند سرویس از یک لایه LLM مشترک استفاده می‌کنند

## نسبت Guardrails با Request Headers و هویت

در سناریوهای production، Guardrails وقتی مفیدتر می‌شود که به زمینه درخواست هم دسترسی داشته باشد. برای مثال:

- کدام tenant درخواست را فرستاده
- این ترافیک متعلق به کدام team یا workload است
- سطح دسترسی و policy این کلاینت چیست

به همین دلیل، درک [Request Headers](/request-headers) و مدل هویتی گدارAI برای طراحی guardrailهای خوب مهم است.

## نسبت Guardrails با مشاهده‌پذیری

اگر فقط guardrail را اجرا کنید اما نتیجه آن را در observability نبینید، به‌مرور فهمیدن اثر واقعی policyها سخت می‌شود. Guardrails وقتی ارزش بیشتری پیدا می‌کند که بتوانید این موارد را تحلیل کنید:

- کدام guardrail بیشترین fail را دارد
- failها مربوط به کدام team، model یا workload هستند
- کدام policy باعث افزایش latency شده است
- چند درخواست به دلیل guardrail متوقف، retry یا reroute شده‌اند

برای این لایه تحلیلی، [OpenTelemetry برای مشاهده‌پذیری](/observability-opentelemetry) و [رهگیری هزینه](/cost-tracking) می‌توانند مکمل خوبی باشند.

## رویکرد پیشنهادی برای شروع

برای بیشتر تیم‌ها، این مسیر عملی‌تر است:

1. اول integration پایه را با [شروع سریع](/quick-start) و [اولین درخواست به Gateway](/making-llm-requests-via-gateway) برقرار کنید.
2. بعد روی use caseهای پرریسک، Guardrailهای ساده و deterministic تعریف کنید.
3. سپس moderation، schema validation و policyهای سطح تیم یا tenant را اضافه کنید.
4. در نهایت، رفتارهای orchestration مثل deny، fallback یا retry را فقط جایی فعال کنید که اثرشان را در production سنجیده‌اید.

## چند توصیه عملی

### با Guardrailهای ساده شروع کنید

Regex، schema و ruleهای واضح معمولاً قبل از Guardrailهای پیچیده‌تر ارزش زیادی ایجاد می‌کنند.

### Guardrail را با business impact بسنجید

هر policy باید روشن کند چه ریسکی را کم می‌کند و چه هزینه‌ای مثل latency یا false positive دارد.

### deny را محتاطانه فعال کنید

بستن کامل request یا response تصمیم پرهزینه‌ای است و بهتر است بعد از مشاهده رفتار واقعی ترافیک انجام شود.

### Guardrail را فقط روی متن نگیرید

در سناریوهای tool-calling، structured output و workflowهای agentic، failure modeها فراتر از متن ساده هستند.

## FAQ

### آیا Guardrails همان Moderation است؟

خیر. moderation یکی از ابزارهای ممکن در این فضاست، اما guardrails دامنه بزرگ‌تری دارد و می‌تواند تصمیم‌های عملیاتی بعد از validation را هم شامل شود.

### آیا Guardrails فقط برای خروجی مدل است؟

خیر. خیلی وقت‌ها کنترل ورودی حتی مهم‌تر است، مخصوصاً برای prompt injection، داده نامعتبر و محتوای ناسازگار با policy.

### آیا همه Guardrailها باید request را متوقف کنند؟

نه. در بسیاری از موارد بهتر است ابتدا فقط log، measure و analyze کنید و بعد برای subsetهای حساس‌تر deny یا fallback را فعال کنید.
