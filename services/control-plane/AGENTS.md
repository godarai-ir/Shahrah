# control-plane AGENTS

## Purpose

Go implementation of Shahrah's control-plane and API gateway. This service owns:

- tenant-scoped management APIs under `/api/v1`
- gateway proxy endpoints under `/v1`
- auth, RBAC, onboarding, and login-discovery flows
- provider account, model, team, org-unit, virtual-user, PAT, and role management
- billing, wallet, and top-up flows
- request traces, trace privacy, metrics, and observability
- platform service-account administration for privileged automation
- response caching and provider-routing behavior

This is the backend source of truth for platform behavior. Frontends should consume it through their own app routes or contract clients.

## Working Rules

1. Treat `internal/` as service-private implementation.
2. Keep shared public types in `packages/contracts`; do not create a parallel
   control-plane type package.
3. Do not edit applied migration files in place.
4. Preserve secret redaction in logs and headers.
5. Prefer explicit contract tests over undocumented fallback behavior.
6. Use `MASTER_KEY` only as a bootstrap/admin credential; platform workloads should use scoped service accounts.
7. Keep canonical provider identities in `internal/providerregistry`. Provider
   HTTP adapters belong behind the provider-egress boundary in `services/silk-road`, not in a
   second control-plane provider registry.
8. Add persistence to the narrow feature repository (`PlanRepository`,
   `WalletRepository`, `SupportRepository`, or `ProviderAccountRepository`),
   not directly to `storage.Store`.
9. Keep transition, validation, and precedence rules in
   `internal/domain/<feature>`; storage loads and persists state.
10. Inject storage collaborators through `storage.StoreDependencies`; do not
    add post-construction setter injection.

## Current Entry Points

- `cmd/server`: main control-plane server
- `cmd/platform-service-account`: creates or revokes scoped platform service credentials
- `cmd/metricsbench`: metrics benchmarking helper

## Public API Surface

Protected and public routes are registered in `internal/server/server.go`.

Important groups include:

- `/health`, `/ready`, and `/metrics`
- `/v1/*` gateway endpoints for chat, completions, responses, embeddings, moderations, images, and model listing
- `/api/v1/*` management APIs for onboarding, PATs, teams, org units, virtual users, virtual models, wallets, traces, prompts, policies, providers, roles, users, and settings
- `/api/v2/traces/*` trace-detail endpoints used by tenant-admin
- `/api/v1/platform/*` platform-admin endpoints protected by `MASTER_KEY` or a scoped platform service account token

## Contract Notes

`control-plane` consumes `model-discovery` as an upstream API for provider-catalog flows.

- Live Swagger UI: `http://localhost:3002/docs`
- Live OpenAPI JSON: `http://localhost:3002/docs/openapi.json`
- Shared contract notes: [docs/model-discovery-api-contract.md](/D:/source/Shahrah/docs/model-discovery-api-contract.md)
- Contract test: [services/control-plane/internal/admin/provider_catalog_openapi_contract_test.go](/D:/source/Shahrah/services/control-plane/internal/admin/provider_catalog_openapi_contract_test.go)

When changing model-discovery usage:

1. Regenerate the upstream spec if needed.
2. Update control-plane handlers or client logic.
3. Extend the contract assertions for any new endpoint, required field, or parameter constraint.
4. Avoid adding silent fallback behavior that hides upstream drift.

## Required Configuration

Configuration is loaded from `proxy_config.yaml` plus environment variables.

Common required or important env vars:

- `DATABASE_URL`: required
- `MASTER_KEY`: required for platform-admin bootstrap APIs
- `CONTROL_PLANE_SERVICE_TOKEN`: generated by `cmd/platform-service-account`
- `SILK_ROAD_URL`: direct provider-egress endpoint for upstream provider traffic
- `REDIS_HOST`, `REDIS_PASSWORD`: optional cache backend
- `CLICKHOUSE_DSN`: trace storage/read backend
- `ZARINPAL_MERCHANT_ID`: required for `provider=zarinpal`
- `IDPAY_API_KEY`: required for `provider=idpay`
- `SHAHRAH_DISCOVERY_TOKEN`: optional dedicated model-discovery credential
- `SHAHRAH_SMART_CACHE_EMBEDDING_BASE_URL`: opaque embedding base URL for smart cache
- `SHAHRAH_SMART_CACHE_EMBEDDING_API_KEY`: embedding API credential for smart cache
- `TYPESAFE_API_KEY`: optional TypeSafe Jev credential for `semantic_policy` guardrails

## Database and Local Verification

Relevant migrations live under `db/main/migrations`.

Typical local verification:

```bash
go test ./...
go run ./cmd/server
go build ./cmd/server
```

For service-account provisioning:

```bash
go run ./cmd/platform-service-account --profile=support-admin
```

## Implementation Checklist

1. Add or update tests alongside behavior changes.
2. Verify route or schema changes against the consuming apps.
3. Check that logs, errors, and trace payloads do not leak secrets.
4. Confirm the relevant API contracts still match the consuming frontend expectations.
